## 1. 版本定位与结论

**1.x 末版**已经把"单进程、人工驱动"的泄漏排查主线做完整：选进程 → 预热打基线 → 每轮打点 → 判定摘要与打点区间 → 一键报告三件套 → 两任务对比。

**2.0.0 的定位**：从"看曲线的工具"升级为"可自动化、可通宵、可测多进程、可交付证据的泄漏排查工作台"。四条主线：

| 主线 | 2.0 要解决的空白 | 关键能力 |
|---|---|---|
| **自动化** | 没有任何程序化入口，接不进 CI 与自动化脚本 | `pmctl` 命令行 + 本地 IPC 协议 + 无窗口模式 + 判定退出码 / JUnit |
| **通宵与长时** | 存储 193 B/行，3 天数据打开 5 秒；被测崩溃即任务结束；工具重启不续采；电脑空闲睡眠 | 存储 v5（约 23 B/行）+ 分钟汇总 + 查询改写；退出取证、重启续接、续采、阻止睡眠、磁盘守卫 |
| **多进程** | 一个任务只对应一个 PID，子进程重建即跟丢 | 进程树 / 同名合并 / 合计 / 子进程数指标；全系统快照一次采全 |
| **证据与结论** | 报告缺被测版本与环境，结论要手抄，只能两两比 | 结论优先的分析页、报告版式 2.0、证据包 zip、多任务按轮对比、参考基线库、方案模板 |

同时补齐**大版本发布的地基**：1.4.1 用户的真实升级路径（库 v1 → v5）、安装器与更新通道兼容、性能基准、24 小时浸泡、真机清单、beta 流程。

**工作量**：全部条目名义约 **125 人日**（含测试与文档，已去重），其中 2.0.0 范围约 **100 人日**，其余进 2.1。参照上一轮：32.5 人日的重构方案由子智能体在约一个工作日的会话内完成；2.0.0 预计 **4–6 个工作日的会话** + **1–2 周 beta 观察期**。

## 2. 方案来源与已核实的事实

四位专家（opus）各自独立成文，主审（Fable）汇总去重并核实关键事实。原文存于本地 `context\02_项目维护\2.0规划提案\`（不入库）：`v2_proposal_workflow.md`（泄漏排查工作流，13 项功能 + 10 项优化）、`v2_proposal_ux.md`（界面，21 条问题 + 14 项提案）、`v2_proposal_engineering.md`（架构与性能，15 项，附本机实测）、`v2_proposal_quality.md`（质量与发布，升级矩阵 + 门槛 + 里程碑）。

**主审已亲自核实**：

| 事实 | 核实方式 | 影响 |
|---|---|---|
| 已发布的 1.4.1 数据库是 **v1**（`git show v1.4.1:data/database.py` → `SCHEMA_VERSION = 1`）；v2–v4 从未发布 | git | 真实升级路径是 v1 → v5 一次跑完；现有迁移测试全用手工构造的旧库，缺真实样本。2.0 加一环 v5 不增加用户感知的升级次数，**是改存储结构成本最低的时间点** |
| `compare_version("2.0.0-beta.1", "2.0.0")` 返回 1（判 beta 更新） | 运行 | beta 必须以 prerelease 发布且先修比较函数，否则 beta 用户收不到正式版 |
| 1.4.1 更新器只取**第一个**文件名含 `setup` 的 `.exe`，不校验 digest 与域名 | `git show v1.4.1:core/update_checker.py` | 2.0.0 Release 只能有一个含 setup 的 exe，ASCII 文件名 |
| `psutil.Process.num_threads()` 单次 **16 ms**（触发全系统进程快照）；`list_processes()` 冷启动 **1.9 s**（在主窗口显示前的界面线程上） | 运行 | 泄漏预设含线程数，5 任务每秒约 50–80 ms 纯采集开销；启动卡顿 |

**专家实测、主审未复核**（数量级可信，数值以阶段 0 固化的基线为准）：v4 存储 193 B/行；单任务 5 指标 1 秒周期跑 3 天后分析页"全部"范围整批加载 5.1 s、7 天 13.9 s；紧凑结构原型 23 B/行，基于分钟汇总的分桶 3 ms；onedir 141 MB / 安装包 44.6 MB。

**CHANGELOG 组织**：beta 期间继续写在"未发布"段，GA 时一次性整理；升级须知放第一屏（库升级到 v5 并备份为 `monitor.db.bak_v1`、所需空间、大库首次启动较慢、三项内存指标合并不可逆、页面合并、更新强制校验 SHA-256、数据目录不变、回退方法）。

## 11. 工作方式

- **指挥 / 执行**：主会话（Fable）拆任务、定接口、复核与验收；opus 子智能体按互不重叠的文件集并行实施；每阶段结束全量测试、离屏截图目测、本地提交；push / tag / Release 仍需用户明确授权。
- **独立评审**（opus `reviewer`）只用于高风险阶段：阶段 1（v5 迁移与汇总不变式）、阶段 2（IPC 安全边界、系统快照解析与回退）、阶段 3（续接 / 续采的状态机与退出路径不变式）。
- **测试承诺**：每项新能力经注入接口（`SnapshotHub`、`ProcessTreeSource`、`ExitCodeProbe`、`TargetInfoProbe`、`ProcessLauncher`、`WindowEventSource`、假时钟）在离屏下覆盖；ctypes 生产实现只做薄封装与降级路径测试。现有 1759 个用例不改断言语义（A-4 图表点集的有意变化除外，须在提交说明里写明）。
- **真机**：每阶段涉及界面的改动用 KimiCU 在真实窗口目测一次（临时数据目录）；发布前按 F-12 清单在打包安装版上完整走一遍。
