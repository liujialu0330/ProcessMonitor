## 1. 项目定位与技术栈

**进程监控助手（ProcessMonitor）** 是面向软件测试人员的 Windows 桌面应用：周期性采集指定进程的 26 项性能指标（内存 11 / CPU 4 / 系统资源 5 / IO 6），实时展示、SQLite 持久化、历史图表回放、CSV 导出，核心场景是用“基线—打点—变化量/增长速度”排查内存、句柄、GDI/USER 对象和线程泄漏。

| 技术 | 用途 |
|------|------|
| Python 3.8+（CI 与发布统一 3.11） | 语言 |
| PyQt5 + PyQt-Fluent-Widgets | 界面与 Fluent 控件、QConfig 用户配置体系 |
| psutil（+ ctypes 调 `user32.GetGuiResources`） | 进程指标采集 |
| pyqtgraph | 历史图表（日期轴、十字线、打点竖线、导出） |
| SQLite（标准库 `sqlite3`，WAL） | 持久化 |
| urllib（标准库） | 自动更新检查与下载 |
| PyInstaller（onedir）+ Inno Setup | 打包与安装包 |
| pytest | 自动化测试 |

仅面向 Windows（句柄/GDI/USER、托盘、命名管道单实例均依赖 Windows）。最多同时运行 5 个任务（`config.MAX_MONITOR_TASKS`）。

## 2. 目录与分层

四层单向依赖：**UI → Core → Data → Utils**，其上是组装层 `app/`（只在启动与退出时把各层拼起来），另有配置。跨层通信一律走 Qt 信号槽；UI 不绕过 core 直接写库（读查询允许直接走注入的 `Database`）。`ui` / `core` / `data` / `utils` 不得导入 `app` 包（`tests/test_layering.py` 守护）；根目录的 `config` 在访问兼容路径常量时惰性委托 `app.paths`，是唯一例外。

数据库与日志位置：路径规则只在 `app/paths.py` 的 `AppPaths.resolve()` 定义一份。打包后为 `%LOCALAPPDATA%\进程监控助手\data\monitor.db` 与 `...\logs\`；开发环境为项目下的 `data\` 与 `logs\`。设置了 `PROCESS_MONITOR_DATA_DIR`（非空）时数据目录以它为准，日志写到该目录下的 `logs\`。配置文件 `config.json` 与数据库同在数据目录。`resolve()` 只做纯计算，由组合根 `ensure_dirs()` 建目录，并把 `log_dir` 传给 `setup_logging`。

### 2.1 指标体系

指标键、分类、单位、中文名、说明集中在 `utils/metrics.py`，其余模块只引用不重复定义。要点：

- Windows 上 psutil 的 vms / pagefile / private 数值相同，已合并为 `memory_private`（“私有字节”），“提交大小峰值”改名“私有字节峰值”；旧键经 `canonical_metric_type` 归一，库里的旧键由 v1→v2 迁移改写。
- 内存类原始值单位为 KB，展示时按量级自适应 KB/MB/GB/TB；计数类指标为整数。
- “泄漏排查预设”（私有字节、句柄、GDI、USER、线程）是监控页默认选择，用户的上次选择保存在 `app_config.last_metrics`，读取时经 `normalize_metrics` 校验，非法或为空回落到预设。
- `num_ctx_switches_involuntary`（非自愿上下文切换）已废弃：Windows 上 psutil 恒为 0。它不在 `AVAILABLE_METRICS`（可选集合）里，列入 `DEPRECATED_METRICS`；显示名、单位与格式化保留，旧任务数据照常显示与导出。
- 新增指标需同步：键常量、分类列表、中文名、单位、说明、（内存类）KB 集合/整数集合，以及采集器中的取值分支。

### 2.2 页面职责

| 页面 | 职责 |
|------|------|
| 实时监控（`monitor_page`） | 进程搜索与 PID 输入、指标选择、周期与备注、创建任务；维护任务卡片（含已结束卡片）；打点、暂停/恢复、停止确认；配额提示 |
| 历史数据（`history_page`） | 任务/指标/时间范围筛选；统计条、趋势图（十字线、打点竖线、PNG/剪贴板导出）、明细表；运行中任务自动刷新；删除已停止任务的数据 |
| 导出数据（`export_page`） | 选择任务、任务摘要、保存路径与覆盖确认，驱动 `ExportWorker`；导出期间在 manager 登记，与清理数据库互斥 |
| 设置（`setting_page`） | 主题、默认周期、保留策略、托盘开关；数据库占用、清理压缩（后台线程，与运行中任务及导出互斥） |
| 关于（`about_page`） | 版本信息、检查/下载/安装更新、缺少校验信息时的发布页引导 |

页面依赖一律构造注入、必填，页面内不再自建数据库、管理器或服务：`MonitorPage` / `HistoryPage` / `ExportPage` / `SettingPage` 为 `(db, manager, services, parent=None)`，`AboutPage` 为 `(services, parent=None)`，`MainWindow` 为 `(db, manager, services)`。组合根 `app/bootstrap.py` 显式构造唯一的 `Database`、`MonitorManager(db=db)`、`ThreadRegistry` 与 `production_services(manager, registry)`，`MainWindow` 把同一份 `services` 分发给全部页面。进程查询（列表、按名查找并排除本程序自身）一律经 `services.process_query`（生产实现委托 `core.process_catalog`），页面不自行遍历进程表，也不为查询构造 `ProcessCollector`。页面的提示经 `services.notifier`、确认框/关窗三选/打开文件夹或网址经 `services.dialogs`、当前时刻经 `services.clock`，不直接调用 `InfoBar`、对话框类、`os.startfile` 或 `datetime.now`；测试用 `tests/factories.py` 构造页面并注入 `tests/doubles.py` 的替身。

### 2.3 配置分工

`config.py` 保存随代码发布的常量与缺省值；`app_config.py` 把其中需要用户可调的项包装为可持久化的 `ConfigItem`。页面与主窗口的业务读取（上次所选指标、默认周期、保留天数、关闭到托盘）经 `services.preferences`（生产实现 `ConfigPreferences` 读 `cfg`）；设置页的设置卡片直接绑定 `ConfigItem`，由卡片自身读写落盘。`app_config.py` 的主题项见 7.3 节契约。

- **取值范围只在 `app_config` 定义**：采集周期范围 `interval_range()` 与保留天数可选值 `retention_options()` 都从对应 `ConfigItem` 的校验器读出；页面经 `services.preferences.interval_range()` / `retention_options()` 取用（监控页周期输入框的范围、设置页保留天数选项的文案），不另写数字。
- **跳过的版本并入配置文件**：“跳过此版本”存于 `cfg.skipped_version`（`get_skipped_version` / `set_skipped_version`）。旧版单独保存的 `update_prefs.json` 由 `load_app_config` 一次性导入（`cfg` 已有值时以 `cfg` 为准）后删除；旧文件损坏按“未跳过”处理，删除失败只记日志、下次启动再试。

### 2.4 启动顺序（组合根）

`main.py → app.bootstrap.run()`，顺序固定，调整前先确认每一步的前置条件：

1. `AppPaths.resolve()` 并 `ensure_dirs()`；
2. 日志 `setup_logging(paths.log_dir)` 与全局异常兜底 `install_excepthook`（早于 ui/core/data 的导入，导入期异常也能落日志）；
3. 创建 `QApplication`（高 DPI、`setQuitOnLastWindowClosed(False)`）；
4. 单实例：已有实例时通知其激活窗口并返回 0（此时尚未创建任何线程与窗口）；否则开始监听；
5. `load_app_config(paths)`、排版、主题（页面构造时就会读配置）；
6. 显式调用迁移运行器 `MigrationRunner(...).migrate()`（可能备份、还原、改名库文件，必须早于任何常驻连接）；
7. `Database(paths.db_path, migrate=False, migration_report=...)`；
8. `MonitorManager(db=db)`（普通对象，非单例）；
9. `MaintenanceService.startup_reconcile(保留天数)`（任何任务启动之前）；
10. `ThreadRegistry()` 与 `production_services(manager, registry)`；
11. `MainWindow(db, manager, services)`。托盘控制器 `TrayController` 由主窗口在构造时创建并持有：托盘菜单与动作需要以窗口为父控件，生命周期与窗口一致，故不由组合根单独注入；退出协调器同理在真退出时由主窗口按注入的 manager、`services.threads`、db 现建；
12. 事件循环；返回后用 `os._exit` 结束进程（理由见第 6 节）。数据库只由退出协调器关闭一次，组合根不再重复关闭。

## 3. 线程模型与跨线程信号

### 3.1 线程清单

| 线程 | 类型 | 生命周期 |
|------|------|---------|
| UI 主线程 | Qt 事件循环 | 全程；所有控件与定时器只在此线程操作 |
| `MonitorWorker` | 每个监控任务一个 QThread | 任务启动到收尾结束；停止后对象不可复用，重新监控要新建任务；线程 `finished` 后由 manager 自行移除并释放 |
| `ExportWorker` | CSV 导出，`BackgroundTask` | 一次导出；可取消；使用页面注入的 `Database` 实例，线程内不另建 |
| `HistoryRefreshWorker` | 历史页运行中任务的自动刷新查询，`BackgroundTask` | 一次刷新；同一时刻最多一个，只读不改库；结果经 `LatestRequestGate` 判过期 |
| `CleanupWorker`（`core/workers/`） | 数据库清理与压缩，`BackgroundTask` | 一次清理；不可取消；维护锁由设置页在界面线程两段式占用（见 7.6 节） |
| `UpdateChecker` / `UpdateDownloader` | 更新检查与下载，`BackgroundTask` | 一次检查/下载；下载可取消 |

**短命线程的统一写法**（`core/workers/base.py`）：子类只实现 `execute(token)`，不覆盖 `run()`；返回值经 `result` 发出，异常一律捕获、记日志后经 `failed` 发出（`TaskError` 表示预期内失败，消息直接给用户、不记堆栈），`progress` 报进度；被取消（`CancelToken`）后既不发 `result` 也不发 `failed`。结果/失败信号是 `run()` 的最后一个动作。“最新请求获胜”用 `LatestRequestGate`：发起时 `next_seq()` 取号，结果回来 `is_current(seq)` 为真才应用。

**线程登记表**（`core/shutdown.py` 的 `ThreadRegistry`，经 `services.threads` 注入页面）：页面启动短命线程前 `register(thread, name=, cancel=, timeout_ms=)` 一次；线程 `finished` 时登记表自动注销并 `deleteLater`，页面不再自行连 `deleteLater`，也不在业务信号的槽里释放线程对象。退出时 `shutdown_all` 先对仍在运行的线程逐个调用取消回调，再按登记顺序逐个带超时等待，超时只记日志。现有登记：检查更新（1000ms，无取消）、更新下载（2000ms，可取消）、导出数据（2000ms，可取消）、清理数据库（5000ms，不可取消）、历史自动刷新（3000ms）。

### 3.2 采集线程的调度与收尾

- **调度**：按 `time.monotonic()` 截止时间推进，每周期 `deadline += interval`，不随采集耗时累积漂移；等待统一用 `threading.Event.wait(剩余时间)`，`stop` / `pause` / `resume` 置标志后 set 事件即可立即唤醒，无需轮询。落后超过一个周期（系统休眠唤醒、严重卡顿）则重置截止时间，不补采。暂停时无超时等待，恢复后立即采一次。
- **落库**：采集结果进缓冲后立即 flush（`SAVE_BATCH_SIZE` 固化为 1）。flush 失败时缓冲保留待下一周期重试，缓冲上限 1000 条（超出丢弃最旧），连续失败达到阈值经 `error_occurred` 通知界面一次。
- **停止**：`stop()` 只改状态并 set 事件，近乎立即返回、不阻塞界面。收尾（最后一次 flush → 写 `stopped` 状态 → 置 `STOPPED` → 发出 `task_stopped`）全部在线程自己的 `run()` 的 `finally` 中完成，因此界面收到 `task_stopped` 时数据与状态一定已落库。
- **线程对象释放**：manager 把每个任务线程的 `QThread.finished` 连到自己的槽，线程真正结束后由 manager 自行从字典移除、`deleteLater` 并发出 `task_removed`；界面不必、也不应在 `task_stopped` 的槽里释放线程。`remove_task` 不再 `wait()`：线程仍在运行（含收尾中）时只请求停止，移除交给 `finished`；线程没在运行时立即移除。`stop_all_tasks` 同样只给全部任务置停止标志、不等待，等待由退出协调器带超时完成（见第 6 节）。短命线程的释放见 3.1 节的线程登记表。
- **PID 复用**：采集器依赖 `psutil.Process.is_running()` 对进程创建时间的比对，PID 被新进程占用视为进程已退出，任务以 `StopReason.PROCESS_EXITED` 结束。从进程列表选进程时，`get_all_processes()` 返回的 `create_time` 经 `create_task(..., create_time=...)` 传给任务，线程启动时先与该 PID 当前进程比对，不一致直接以 `StopReason.PID_REUSED` 结束并报错、不写数据点（界面文案与进程退出相同，均为“进程已终止”）；手动输入 PID（无创建时间）或读不到创建时间时跳过比对。

### 3.3 任务状态

| 层 | 状态 | 说明 |
|----|------|------|
| 库（`tasks.status`） | `running` / `stopped` | 启动时写 `running`，收尾写 `stopped`；崩溃遗留的 `running` 由启动校正处理 |
| 线程（`MonitorWorker`） | 显式状态 `WorkerState`：`WAITING` / `RUNNING` / `PAUSED` / `STOPPING` / `STOPPED` | 读写一律经状态锁；`is_running()` / `is_paused()` 只由状态派生，不与 `QThread.isRunning()` 混用 |
| 卡片（`TaskCard`） | 运行中 / 已暂停 / 正在停止 / 已结束 | 已结束的卡片不占配额；“重新监控”新建任务 |

`WorkerState` 迁移表（其余组合一律拒绝且保持原状态）：

| 起始 | 触发 | 结果 |
|------|------|------|
| `WAITING` | `start()` | `RUNNING` |
| `WAITING` | `stop()` | `STOPPED`（从未启动，没有线程需要收尾） |
| `RUNNING` | `pause()` | `PAUSED` |
| `PAUSED` | `resume()` | `RUNNING` |
| `RUNNING` / `PAUSED` | `stop()` 或主循环自行结束（进程退出、PID 复用等） | `STOPPING` |
| `STOPPING` | 收尾落库完成（发出 `task_stopped` 之前） | `STOPPED`（终态，对象不可复用） |

两个口径：`ACTIVE_STATES = {RUNNING, PAUSED}`（已请求运行且未请求停止，即 `is_running()`）；`LIVE_STATES = {RUNNING, PAUSED, STOPPING}`（线程仍可能写库）。`create_task` 按 manager 中保存的任务数限制上限，线程结束后 manager 自行移除，已结束的卡片因此不占配额。界面上的“n/5 运行中”、退出确认与数据库维护互斥都以 `running_task_count`（按 `LIVE_STATES` 计数）为口径。

### 3.4 信号链

```
MonitorWorker ──data_updated(task_id, {指标: 值})────┐
            ──metrics_unavailable(task_id, {指标: UnavailableReason})┤
            ──task_stopped(task_id, StopReason)───────┤→ MonitorManager 同名信号（转发）→ MonitorPage / SettingPage 等
            ──error_occurred(task_id, msg)────────────┘
MonitorManager 另有 task_added / task_started / task_removed / task_limit_reached
MonitorPage ──history_requested(task_id)────────→ MainWindow：切到历史页并选中该任务
            ──task_ended_abnormally(title, msg)──→ MainWindow：窗口在后台时发托盘气泡
AboutPage   ──update_available_silent(info)─────→ MainWindow：非模态 InfoBar（托盘隐藏时补气泡）
ExportWorker ──export_progress / export_finished / error_occurred──→ ExportPage
UpdateChecker / UpdateDownloader ──check_finished / download_progress / download_finished / error_occurred──→ AboutPage
```

- `data_updated` 的载荷是每次新建的 `dict`；采集失败的指标不在其中。
- 停止原因与指标不可用原因在信号中传 `core/contracts.py` 的枚举（`task_stopped` 为 `pyqtSignal(str, object)`），中文文案只在 `ui/formatting.py` 的 `stop_reason_text` / `unavailable_reason_text` 中定义；`error_occurred` 仍传中文消息字符串。
- 界面不持有、不调用任务线程（`MonitorWorker`）对象：任务信息与状态经 `MonitorManager` 的只读快照与查询获取（`get_task_info` / `list_task_infos` 返回 `TaskInfo`，另有 `is_task_active`、`is_task_paused`、`has_running_task_for_pid`、`running_task_count`）。`get_task` / `get_all_tasks` 仅供 core 内部与测试使用。
- `MonitorManager` 是普通 QObject（不是单例），由组合根以唯一的 `Database` 实例构造后注入 `MainWindow`，再由主窗口向下分发；测试中每个用例各自构造。
- 单实例的“激活”消息由 `QLocalServer` 的新连接触发，发出 `SingleInstanceGuard.activation_requested`，由入口连接到激活主窗口。

## 4. 核心数据流

### 4.1 采集 → 落库 → 展示

```
用户选进程/指标/周期/备注 → MonitorPage 校验（不默认选进程、同 PID 重复需确认、配额只计运行中任务）
  → MonitorManager.create_task → 注入同一 Database 的 MonitorWorker → start
  → run(): 登记任务行 → 进程存在性检查 → 创建时间比对（有 create_time 时）→ (含 CPU 指标则预热，首个样本推迟一个周期) → 定时循环
        collect_metrics(指标列表)      一个周期共用 oneshot 缓存与同一时间戳
          · 成功的指标 → DataPoint 入缓冲 → flush 到 data_points（同事务更新 sample_count / last_sample_at）
          · 失败的指标 → 不入返回字典，记入 collector.last_unavailable（留空，不记 0）
        emit data_updated → TaskCard 刷新数值、较开始变化量、趋势图
        新出现的不可用指标 → emit metrics_unavailable（每指标每任务一次）→ 卡片“不可用” + 提示原因
  → 进程消失或用户停止 → 收尾 → task_stopped → 卡片保留为“已结束”（查看历史 / 重新监控 / 关闭）
```

采集失败语义是全链路契约：采集器、落库、卡片、历史图表、导出都把“缺失”当作空，绝不当作 0。权限不足时，非管理员运行对更高权限进程只有 `memory_uss` 采不到；其他会话进程（如 session 0 服务）的 GDI/USER 对象数抛“不支持”，与权限不足区分。

### 4.2 展示（历史页）

- 任务列表：`sample_count > 0` 的任务（单条 SQL）；下拉文本含时长、备注与“运行中”。默认范围“全部”；范围锚定该任务最后一个数据点的时间而非当前时刻。
- 图表数据由数据库端分桶降采样（最多 2000 桶，每桶取最小/最大两点）；统计条由 `analytics.legacy_stats` 在整个所选范围上聚合（起点/当前/变化量/增速/最小/最大，增速为最小二乘斜率，单位“每小时”）；明细表只取最近 2000 条并标注总数；打点另查 `task_markers` 画竖线。
- 坐标轴：`chart_axes` 中的纵轴按显示单位取整刻度，计数类指标用整数刻度；`sparkline` 与图表对平直曲线设纵轴最小跨度。
- 查询编排只有一份：`core/history_refresh_worker.query_history_data`（明细 `points.fetch(PointQuery)`、统计 `analytics.legacy_stats`、分桶 `analytics.legacy_buckets`、打点 `markers.list`，起点为 datetime），手动加载与自动刷新共用。读库失败（`StorageError`）时手动加载显示“读取数据失败”并弹错误提示，与“暂无数据”区分；自动刷新失败保留当前显示，连续失败只提示一次。
- 运行中任务：页面可见时定时刷新，保留用户的选择与缩放；查询（锚点、明细、分桶、统计、打点）在 `HistoryRefreshWorker` 中执行，worker 只查询并返回 dataclass，主线程槽再套用到控件，绝不在工作线程碰控件；结果带请求序号与（任务、指标、范围）标识，过期或已切换则丢弃；刷新间隔随数据量分三档拉长，明细视图、鼠标悬停图表、窗口最小化时跳过；任务结束时整体重载一次。
- 页面联动：历史页与导出页在 `showEvent` 中刷新任务列表（见 7.5 节）。

### 4.3 导出

`ExportPage` 选择任务与路径（切任务重置默认文件名，目标已存在需确认覆盖）→ 经 `manager.begin_export()` 登记（清理数据库进行中则拒绝并提示稍后再导出），线程 `finished` 时 `end_export` → `ExportWorker` 在线程中用 `points.iter_batches` 游标分批读取（打点经 `markers.list`；读库失败抛 `StorageError`，走导出失败路径），经 `core/export.py` 的纯函数透视为宽表（每行一次采集、每指标一列、末列“打点”）→ 写入同目录 `<目标>.tmp`，成功后 `os.replace` 到目标；取消或失败只删除临时文件，不破坏已有文件。CSV 为 UTF-8 BOM。

### 4.4 自动更新

`UpdateChecker` 拉取 GitHub 最新 Release → `parse_release_info` 提取版本、资产地址与 `asset_digest`。`UpdateDownloader` 只接受 https 且主机在白名单（`github.com`、`objects.githubusercontent.com`、`release-assets.githubusercontent.com` 及其子域）的地址，重定向同样校验；必须带有效的 `sha256:` digest，下载后逐字节校验，不一致删除文件。缺少 digest 时不下载，界面引导到发布页手动下载。静默检查（启动 3 秒后）发现新版本只发信号，由主窗口以非模态 InfoBar 提示。

## 5. 数据库表结构与迁移

### 5.1 表结构（Schema v4，`PRAGMA user_version = 4`）

| 表 | 列 | 说明 |
|----|----|------|
| `tasks` | `task_id` PK, `pid`, `process_name`, `metric_type`, `interval`, `start_time`, `end_time`, `status`, `note`, `sample_count`, `last_sample_at`, `create_time` | `metric_type` 存 JSON 数组文本；`sample_count` 为采样周期数（同一周期多指标算一次），与数据点同事务维护；历史页/导出页按 `sample_count > 0` 判断有数据；`create_time` 为被监控进程的创建时间（epoch 秒，可空，用于识别 PID 复用，`create_task` 传入后随任务行落库） |
| `data_points` | `id` PK, `task_id`, `timestamp`, `value`, `metric_type` | `metric_type` 可空（兼容旧数据）；仅有的一个（非 UNIQUE）索引 `(task_id, metric_type, timestamp)` |
| `task_markers` | `id` PK, `task_id`, `timestamp`, `label`, `created_at`, `kind` | 打点；`kind` 取 `user`/`baseline`/`pause`/`resume`（默认 `user`）；索引 `(task_id, timestamp)` |

- 外键约束未启用，删除任务时手工级联（`data_points`、`task_markers`、`tasks` 同一事务）。
- 每个连接统一设置 `journal_mode=WAL`、`busy_timeout=5000`、`synchronous=NORMAL`（`ConnectionFactory` 负责）。
- **常驻占位连接**：SQLite 在最后一个连接关闭时 checkpoint 并删除 `-wal/-shm`；每次操作新建连接、无常驻连接时，每次写入都等于“最后一个连接关闭”，`-wal` 被反复删除重建，实测单次写入约 13.65 ms。工厂默认持有一个只读（`query_only`）空闲连接让 `-wal` 常驻，单次写入降到约 1.55 ms；`-wal` 由自动 checkpoint 循环复用。迁移/备份/改名库文件时用 `keep_alive=False`（Windows 上打开的文件不能改名），`Database.close()` 释放占位连接。常驻连接下 `-wal` 不会随连接关闭被删，故 `Maintenance.vacuum` 在 VACUUM 前后各做一次 `wal_checkpoint(TRUNCATE)`，`cleanup_older_than` 删除后也截断一次，避免“压缩后占用反而变大”。
- 启动时（任务启动前）由组合根经 `MaintenanceService.startup_reconcile` 按序各调用一次：`reconcile_orphan_tasks`（把崩溃遗留的 `running` 任务校正为 `stopped`，结束时间取 `last_sample_at`）、`reconcile_sample_counts`（对 `sample_count=0` 但有数据点的任务重算，兜底“回退旧版再升级”的情形）、`cleanup_old_tasks`（保留天数默认 0 = 禁用，且必须在孤儿校正之后）。这些方法刻意不放在构造函数里。

### 5.2 迁移机制（v0 → v3）

- 新库直接建当前结构并置 `user_version`；旧库按 `user_version` 链式迁移：
  - **v0 → v1**：`data_points` 补 `metric_type` 并按任务原指标回填；`tasks.metric_type` 由裸字符串转 JSON 数组。
  - **v1 → v2**：`memory_vms` / `memory_pagefile` 并入 `memory_private`，同一 `(task_id, timestamp)` 的重复数据点去重。
  - **v2 → v3**：`tasks` 增加 `note` / `sample_count` / `last_sample_at`（幂等，先查列）；新建 `task_markers`；删除孤儿数据点；回填 NULL 的 `metric_type`；索引收敛为 `(task_id, metric_type, timestamp)` 并删除旧索引；回填 `sample_count` 与 `last_sample_at`。
  - **v3 → v4**：`tasks` 增加 `create_time`，`task_markers` 增加 `kind`（幂等，先查列）。
- 迁移代码在 `data/db/migrations/`：每版一个模块（`vN.py`，`apply(cursor)`），由 `MigrationRunner` 串成链并负责备份、事务、还原与结果报告（`MigrationReport.outcome`），`Database` 只把结果映射为三个提示标志。
- **事务与备份**：迁移前先 `wal_checkpoint(TRUNCATE)` 再文件级备份为 `monitor.db.bak_v{原版本}`；整条迁移链在一个显式事务里执行（DDL 与 `user_version` 同事务），任一步失败整体回滚，随后从备份还原并重试一次。
- **三态结果**（互斥，主窗口据此提示）：`migration_failed`（迁移失败且旧数据仍在原库：通常已从备份还原；还原与改名都失败时旧库原样保留、不写 `user_version`，下次启动重新迁移；本次运行新数据无法保存）、`data_reset`（还原也失败，损坏库连同 `-wal/-shm` 改名为 `.broken_<时间戳>`，以空库运行）、`backup_aborted`（备份失败，已中止迁移，旧库原样保留）。
- 整个流程每进程只尝试一次（类级 guard），避免反复实例化 `Database` 重复备份。
- 迁移代码用字面量写死别名与版本号，不引用会演进的常量（运行时解析函数的冻结副本在 `_frozen.py`）；新增迁移时只追加一个 `vN.py` 并在链上加一环。
- 旧库迁移未成功时，`TaskRepo.list_with_data` / `AnalyticsRepo.sample_count` 在缺少 `sample_count` 列时回退为按数据点判断，`mappers.row_to_task` 对缺失的新列取默认值，旧指标键在界面上仍显示为“私有字节”。

### 5.3 门面与仓储分工、错误语义

- **仓储**（`db.tasks` / `db.points` / `db.markers` / `db.analytics` / `db.maintenance`）共用 `Database` 的同一个连接工厂，每次操作自建连接，可在任意线程调用。失败一律抛 `StorageError`（原始 `sqlite3.Error` 挂在 `__cause__`）；参数类型错误（`TypeError`/`ValueError`）是调用方的编程错误，原样抛出，不伪装成存储故障。**新代码直接用仓储**，需要区分“读取失败”与“没有数据”的地方（历史页、导出、设置页清理）必须用仓储并捕获 `StorageError`。
- **门面旧方法**（`save_task`、`get_task_data_points`、`get_metric_stats`、`add_marker` 等）是对仓储的薄委托，签名与返回语义不变：原来吞异常返回 `None` / `[]` / `0` / `False` 的，捕获 `StorageError` 后记 ERROR 日志（带堆栈）并返回原值；成功时的布尔方法仍返回 `True`（与是否命中行无关）。`save_data_points` 的连续失败计数与日志节流（首次带堆栈，之后每 100 次一条）留在门面。旧方法的 `since_iso` 字符串在门面内部转成 `datetime` 再交给仓储。采集线程（`save_task` / `save_data_points` / `update_task_status`）与启动校正（`reconcile_*` / `cleanup_old_tasks`）继续走门面。
- **例外**：`vacuum()` 失败抛 `StorageError`（设置页据此提示“清理失败”，不再显示“完成”）；`iter_data_points()` 失败抛 `StorageError`（导出必须知道读取是否完整）。
- 打点 ID：`markers.add` 返回自增 ID；`MonitorManager.add_marker` 直接用它，门面 `add_marker` 仍只返回布尔。
- 依赖方向：`data` 不依赖 `core`。聚合结果转趋势拟合输入用 `core.analysis.trend.fit_input_from_aggregates(agg)`。`gaps` / `buckets` 的空洞判定默认倍数为 2.5（相邻采样间隔 > 2.5 × 采集周期）。

## 6. 退出路径不变式

组合根创建 `QApplication` 时设置 `setQuitOnLastWindowClosed(False)`，因此唯一真退出路径是 `MainWindow.closeEvent` 收尾完成后显式调用 `QApplication.quit()`；`app.bootstrap.run()` 在 `exec_()` 返回后以 `os._exit` 终止进程，规避仍在阻塞的后台线程（如卡在 `urlopen` 的下载线程）被销毁时 Qt 的致命中止（0xC0000409）。

**收尾只经 `ShutdownCoordinator`**（`core/shutdown.py`）。真退出时主窗口先隐藏窗口给出即时反馈，再按固定四步收尾，进度文案（“正在停止监控任务…”“正在结束后台操作…”“正在保存…”）写日志并显示在托盘图标的悬停文字上：

1. `manager.stop_all_tasks()`：给全部监控任务置停止标志（不等待）；紧接着 `registry.cancel_all()` 对登记表里仍在运行的短命线程（检查更新、下载、导出、清理、历史刷新）统一发出取消，让它们与任务收尾并行；
2. `manager.join_all(3000, deadline=)`：带超时等待任务线程收尾落库；
3. `registry.shutdown_all(deadline=)`：按登记顺序等待登记表线程（已取消的不重复取消），登记后从未启动的条目顺手清掉；
4. `db.close()`：关闭数据库（释放常驻占位连接）。

整个流程有 **30 秒总期限**：开始时换算成截止时间传给第 2、3 步，落实到每一次等待——每次取单项超时与剩余时间的较小者，剩余 ≤0 的直接跳过并记日志，因此卡住的线程再多，总耗时也不超过期限；期限耗尽后各步仍照常执行（只是不再等待），进度文案顺序不变，仍关闭数据库。任何一步出错只记日志、绝不抛异常。期限内没收完的线程随后被 `os._exit` 直接终止——“不丢数据”由“总期限 + 日志”兜底，而不是无限等待。以下不变式不得破坏（`tests/test_close_behavior.py` 守护）：

1. 默认配置（不最小化到托盘）且无运行中任务时，关窗直接走真退出。
2. 托盘菜单“退出”、关于页“立即安装”（`install_requested` → `quit_for_install`）都置 `_really_quit = True`，绕过隐藏分支与确认对话框，走同一条真退出路径。系统注销/关机（`commitDataRequest`，DirectConnection）同样置位，并在处理函数里直接 `close()` 进协调器：Qt 的会话结束流程只关闭可见窗口，隐藏在托盘时若等它发关闭事件，协调器会被绕过；收尾只做一次，之后的关闭事件直接接受。会话结束被取消、窗口重新显示（`showEvent` / 托盘“显示主界面”）时，只复位由会话结束置的标志，之后关窗仍走托盘与确认。
3. 隐藏到托盘不停止任务、不做任何清理，仅忽略本次关闭事件。
4. 有运行中任务且并非 `_really_quit` 时经 `services.dialogs.ask_close_action` 弹出三选（生产实现为 `CloseActionDialog`：最小化到托盘 / 停止监控并退出 / 取消）；主按钮与默认焦点是“最小化到托盘”，无托盘时隐藏主按钮、焦点给“取消”，“停止监控并退出”是普通按钮、回车不触发。开启“关闭时最小化到托盘”且托盘可用时直接隐藏。
5. 无托盘环境（offscreen/CI 或精简系统）下 `TrayController.is_available()` 为 False，所有托盘分支天然短路，行为退化为无托盘现状。
6. 真退出的收尾整体包进 `try/finally`，`QApplication.quit()` 放在 `finally`：收尾中途抛异常也必须退出，否则窗口已隐藏而事件循环不退出，用户无法恢复。`finally` 里先隐藏托盘图标（`os._exit` 不经 Qt 析构，不隐藏会残留幽灵图标）。
7. 真退出只经 `ShutdownCoordinator` 按上述四步收尾，总期限 30 秒按截止时间落实到每次等待、超时记日志；主窗口不逐页收尾线程，页面新增短命线程时只需在 `services.threads` 登记。
8. 单实例守卫在 `QApplication` 创建之后、窗口与线程创建之前运行：连上已有实例则发送激活消息并直接返回退出码 0；监听失败降级为允许多开，不能因单实例机制本身阻止用户使用。

## 7. 关键契约

### 7.1 采集失败语义

采不到的指标**不记 0**：`collect_metrics` 的返回字典中不包含它，原因记入 `collector.last_unavailable`；任务通过 `metrics_unavailable` 通知界面；库里该时间戳不存在对应行，历史图表与 CSV 按空处理。原因是 `UnavailableReason` 枚举。不适用的指标（如其他会话进程的 GDI/USER）以携带原因枚举的 `MetricNotSupported` 表达，与权限不足（`AccessDenied` → `ACCESS_DENIED`）区分，文案不同。进程不存在或 PID 被复用时 `collect_metrics` 返回 `None`，任务据此以 `StopReason.PROCESS_EXITED` 结束。

### 7.2 时间参数纪律：仓储只收 datetime

库内时间戳是 TEXT，一律为 `datetime.isoformat()` 形态，比较靠字典序。仓储的时间参数（`PointQuery.since/until`、`markers.list`、`analytics.*` 的 `since/until/ts`）**只接受 `datetime`**，在 `data/mappers.to_iso` 统一转成 ISO 文本，传入 float/int/str 直接 `TypeError`——从入口杜绝绘图用的 epoch float（`dp.timestamp.timestamp()`）流入查询（SQLite 会把它转成文本参与比较，恒小于任何 ISO 串，过滤静默失效）。`ui` 与 `core` 不再出现 `since_iso` 字符串参数；门面旧方法的 `since_iso` 仅为兼容保留，内部转换。

### 7.3 主题 themeMode 禁止重定义

`app_config.AppConfig` 直接复用 `QConfig` 基类内置的 `themeMode`，**不得**重新声明同名 `ConfigItem`。`qfluentwidgets.setTheme()` 操作模块级单例 `qconfig.themeMode`，`QConfig.set()` 又用 `is` 身份比较判断是否主题项；重定义会产生两个互不联动的对象，表现为“设置页选了深色没生效”“重启后主题还原”。启动时应用主题要传原始配置值 `cfg.get(cfg.themeMode)`（可能是 AUTO），不能传解析后的 `qconfig.theme`，否则会把“跟随系统”静默覆写成具体主题。

### 7.4 ComboBox 先 addItem 后 setItemData

qfluentwidgets 的 `ComboBox.addItem` 不返回索引，且不能在添加前设置 userData：必须先 `addItem(text)`，再用 `index = count() - 1` 调 `setItemData(index, value)`。任务下拉与指标下拉都靠 userData 携带 `task_id` / `metric_type`，文本只用于显示。

### 7.5 showEvent 联动

页面之间没有直接的数据推送，新建任务后历史页与导出页的任务列表靠各自的 `showEvent` 在每次切入时重新加载（历史页还借此启动自动刷新计时、`hideEvent` 停止；导出页同样在页面可见期间定时刷新运行中任务）。页面开着期间，运行中任务的下拉时长靠这两个定时器原地改写文字（`setItemText`），不重建列表，以免打断用户当前的选择与图表视图。新增依赖其他页面数据的页面时沿用此机制，并注意长耗时操作（如导出）期间用户切走再切回会重复触发 `showEvent`，需保证控件状态幂等。

### 7.6 数据库维护互斥

清理/压缩数据库与运行中任务、导出互斥，维护锁只经 `MaintenanceService` 占用与释放（底层是 `manager.begin_maintenance` / `end_maintenance`，页面不直接调用）。设置页用**两段式**：点击后先做只读预检（有运行中任务或导出时直接提示，不弹确认）→ 确认 → 在**界面线程**调用 `maintenance.begin()`（已有维护、有运行中任务或导出时抛 `MaintenanceBusy(reason)`，按 reason 提示，不启动线程）→ 以 `CleanupWorker(..., already_locked=True)` 启动后台线程（线程内 `cleanup_and_vacuum(days, already_locked=True)` 不占也不放锁）→ 线程 `finished`（无论成功、失败）后在界面线程 `maintenance.end()`。开始监控、开始导出的判断同样在界面线程，与占锁串行，因此不存在“确认之后、后台线程真正占锁之前”任务或导出趁机开始的窗口。维护期间 `create_task` / `start_task` / `begin_export` 被拒绝。不在界面上使用时，`cleanup_and_vacuum(days)` 自行占锁并在结束时释放。导出页启动线程前 `begin_export()`，线程 `finished` 时 `end_export()`（每个 worker 各注销一次，与页面引用是否已被替换无关）。删除任务数据（`delete_task_data`）对运行中任务同样拒绝。

### 7.7 日志与异常兜底

`app.bootstrap.run()` 最早处（解析路径之后）调用 `setup_logging`（根 logger 挂 `RotatingFileHandler`，5MB x 5）与 `install_excepthook`（未捕获异常记日志，并在主线程弹窗提示日志位置；`faulthandler` 把致命信号写入 `crash.log`）；工作线程中的异常只记日志、不打断采集。各模块一律用 `logging.getLogger(__name__)`。数据库失败的处理见 5.3 节：门面旧方法返回 `False` / 空结果并记日志；仓储抛 `StorageError`，由调用方转成界面上的失败提示。

### 7.8 其他约定

- 组合根构造并注入的 `Database` 是全应用唯一实例；`MonitorWorker` 的 `db` 必须注入（缺省抛 `TypeError`），`ui` / `core` 不得自建 `Database()`（`tests/test_layering.py` 守护）。
- 监控任务停止后线程对象不可复用，`start_task` 拒绝已结束的任务；“重新监控”通过新建任务实现。
- 耗时操作不放 UI 线程；UI 写库一律经 manager，读查询可走注入的 `Database`。
- 不可撤销操作（删除任务数据、清理数据库）的确认框统一经 `services.dialogs.confirm`，生产实现为 `ui/components/confirm.py` 的 `DestructiveConfirmBox`：按钮文案中文（如“删除”/“清理”与“取消”），显示后焦点在“取消”。

## 8. 测试与 CI

- 运行：`python -m pytest tests/`；用例清单用 `pytest --collect-only -q` 查看，本文不列清单。
- `pytest.ini` 只配置 `testpaths = tests`。`tests/conftest.py` 默认把 `QT_QPA_PLATFORM` 设为 `offscreen`，并通过自动 fixture 只设置环境变量 `PROCESS_MONITOR_DATA_DIR` 指向临时目录（不覆写任何路径常量，路径都由 `AppPaths.resolve()` 在使用时解析），**测试不得触碰开发机的 `data\`**；需要显式注入路径的用例用 `app_paths` fixture 拿到本用例的 `AppPaths`。另有会话级 `QApplication`、迁移记录与应用配置复位。新增涉及路径的模块时，从注入的 `AppPaths` 取路径，不新增模块级路径常量。
- 数据目录也可由环境变量 `PROCESS_MONITOR_DATA_DIR` 指定，便于便携运行与手工验证。
- 测试分层：数据层与迁移（含旧库构造）、采集与调度鲁棒性、导出纯函数与线程、更新校验、页面流程与界面契约（布局、排版、格式化）、单实例、日志与隔离；`tests/e2e/` 是 offscreen 下的全链路冒烟（建任务 → 采集 → 历史页 → 导出 → 设置页 → 关窗）。涉及 GUI 的用例用 offscreen，不弹窗口。
- CI（`.github/workflows/ci.yml`）：push 到 main 与 PR 触发，`windows-latest` + Python 3.11，用 `requirements-lock.txt` 安装依赖，设置 `QT_QPA_PLATFORM=offscreen` 后运行 `pytest tests/ -v`。
- 发布前建议另用真窗口跑一次 `tests/e2e/test_gui_smoke.py`（说明见打包文档）。

## 9. 打包与发布链

```
改版本号（config.APP_VERSION）→ 全量测试 → build\build.bat → GitHub Release（上传安装包）
```

- `build\build.bat` 是无人值守一键脚本：读取版本号 → 生成 `version_info.txt` → PyInstaller 以 onedir 模式打包（`ProcessMonitor.spec`）→ 校验产物体积/文件数并冒烟启动 → Inno Setup（`setup.iss`）编译安装包 → 产出 `dist\installer\进程监控助手_v{版本}_Setup.exe` 及同内容的 `Windows_v{版本}_Setup.exe`（后者用于 Release 资产命名）。
- 打包用 `requirements-lock.txt` 复现验证过的精确依赖；`requirements.txt` 只声明宽松下限供开发。
- 自动更新依赖 Release 资产的 `digest`（`sha256:`）：发布时上传的资产由 GitHub 生成摘要，应用据此校验；没有摘要时用户只能手动下载。
- 安装目录与数据目录分离（数据在 `%LOCALAPPDATA%`），覆盖安装与卸载重装不影响历史数据。
- 不提交 `build/` 下的临时产物、`dist/`、DLL/EXE、数据库；详细步骤、常见问题见 `build/README_打包说明.md`。
