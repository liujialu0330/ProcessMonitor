## 1. 项目定位与技术栈

**进程监控助手（ProcessMonitor）** 是面向软件测试人员的 Windows 桌面应用：周期性采集指定进程的 26 项性能指标（内存 11 / CPU 4 / 系统资源 5 / IO 6），实时展示、SQLite 持久化，在分析页给出每个指标的判定摘要、打点区间与趋势图（可两任务对比），并一键导出报告（图片 + 明细 CSV + 摘要 CSV）。核心场景是用“基线—打点—每轮增量/增速判定”排查内存、句柄、GDI/USER 对象和线程泄漏。

| 技术 | 用途 |
|------|------|
| Python 3.8+（CI 与发布统一 3.11） | 语言 |
| PyQt5 + PyQt-Fluent-Widgets | 界面与 Fluent 控件、QConfig 用户配置体系 |
| psutil（+ ctypes 调 `user32.GetGuiResources`） | 进程指标采集 |
| pyqtgraph | 分析页趋势图（小倍数/叠加、min/max 带、日期轴与相对时间轴、十字线、打点竖线、空洞阴影、概览刷选）与报告图片的离屏渲染 |
| SQLite（标准库 `sqlite3`，WAL） | 持久化 |
| urllib（标准库） | 自动更新检查与下载 |
| PyInstaller（onedir）+ Inno Setup | 打包与安装包 |
| pytest | 自动化测试 |

仅面向 Windows（句柄/GDI/USER、托盘、全局快捷键、命名互斥量单实例均依赖 Windows）。最多同时运行 5 个任务（`config.MAX_MONITOR_TASKS`）。

## 2. 目录与分层

数据库与日志位置：路径规则只在 `app/paths.py` 的 `AppPaths.resolve(env, frozen, argv)` 定义一份，数据目录按以下四级取第一个命中的来源，命中的是哪一级记在 `AppPaths.source`（`cli` / `env` / `portable` / `default`，常量在 `config.py`，兼容常量 `config.DATA_DIR_SOURCE` 供设置页显示）：

1. 命令行 `--data-dir <路径>` 或 `--data-dir=<路径>`（出现多次以最后一次为准；缺路径或路径为空抛 `DataDirError`，不当作当前目录）；
2. 环境变量 `PROCESS_MONITOR_DATA_DIR`（非空）；
3. 便携模式：基础目录（打包为 exe 所在目录，开发为项目根）下存在 `portable.flag` 时，数据在 `<基础目录>\data`、日志在 `<基础目录>\logs`；
4. 默认：打包后为 `%LOCALAPPDATA%\进程监控助手\data\monitor.db` 与同级的 `...\logs\`；开发环境为项目下的 `data\` 与 `logs\`。

前两级的日志写到数据目录下的 `logs\`。`argv` 缺省取 `sys.argv`，`config` 的兼容常量等惰性解析的调用方与组合根看到同一个数据目录；组合根把 `strip_data_dir_args` 去掉 `--data-dir` 后的参数交给 Qt。配置文件 `config.json` 与数据库同在数据目录。`resolve()` 只做纯计算（便携模式只检查标志文件是否存在），由组合根 `ensure_dirs()` 建目录，并把 `log_dir` 传给 `setup_logging`；数据目录不可用时的处理见 2.4 节。`sync_dir_hint(data_dir)` 是纯函数：数据目录位于 `%OneDrive%` / `%OneDriveConsumer%` / `%OneDriveCommercial%` 所指目录之下，或路径某一级目录名含 OneDrive、Dropbox、Google Drive、坚果云 / Nutstore、iCloudDrive（不区分大小写）时返回提示文案（SQLite 尤其 WAL 模式在同步过程中可能损坏）。

### 2.1 指标体系

指标键、分类、单位、中文名、说明集中在 `utils/metrics.py`，其余模块只引用不重复定义。要点：

- Windows 上 psutil 的 vms / pagefile / private 数值相同，已合并为 `memory_private`（“私有字节”），“提交大小峰值”改名“私有字节峰值”；旧键经 `canonical_metric_type` 归一，库里的旧键由 v1→v2 迁移改写。
- 内存类原始值单位为 KB，展示时按量级自适应 KB/MB/GB/TB；计数类指标为整数。
- “泄漏排查预设”（私有字节、句柄、GDI、USER、线程）是监控页默认选择，用户的上次选择保存在 `app_config.last_metrics`，读取时经 `normalize_metrics` 校验，非法或为空回落到预设。
- `num_ctx_switches_involuntary`（非自愿上下文切换）已废弃：Windows 上 psutil 恒为 0。它不在 `AVAILABLE_METRICS`（可选集合）里，列入 `DEPRECATED_METRICS`；显示名、单位与格式化保留，旧任务数据照常显示与导出。
- 指标元数据只有一份：`utils/metrics.py` 的 `REGISTRY`（`MetricSpec`：键、中文名、单位、分类、`kind`、说明、`requires`、`needs_priming`、预设排位、是否废弃）。显示名/单位/分类/预设/说明等旧表与 `is_integer_metric` / `is_kb_metric` / `format_metric_*` / `min_span_for` / `display_unit_for` / `KB_UNIT_DIVISORS` 全部由注册表按 `MetricKind` 派生（`BYTES_KB` / `PERCENT` / `SECONDS` / `COUNT` / `CUMULATIVE_COUNT` / `CUMULATIVE_BYTES` / `PEAK`）；迷你图与坐标轴不再各存一份百分比集合与 KB 换算表。
- 累计类指标（CPU 时间、页面错误、上下文切换、IO 次数与字节、峰值）`is_cumulative_metric` 为真：它们只增不减，不做"增速"外推。分析页对累计量（`CUMULATIVE_*` / `SECONDS`）画每秒速率、判定摘要显示“平均 X/秒”与“累计量”，峰值类（`PEAK`）显示“抬升 N 次”，详见 2.6 节。
- 纵轴最小跨度：水位量按 `min_span_for(指标)` 给出绝对下限（平直曲线不被放大成满幅波动）；累计量画每秒速率时按 `rate_min_span_for(指标, 参考值)` = max(5% × |参考值|, 1)，恒速曲线不再出现 999.6–1000.4 这类无意义刻度。迷你图与 ChartView 都经 `sparkline.compute_y_range` 取用。
- 采集侧是 `core/process_collector.py` 的 `SAMPLERS: dict[指标键, Callable[[psutil.Process], float]]`，每个指标一个采样函数并已换算到存储单位（字节类 KB，`_kb()` 是唯一的 `/1024`）；`collect_metrics` 按键查表分派，不可用原因的处理不变。`tests/test_samplers.py` 断言 `SAMPLERS.keys() == REGISTRY.keys()`。
- 新增指标只改两处：`REGISTRY` 加一个 `MetricSpec`，`SAMPLERS` 加一个采样函数。
- 进程组（tree / name 任务）的指标：序列键 `指标@成员键`（成员键 = 进程名小写）与合计序列并存，`spec()` / `value_class` / 显示名 / 单位对它们按指标部分解析；进程组专属指标 `process_count`（“进程总数”）放在独立的 `GROUP_REGISTRY`，不进 `REGISTRY`（pid 任务不可选，`len(REGISTRY)` 与 `MetricType` 的一一对应不变）；聚合方式由 `MetricKind` 派生（`group_aggregation`），`MetricSpec.group_applicable=False` 的指标（基本优先级）与峰值类对组不适用。详见 2.8 节。

页面依赖一律构造注入、必填，页面内不再自建数据库、管理器或服务：`MonitorPage` / `AnalysisPage` / `SettingPage` 为 `(db, manager, services, parent=None, ...)`（监控页另收 `hotkey_text`，设置页另收 `maintenance`、`hotkey`），`AboutUpdateGroup` 为 `(services, parent=None)` 并由设置页构造（主窗口经 `setting_page.about_group` 取用），`MainWindow` 为 `(db, manager, services, hotkey=None)`。组合根 `app/bootstrap.py` 显式构造唯一的 `Database`、`MonitorManager(db=db)`、`ThreadRegistry` 与 `production_services(manager, registry)`，`MainWindow` 把同一份 `services` 分发给全部页面。进程查询（列表、按名查找并排除本程序自身）一律经 `services.process_query`（生产实现委托 `core.process_catalog`），页面不自行遍历进程表，也不为查询构造 `ProcessCollector`。页面的提示经 `services.notifier`（统一入口 `route(event, level, title, content, *, action, key)`，便捷写法 `info / success / warning / error(parent, …)` 等价于 `route` 并以 `parent` 为无主窗口时的挂靠控件）、确认框/关窗三选/打开文件夹或网址经 `services.dialogs`、当前时刻经 `services.clock`，不直接调用 `InfoBar`、对话框类、`os.startfile` 或 `datetime.now`；测试用 `tests/factories.py` 构造页面并注入 `tests/doubles.py` 的替身。

### 2.3 配置分工

`config.py` 保存随代码发布的常量与缺省值；`app_config.py` 把其中需要用户可调的项包装为可持久化的 `ConfigItem`。页面与主窗口的业务读取（上次所选指标、默认周期、保留天数、关闭到托盘）经 `services.preferences`（生产实现 `ConfigPreferences` 读 `cfg`）；设置页的设置卡片直接绑定 `ConfigItem`，由卡片自身读写落盘。`app_config.py` 的主题项见 7.3 节契约。

- **取值范围只在 `app_config` 定义**：采集周期范围 `interval_range()` 与保留天数可选值 `retention_options()` 都从对应 `ConfigItem` 的校验器读出；页面经 `services.preferences.interval_range()` / `retention_options()` 取用（监控页周期输入框的范围、设置页保留天数选项的文案），不另写数字。
- **跳过的版本并入配置文件**：“跳过此版本”存于 `cfg.skipped_version`（`get_skipped_version` / `set_skipped_version`）。旧版单独保存的 `update_prefs.json` 由 `load_app_config` 一次性导入（`cfg` 已有值时以 `cfg` 为准）后删除；旧文件损坏按“未跳过”处理，删除失败只记日志、下次启动再试。
- **通知开关与窗口记忆**：`notify_in_background`（Notification 节，默认开，设置页“通知”分组；偏好服务 `notify_in_background()` 现读）；`window_geometry`（`[x, y, 宽, 高]`，最大化时为还原后的位置与大小，空列表 = 没有记录）、`window_maximized`、`window_page`（`monitor` / `analysis` / `setting`）、`analysis_task` / `analysis_range` / `analysis_view_mode` / `analysis_time_mode`（空串 = 没有记录）。窗口与分析页状态经 `ui.window_state.ConfigWindowMemory` 读写，`app_config.update_values` 批量写：只写真的变了的项、整批只落盘一次。
- **配置文件版本化**：`config.json` 根上的 `config_version` 记录文件格式版本（当前 `CURRENT_CONFIG_VERSION = 3`；缺失或不是正整数按 1）。`load_app_config` 读文件后、交给 qconfig 之前经 `migrate_config`（纯函数，表驱动 `CONFIG_MIGRATIONS`：键为源版本，函数把它变换到下一版本，版本号由 `migrate_config` 统一写）迁到当前版本，**只有真的迁移过才回写**（先写 `.tmp` 再 `os.replace`）；版本高于当前时不改写文件、记 WARNING，按能识别的键读取，保存时保留未知的键。v1 → v2 只写版本号：指标键的清洗（废弃键剔除、旧内存键映射）由 `normalize_metrics` 在每次加载时完成；v2 → v3 同样只写版本号（新增窗口记忆与通知开关，缺键即缺省值）。新增版本时在 `CONFIG_MIGRATIONS` 加一项并调大 `CURRENT_CONFIG_VERSION`。

### 2.4 启动顺序（组合根）

`main.py → app.bootstrap.run()`，顺序固定，调整前先确认每一步的前置条件：

1. `AppPaths.resolve(argv=argv)` 并 `ensure_dirs()`（四级来源见第 2 节目录树之后的路径规则）。`--data-dir` 缺路径、路径非法或无权限建目录时：日志尚未初始化，只在默认位置的日志目录（`AppPaths.default().log_dir`）记一条错误并输出到标准错误，打包版（没有控制台）另弹原生错误框写明路径与原因，返回退出码 2（`EXIT_DATA_DIR_UNAVAILABLE`）；**绝不回退到其他数据目录**（那会让数据悄悄写到别处）；
2. 日志 `setup_logging(paths.log_dir)` 与全局异常兜底 `install_excepthook`（早于 ui/core/data 的导入，导入期异常也能落日志）；随即记“数据目录: …（来源: …）”；
3. 创建 `QApplication`（高 DPI、`setQuitOnLastWindowClosed(False)`；命令行先经 `strip_data_dir_args` 去掉 `--data-dir`）；
4. 单实例 `SingleInstanceGuard(data_dir=paths.data_dir)`：已有实例时通知其激活窗口并返回 0（此时尚未创建任何线程与窗口）；否则成为主实例并立即 `listen()` 开始 IPC 监听（激活消息与 pmctl 命令同一条管道，组装完成前除 ping / activate 外的命令回 `not_ready`；细则见本节末与 2.7 节）。`--background`（无窗口模式）的从实例不发激活消息，监听失败直接返回 4（`EXIT_IPC_UNAVAILABLE`），其余步骤改走 `_run_headless`（见 2.7 节）；
5. `load_app_config(paths)`、排版、主题（页面构造时就会读配置；进度窗口也要跟随主题）；
6. 迁移数据库（可能建临时文件、换库、改名，必须早于任何常驻连接）：先 `MigrationRunner.probe()` 只读探测（裸连接，不写入）；需要迁移且待搬迁行数估计（`data_points` 的最大 rowid）超过 `MIGRATION_PROGRESS_THRESHOLD_ROWS`（50 万）或库文件（含 `-wal`）超过 `MIGRATION_PROGRESS_THRESHOLD_BYTES`（100 MB）时，经 `ui/windows/migration_window.run_with_progress_window` 先显示进度窗口、迁移在 `MigrationWorker`（`BackgroundTask`）工作线程执行；否则在界面线程同步 `migrate()`。探测或迁移本身抛出的异常（库被锁、文件损坏）原样交给全局异常兜底，下次启动重新检测。结果为 `FAILED_KEPT`（旧库没能回到原路径）时弹原生错误框写明原文件位置与“改名回 monitor.db 后重启即可重试”，返回退出码 3（`EXIT_MIGRATION_FAILED`）——继续启动会让连接工厂在原路径建出空库，用户的数据看上去“没了”；
7. 只读判定后构造 `Database(paths.db_path, migrate=False, migration_report=..., read_only=..., newer_version=..., schema_mismatch=...)`：迁移没成功（`BACKUP_ABORTED` / `FAILED_RESTORED` / `FAILED_KEPT`，库仍是旧结构；`FAILED_KEPT` 实际已在第 6 步退出）时 `read_only=True, schema_mismatch=True`——本版本的读写都按 v5 结构写成，不能在旧结构上写；否则用 `meta.read_meta_file` 读库的 meta（裸连接加 `query_only`：连接工厂的可写连接会把库切成 WAL，对更高版本写出的库这本身就是一次写入），`reader_blocked` 判定 `min_reader_version` 高于本版本时只读打开并带上写入者版本 `newer_version`。比较时本版本只取发布号部分（`2.0.0-beta.1` 按 `2.0.0` 比：库结构在一个发布线的第一个预发布版就已定稿）；读 meta 失败按可写打开并记日志；
8. `MonitorManager(db=db)`（普通对象，非单例）；
9. `MaintenanceService.startup_reconcile(保留天数, legacy_importer=...)`（任何任务启动之前；只读库整个跳过；步骤见 5.1 节）。其中导回回退 1.4.1 期间数据一步，待导回行数超过 50 万时同样经进度窗口在工作线程执行（标题“正在合并回退期间的数据…”）；
10. `ThreadRegistry()` 与 `production_services(manager, registry)`；`build_context` 另组装 `PowerGuard`（监控期间阻止系统空闲睡眠）与 `SelfMonitor`；
11. 全局打点快捷键：`MarkerHotkey()` → `install(app)` → `bind(偏好里的 marker_hotkey)`（不可用时只记日志，见 2.5 节降级规则），随后 `MainWindow(db, manager, services, hotkey=hotkey)`。托盘控制器 `TrayController` 由主窗口在构造时创建并持有：托盘菜单与动作需要以窗口为父控件，生命周期与窗口一致，故不由组合根单独注入；退出协调器同理在真退出时由主窗口按注入的 manager、`services.threads`、db 现建。窗口显示后依次：`install_watchdog` 安装界面卡死看门狗并交给主窗口（真退出收尾前先停掉，见 7.9 节）、`start_self_monitor` 启动自身监控定时器、`start_storage_guard` 让主窗口接上存储守卫（`attach_storage_guard`：提示、卡片标注、设置页警告）并启动它的定时器、连接激活信号、`_attach_ipc_to_window` 把命令处理器的上下文（manager、db、监控页 Presenter 持有的 `AutoMarkerService`、线程登记表、`services.launcher`、`window.request_quit`）交给 IPC（此前非 ping / activate 的命令都回 `not_ready`）；随后 `sync_dir_hint(paths.data_dir)` 命中时记 WARNING 并调用 `window.show_sync_dir_warning(提示)`；
12. 事件循环；返回后用 `os._exit` 结束进程（理由见第 6 节）。数据库只由退出协调器关闭一次，组合根不再重复关闭。

`build_context()` 是第 7～9 步（没传入迁移报告时先在这里同步迁移），不涉及 `QApplication` 与窗口。

**会话锁与续采**（`core/session_lock.py`、`core/session_recovery.py`）：数据目录下的 `session.lock`（JSON：PID、进程创建时间、启动时间、版本）在第 9 步校正之后写入，所有正常退出路径收尾完成后删除：主窗口真退出（关窗、托盘退出、命令行 `quit`、会话结束）在 `_run_shutdown` 里 `ShutdownCoordinator` 走完之后、`finally` 中删；无窗口模式由 `HeadlessRuntime.quit()` 的 `exit_hooks` 在收尾之后删；事件循环结束后组合根再兜底删一次；隐藏到托盘不是退出，不删。启动时在校正之前先判断上次的结局（`PreviousSession`）：没有锁 = 正常；有锁但记录的进程已不在、PID 已被别的程序占用（创建时间对不上，读不到创建时间时退回比可执行文件名）或锁损坏 = 异常退出（被强杀 / 崩溃 / 断电）；有锁且进程仍是本程序 = 另一个实例（单实例守卫之外的兜底），不判异常，不覆盖也不删它的锁，**启动校正也整个跳过**（库里“运行中”的任务是它正在跑的，校正会把它们收尾成“已停止”并清理数据）；探测记录的进程时权限不足（如上一个实例以管理员身份运行，`probe_process` 抛 `ProbeIndeterminate`）= `UNKNOWN`，无法确认它在不在：不覆盖也不删它的锁、不提供续采，**启动校正同样整个跳过**（它可能正在跑，同 `OTHER_INSTANCE`），只记日志。异常退出时，库里仍是 `running`、被测进程还活着（创建时间与记录一致，进程名也必须一致、不区分大小写——手动输入 PID 的任务没有创建时间，PID 被别的程序占用时靠名字区分；按名监控的任务没有单一被测进程，总是候选）的任务不被启动校正收掉（`startup_reconcile(protect_task_ids=…)`），留在 `AppContext.recovery_candidates`；窗口显示后（`QTimer.singleShot(0)`）弹“继续监控”对话框（`ui/dialogs/recover_dialog.py`，多选、默认全选、“全部放弃”）。选中的由 `MonitorManager.recover_task` 沿用原 `task_id`、开始时间与已有数据重建采集线程（续采成功之后才按库里的方案重新挂接自动打点：停止时长按墙钟从任务原来的开始时间算，与 `stop_condition_reached` 同口径，工具停摆的那段也算；定时打点与阶段快照的节奏从续采时刻起），线程启动时写一条 `kind='recover'` 打点（中断期间是数据空洞，由分钟汇总的空洞机制自然呈现；`recover` 不切启动段）；放弃与续采失败的按孤儿任务收尾（`reconcile_orphan_tasks(only=…)`，结束时间取最后一次采样）。无窗口模式不弹窗：缺省全部照常收尾并记一行日志，加 `--resume-tasks` 则全部续采（该参数同样不交给 Qt）。被强杀后最多丢失一个采集周期的数据：`SAVE_BATCH_SIZE=1`，每周期落库（`tests/test_session_recovery.py` 守护）。续采任务的数据质量列在库里已有值上累加（计划 / 完成 / 跳过周期相加，p95 无法相加取较大者）。

**`--startup-trace`**：各阶段末尾记一次单调时钟（`core.diagnostics.StartupTrace`：路径与日志 / QApplication / 单实例与命令行监听 / 配置与主题 / 迁移 / 组装 / 主窗口 / 显示 / 就绪），启动完成（窗口显示或无窗口模式就绪）后把各阶段耗时写一条 INFO 日志；交给 Qt 之前经 `strip_startup_trace_arg` 去掉该参数。

**迁移进度窗口**（`ui/windows/migration_window.py`）：没有关闭按钮、迁移结束前忽略关闭事件（中途退出会留下 `.migrating`，下次从头再来）。状态行“已处理 N / M 行”、生成汇总阶段“正在生成汇总 N / M”（按序列数），有备份时每行接“ · 备份保存在 <路径>”；进度条按比例换算到固定刻度（行数可能超过 32 位整数）。迁移运行器的进度回调在工作线程里同步调用，worker 只发信号，经队列连接回到界面线程。界面线程**自己轮询**：`worker.wait(50)` 之间 `processEvents()`，不用局部 `QEventLoop`——主事件循环开始前若有人调用过 `QCoreApplication.quit()/exit()`，Qt 5 的局部循环会立即返回，界面线程随即卡在 `wait()` 上。结束后补显示最后一次进度、关闭窗口，结果或异常原样交还组合根。

**启动提示**（主窗口按 `Database` 的标志在窗口显示后给出）：

- 升级成功：“数据库已升级到 v5，旧文件已保留为 monitor.db.bak_v1（可用于回退到 1.4.1）”（文件名按实际备份）；
- 只读库（`read_only`）：顶部常驻横幅（标题“只读模式”），并立即让监控页禁止开始监控与打点（就近提示）。升级没成功、库仍是旧结构（`schema_mismatch`）时横幅为“数据库尚未升级（上次升级失败：<原因>），本次以只读方式打开：不能开始监控与打点，历史数据要等升级完成后才能查看与分析”，并按 `MigrationReport.disk_shortage` 附处理建议（释放磁盘空间 / 关闭可能占用数据库的程序）；此时不再另弹迁移失败提示，历史数据读不出（见 4.2 节）。库由更高版本创建时为“数据库由更高版本（X）创建，本版本以只读方式打开：可以查看与导出，不能开始监控”；
- 门面的三态失败提示（“数据库升级已中止”带磁盘预检的所需/可用空间、“数据库升级失败”带原因、“数据库已重置”）只在库未标 `schema_mismatch` 时弹出；生产路径里迁移没成功一律走上面的只读横幅，`FAILED_KEPT` 在第 6 步已退出；
- 数据目录在同步盘：常驻警告（标题“存储位置风险”），每次启动都提示，不弹对话框。

**单实例细则**（`app/single_instance.py`）：

- **判据与通道分离**：判据是 Windows 命名互斥量 `Global\<实例名>`（ctypes 调 `CreateMutexW`，原子操作，并发启动也只有一个能新建成功）：新建成功即主实例，`ERROR_ALREADY_EXISTS` 即从实例；`ERROR_ACCESS_DENIED`（同名对象存在但打不开，典型是已有实例以管理员身份运行）也按已有实例处理；创建 `Global\` 失败（既不是已存在、也不是拒绝访问，如受限令牌）才退回 `Local\<实例名>` 并记日志，因此探测“实例是否存在”的一方（pmctl）两个名字都要查。用全局命名空间是因为命名管道全机唯一、不分会话：互斥量若在会话局部，同一用户在两个会话（本地控制台 + 远程桌面、计划任务）里各起一份，两边都拿到互斥量、却只有一边能监听管道，另一边就成了收不到命令、关不掉的实例；名字里含用户名，不同用户互不干扰。通道是与实例同名的本地管道 `IpcServer`（`QLocalServer`，设 `UserAccessOption`：DACL 只给当前用户，默认的 NoOptions 会让任何人都能只读连上），传激活消息与 pmctl 命令（2.7 节）；旧版从实例发的裸 `b'activate'`（无换行、发完就断开）仍然认，保留一个版本。
- **实例名** = `ProcessMonitor_<清洗后的用户名>_<sha1(normcase(abspath(数据目录)))[:12]>`，互斥量与管道同名：同一用户、同一数据目录只运行一个实例，不同数据目录（`--data-dir` / `PROCESS_MONITOR_DATA_DIR` / 便携模式）可同时各开一个，同机多用户互不影响。算法在 `utils/instance_name.py`（单实例守卫、IPC 客户端与 pmctl 共用：`single_instance.py` 顶层导入 PyQt5，pmctl 不能依赖它）。
- **从实例**连接管道失败按 50 / 100 / 200 / 400 / 800 ms 退避重试（主实例可能刚拿到互斥量还没 `listen()`），总上限约 3 秒；连没连上都退出——互斥量已证明主实例存在。`--background` 的从实例发的激活请求被忽略（不会把用户的窗口拉到前台）；已有实例是无窗口模式时 `activate` 回 `invalid_state`，窗口模式的从实例据此弹提示“请先用 pmctl quit 结束它，再打开主界面”后退出。
- **安装器探测**：主实例另持有固定名互斥量 `ProcessMonitor.Running`（常量 `INSTALLER_MUTEX_NAME`，会话局部与 `Global\` 各一个，已存在也保留句柄），供 `setup.iss` 的 `AppMutex` 判断程序是否在运行（安装器不知道数据目录，算不出实例名）；见第 9 节。互斥量句柄不主动关闭，随进程结束由系统回收。
- **降级**：ctypes / 互斥量调用失败一律按“允许启动”处理并记日志；非 Windows 没有命名互斥量，退回管道判据（连上即视为已有实例）。主实例 `listen()` 失败只记日志、照常启动（收不到后续的激活请求）。
- **已知边界**：自动更新时安装程序由 `os.startfile` 拉起、主程序随后才退出，安装器可能先提示“请关闭程序”（留待后续处理）；管理员实例已在运行时，普通权限启动的实例约 3 秒后静默退出（不会激活管理员实例的窗口）。

### 2.5 界面层结构

页面文件只做组装与连线：把控件信号接到视图模型 / Presenter 的命令，把它们的信号接回控件更新。业务状态与流程放在无控件的 `viewmodels/` 与 `presenters/`，可复用的控件放在 `widgets/`，纯数据的选项拼装放在 `models/`。页面之间不互相引用，跳转经主窗口中转。

**公共外壳与控件**

| 模块 | 作用 |
|------|------|
| `PageScaffold` | 监控、分析两页的基类：透明无边框的纵向滚动区 + 页头（标题、可选副标题、右侧命令区 `add_header_widget`）+ 内容布局 `add_section`；页边距与区块间距统一为 24，页面不再各写一份 |
| `EmptyStateCard` | “暂无数据 / 读取失败 / 尚未选择”作为内容区的一种状态（图标 + 标题 + 说明），不用浮层提示反复打断操作；分析页内容区使用（监控页没有任务时用专门的三步引导 `EmptyGuideCard`） |
| `qfw_compat` | qfluentwidgets 兼容封装：`InputDialogBase`（显示后焦点交给输入控件并全选，打点对话框继承它）、`CnSwitchSettingCard`（开关文案保持中文）；模块说明是**已知特殊行为清单**的唯一出处（见 7.4 节），能封装的封装一次，不封装的（显式 `setMinimumHeight` 覆盖布局最小尺寸）在清单里说明原因并有回归测试 |
| `SearchableCombo` | 可搜索下拉：调用方只面对“选项 `(文本, 数据)` 列表 + 当前数据”；`set_items(pairs, keep=)` 一次完成清空、填充、不选中、恢复选中且不发信号；`current_data()` 只在输入框文本与所选项完全一致时返回数据；回车时文本正好是某项则选中它，纯数字按调用方给的规则选中对应项或原样保留（交给 PID 解析），其余选补全首项，不让库把手输文本加成新选项 |

**通知渠道：`ui/services/notifier.py` 的 `Notifier.route`**

所有提示（页面的 InfoBar、托盘气泡、存储提示、更新提示）只经 `services.notifier`；生产实现 `InfoBarNotifier` 按“窗口状态 × 级别”选渠道，主窗口创建后经 `attach(window, tray=, background_enabled=)` 接入（替身通知服务没有 `attach` 时主窗口跳过）：

| 主窗口状态（`window_state`） | 渠道 |
|------|------|
| 前台（可见且激活） | 主窗口上的 InfoBar，`InfoBarPosition.BOTTOM_RIGHT`（挂在主窗口而不是某个页面，切页不丢） |
| 后台（可见但未激活 / 最小化 / 隐藏到托盘） | 托盘气泡（设置项 `notify_in_background` 为开且托盘可用）；常驻提示（错误、不自动消失的警告）另在主窗口上留一条 InfoBar；气泡发不出去（开关关闭、无托盘）时所有提示都留在主窗口上 |
| 无主窗口（无窗口模式；没有 `attach`） | 只写日志；调用方给了 `anchor` 时（页面单独使用、测试）挂在 `anchor` 上 |

- **参数**：`event` 事件名（`EVENT_*`，用于日志与是否闪任务栏）、`level`（success / info / warning / error）、`action=NoticeAction(文本, 回调)` 带按钮（InfoBar 上的 `PushButton`；气泡没有按钮）、`key` 同类合并键、`duration` 显式时长（毫秒，小于 0 常驻）。返回 InfoBar；只发了气泡 / 只写了日志时 `route` 返回 `None`，便捷写法返回占位对象 `DetachedBar`（`addWidget` / `close` / `closedSignal` 照常可调）。
- **停留时长**（`resolve_duration`）：成功 / 一般 2 秒、警告 5 秒、带操作按钮 6 秒、错误常驻；调用方显式给值时以调用方为准。
- **同类合并**：同一 `key` 最多同时 2 条；再来第 3 条时关掉最旧的一条，保留最近的两条，并在最新一条末尾写“（另有 N 条同类提示）”（N 是已被关掉的条数，之后每多一条加 1，不会让最早的那条一直挂着）；上一条的“另有 N 条”后缀随之撤掉（`NoticeBar.set_content`），数字只出现在最新一条上；带 N 的那条自己关闭后计数归零。`NoticeBar` 另补了库的一个缺陷：关掉最旧一条后紧接着弹的新条拿到没有起止值的“下沉”动画，会顶掉自己的滑入动画而停在窗口右边界外，显示时把两个动画的起止值对齐。
- **闪任务栏**：`ALERT_EVENTS`（`task.abnormal_end` 被测进程崩溃 / 退出、`task.error` 内部错误）发生时窗口在后台（最小化或被盖住）调 `QApplication.alert(主窗口, 0)`，与气泡开关无关；前台不闪。
- **存储提示的“同一时刻一条”**：`StorageNotices` 在发新的空间类提示前先 `close()` 上一条，新提示可能没有提示条（后台气泡），所以先关后发。
- 气泡标题 / 正文分别截到 60 / 240 字；`NoticeBar` 在显示后追加按钮时重算右下角位置。

**窗口与工作状态记忆（`ui/window_state.py` + `MainWindow`）**

- **记什么**：窗口几何（最大化 / 最小化 / 全屏时取 `normalGeometry`）、是否最大化、当前页；分析页：用户亲手选过的任务（默认自动选中的最新任务不记）、预设时间范围（刷选出的自定义范围不记）、视图（小倍数 / 叠加Δ%）与时间模式。摘要表用户勾选的列（表头右键）也一并记住（`AnalysisMemory.summary_columns`，配置项 `analysis_summary_columns`，逗号分隔的列键，空 = 没有勾选过、列随档位走）。
- **启动**：`place_window(记住的几何, 各屏幕可用区, 最小尺寸)`：与某屏幕的交叠不小于 100×50 时沿用（大小收进该屏、位置挪到完全落在其可用区内），否则（没有记录 / 已完全不在任何屏幕上）默认大小居中到主屏；默认大小 `min(1280×820, 主屏可用区 × 90%)`，不小于窗口最小尺寸。随后按记忆最大化，`AnalysisPage.restore_memory` 恢复范围 / 视图并交给视图模型 `restore_selection(task_id)`：下一次载入任务列表时按该任务选中；任务已被删除则静默退回默认的“自动选中最新任务”，不提示。
- **启动页**：记住的页面；`manager.has_running_tasks()` 时固定为监控页。续采在窗口显示之后才发生，组合根在 `run_recovery` 续采了任务后调 `MainWindow.show_monitor_page()`。
- **保存时机**：几何（移动 / 缩放）、页面切换与分析页选择 / 范围 / 视图变化后防抖 1 秒（`WINDOW_STATE_SAVE_DELAY_MS`，单次定时器每次变化重新计时）；真退出时 `closeEvent` 在收尾之前立即保存一次。`WindowMemoryStore.save` 内容没变不写盘，失败只记日志。
- **服务与测试**：`UiServices.window_memory` 为 `None`（测试默认）时主窗口不记忆、不写配置；测试注入 `tests/doubles.FakeWindowMemory`（屏幕列表可指定）。

**响应式布局（`ui/layout_breakpoints.py`）**

- **档位**：按“内容区宽度”——页面区域（`PageScaffold` 自身宽度，侧栏已扣除；不是窗口宽度）分三档：compact < 900、regular 900–1099、wide ≥ 1100；窗口 1280（侧栏展开）的内容区约 1130，属 wide（实测 9 列在约 1027 px 内放得下，默认窗口显示全部列），约 1000 宽的窗口属 regular，1920 最大化属 wide，800 的最小窗口属 compact。切换带 ±16 px 回滞（向上要达到 916 / 1116，向下要低于 884 / 1084），拖动窗口边缘不会来回抖；第一次喂入宽度按无回滞的纯函数算。
- **广播**：`LayoutBreakpoints.track(widget)` 跟随控件 Resize 喂宽度，档位变了发 `tier_changed(档位)`；页面（`PageScaffold.breakpoints`）与主窗口（`MainWindow.breakpoints`，跟随页面堆叠区）各持一个。页面把子控件的订阅在一处接上（`AnalysisPage._apply_tier`），控件自己决定怎么调整，不在各自的 `resizeEvent` 里写宽度判断。
- **各档位规则**：

| 控件 | wide | regular | compact |
|------|------|---------|---------|
| 摘要表列 | 全部（指标 · 基线 · 当前 · 较基线 · 每轮均增 · 增速 · R² · 末段趋势 · 判定 · 上限占比） | 不单列“增速 · R²”（并入“指标”与“判定”的悬停提示）与“末段趋势” | 再把“基线”“当前”合成“基线 → 当前”，不单列“上限占比” |
| 小倍数图 | 3 列 | 2 列 | 1 列 |
| 工具条范围 | 七段分段控件 | 七段分段控件 | 下拉（与分段控件同步），任务槽位最小宽度 240 → 150 |
| 结论条 | 依据与刷新状态在主句右侧 | 同左 | 依据、刷新状态与“复制结论”移到第二行 |
| 侧栏 | 窗口 ≥ 1200 展开（qfluentwidgets 在窗口窄于 1200 时自动收起） | 同左 | 进入 compact 时若侧栏正以占位方式展开则收成图标栏 |

- **摘要表的列**：`plan_columns(档位, 用户勾选)` 给出显示哪些列；“指标”“判定”始终可见；表头右键（`SummaryTable.column_menu`）勾选列，勾选结果（`user_columns`）优先于档位默认——设置后各档位都显示所勾选的列、不再合并“基线 → 当前”，菜单“恢复默认”回到跟随档位；没有任何带上限的指标时“上限占比”无论如何不显示。勾选经 `columns_changed` → 主窗口防抖保存 → `AnalysisMemory.summary_columns`。
- **高 DPI**：控件取设备像素比一律用 `devicePixelRatioF()`（`QWidget.devicePixelRatio()` 返回整数，125% / 150% 下会取整）；`QScreen` / `QImage` 的 `devicePixelRatio()` 本身是小数，`tests/test_layout_breakpoints.py` 的扫描只放行这两处。

**任务下拉：`TaskOptionsModel` + `TaskSelector`（分析页任务选择与对比任务共用）**

- `TaskOptionsModel`（纯 Python）：输入任务列表、运行中任务 ID 集合（任务状态服务的视角，不看库里的 `status` 列）与调用方给出的 `now`，输出选项（文本、提示、是否运行中）。`rebuild` 整体重建；`refresh_running(now, running_ids, latest)` 只原地更新运行中任务的时长文案，返回发生变化的下标。选项文本的开始时间固定为“月-日 时:分”，带年份的完整日期由提示给出。
- `TaskSelector`（薄控件）：`set_options(options, keep_id)` 整体替换并按 `keep_id` 恢复选中，全程不发信号；`update_option(index, option)` 原地改写一项；`select_by_id(id, silent=)` 程序选中；`current_id()`；逐项悬停提示。**对外唯一的信号是 `task_selected(task_id, explicit)`**：`explicit` 为真表示用户在下拉里点选，为假表示程序选中。内部 `combo` 只供布局与“模拟用户点选”的测试使用。

**分析页：`AnalysisViewModel` + `HistoryAutoRefresh` + `widgets/analysis` 控件**

`AnalysisViewModel`（QObject，无控件、不弹提示）继承 `HistoryViewModel`：基类持有任务列表、当前任务/焦点指标/时间范围、是否自动选中、可否删除与加载中状态，以及选择规则、异步查询、过期判断与自动刷新；子类在其上做多指标分析、自定义范围、视图模式、任务对比、导出与打点编辑。

| 命令 | 说明 |
|------|------|
| `reload_tasks()` | 主线程读任务列表（单条 SQL），随后按选择规则恢复/跟随/回落，并发起数据加载 |
| `select_task(id, explicit)` | 选中任务；任务不在列表（尚无数据）时返回 False，页面据此提示 |
| `select_metric(metric)` | 切换焦点指标：已有该指标的结果时直接显示，不再查库 |
| `set_range(key)` / `set_custom_range(start, end)` / `refresh()` | 切预设范围（含“自基线”）、概览条刷选出的自定义范围（过短视为误触）、手动刷新 |
| `set_view_mode` / `set_time_mode` | 小倍数 / 叠加 Δ%，绝对 / 相对时间（纯显示状态，不查库） |
| `set_compare_task(id)` | 选择对比任务（None 关闭对比），按焦点指标异步查它的快照 |
| `add_marker_at` / 改名 / 删除 / 设为基线 | 右键打点编辑，经 manager 执行；成功后 `markers_changed` 触发静默重查 |
| `select_member(key)` | 进程组任务专用：切到某个成员（None = 合计）；整页改用 `指标@成员键` 序列，不查合计、只读成员快照；成员没有数据时发 `empty_state`，焦点指标挪到该成员第一个有数据的指标。pid 任务恒返回 False |
| `start_export(job)` | 启动 `ReportWorker`；被拒时返回原因（导出进行中 / 清理数据库中） |
| `delete_current()` | 删除当前已结束任务的数据（确认框由页面经 services 弹出） |
| `on_tick()` / `cancel_pending()` | 自动刷新到点（与用户操作同一查询路径与请求序号）/ 页面隐藏时让在途查询作废 |

| 信号 | 含义 |
|------|------|
| `tasks_changed(list, set, now)` / `tasks_refreshed(list, set, now)` | 任务列表重建 / 只原地刷新运行时长等文案；页面经 `TaskOptionsModel` 重填或改写下拉 |
| `selection_changed(task_id, metric, explicit)` | 当前选择；页面以 `select_by_id(silent=True)` 同步下拉 |
| `analysis_ready(TaskAnalysis)` | 一次加载的全部指标快照，紧接着发焦点指标的 `snapshot_ready(HistorySnapshot)`；`auto_refresh` 为真时保留用户的缩放/平移 |
| `custom_range_changed` / `view_mode_changed` / `time_mode_changed` | 自定义范围与视图状态 |
| `compare_ready(CompareResult)` | 对比结果（关闭对比时为 None） |
| `members_changed(list[MemberOption])` / `member_selection_changed(member)` | 进程组任务的成员下拉选项（按显示名排序，含实例数）/ 当前成员（None = 合计）；换任务、清空选择时先发空列表 |
| `export_busy` / `export_progress` / `export_finished` / `export_failed` | 导出线程开始/结束、已处理点数、`ReportResult`、失败说明 |
| `empty_state(title, hint)` / `busy(bool)` / `error(title, content)` | 空状态卡；用户操作触发的加载（定时刷新不置忙，页面超过 300ms 才显示进度条）；需要提示的错误（自动刷新的连续读库失败只发一次） |

- **选择只走一条路径**：恢复选中、自动跟随最新任务、用户选过不再切走、选中任务消失后回落（自动选中时）或清空（用户显式选中时）都集中在 `reload_tasks` 里；控件的程序设置一律不发信号，页面因此不需要 `blockSignals`。换任务时自定义范围自动回到“全部”。
- **多指标并行、整批判过期**：一次加载对任务的每个指标各发一个 `run_history_query(analysis=True)`，经注入的执行器并行跑在后台线程（生产实现 `HistoryWorkerRunner`：每个请求一个 `HistoryRefreshWorker`，登记到 `services.threads`；线程没送出结果就结束时补一个失败快照）；全部返回后合并为 `TaskAnalysis`，按批次序号（`LatestRequestGate`）整体判过期，切换后迟到的结果直接丢弃。同一事件循环轮次内的多次加载请求合并成一次（导航跳转时“页面显示重载 + 选中目标任务”只查一次）。唯一留在主线程的读取是任务列表。焦点指标只决定明细表、区间表与概览条显示哪个指标。
- **进程组任务的成员视图**（tree / name，见 2.8 节；pid 任务整条路径不变）：任务查询仍只查合计，`last_analysis` / `last_snapshot` 恒为合计；成员数据由独立的“成员加载”补充——`MemberRunner`（注入点，生产实现 `MemberWorkerRunner`：登记为“进程组成员查询”，一次请求用一个 `MemberSnapshotsWorker` 线程按序读完全部成员序列；测试用 `synchronous_member_runner(db)`，只注入 `worker_runner` 时自动配同步版）与合计同批判过期，批次要等合计与成员都回来才发 `analysis_ready`。`select_member` 之后 `view_analysis()` 把成员快照拼成页面用的 `TaskAnalysis`，`series_key(metric)` 给出当前该画的序列键（`指标@成员键`），页面、概览条与焦点图都经它取数；`select_metric` 先去掉 `@` 后缀。成员从任务里消失时自动回落到合计；换任务一律回到合计。整体判定横幅用 `core.verdict.member_overall`（合计与全部成员合并，点名上涨的成员）；摘要表在成员视图下用该成员各序列的判定。
- **重启续接任务的逐段判定**：合计与成员都回来后，`focus.segment_count > 1` 的任务再由 `SegmentsRunner`（注入点，生产实现 `SegmentsWorkerRunner`：登记为“分段判定查询”，一个 `SegmentsWorker` 线程调 `core.history_query.load_segments`，与 `pmctl verdict`、证据包同一函数；测试用 `synchronous_segments_runner(db)`，只注入 `worker_runner` 时自动配同步版）在后台加载，随 `TaskAnalysis.segments` 一起发布，批次未齐不发 `analysis_ready`；没有重启（一段）的任务直接用已有快照构造，不查库。统计落在最后一段时（`reuse_last`）复用这批快照作最后一段，自定义范围落在更早的段时最后一段也重查；加载失败记 WARNING 并沿用同一任务上一次的分段。
- **上限占比**：进程组合计的上限占比一律写“—”（悬停“进程组合计不适用单进程上限”）；成员实例数大于 1 时同样写“—”（悬停说明多实例求和不适用单进程上限）。`object_count_limit` 只认基础指标键，成员键要先 `split_member_key`。

**全局打点：托盘菜单与快捷键**

- 托盘右键菜单“打点”不弹窗，直接用默认名称在当前时刻打点：只有一个任务时是一项“打点（demo.exe · PID 1234）”，多个任务时是子菜单（全部任务 + 逐个任务），没有任务时置灰；候选任务在菜单弹出前经 `MonitorPresenter.marker_targets` 现取。
- 全局快捷键 `ui/hotkey.py` 的 `MarkerHotkey`：Windows 上经 `RegisterHotKey`（窗口句柄为空，热键归界面线程）注册，`QAbstractNativeEventFilter` 接收 `WM_HOTKEY` 后发 `triggered`；组合根创建、`install(app)` 并按 `app_config.marker_hotkey` `bind`，设置页改键时重新绑定。注册经可替换的后端（`Win32HotkeyBackend` / `NullHotkeyBackend`），**测试一律注入假后端并用假消息驱动过滤器，不在开发机上注册真实热键**。

- 两个入口都汇到 `MainWindow.quick_marker(task_id=None)` → `MonitorPresenter.quick_marker`：未指定任务时作用于全部运行中/已暂停任务（同一次操作的打点共用一个 `undo_group`）；成功时走打点回显（见下），失败与没有可打点的任务经 `quick_marker_feedback` 交给主窗口，由 Notifier 提示。

**打点回显与撤销（`ui/presenters/marker_feedback.py` + `MonitorManager.undo_*`）**

- **回显**：弹窗打点、托盘与全局快捷键打点成功后，`MarkerFeedback.announce` 经 `Notifier.route(EVENT_MARKER_ADDED, 'success', …, action=NoticeAction("撤销"), key=EVENT_MARKER_ADDED)` 提示（窗口在前台是带“撤销”按钮的提示条，6 秒；不在前台走 E-4 的渠道规则，气泡没有按钮）。内容 `ui.formatting.marker_echo_text`：`第 7 轮 · 句柄数 +18 个 · GDI对象数 ±0 · 私有字节 +1.2 MB（较上轮）`——增量 = 本次打点时刻与上一个打点（时间上最近的更早的用户打点或基线；上一个是基线时写“较基线”）时刻各指标的值之差（`manager.sample_values_at`：时刻之前最近一个样本，采集每周期落库），只列任务的前 3 个指标，某个指标任一端没有值就跳过，一个都算不出（含本次是基线）时只写名称。多个任务一起打点时标题为“已打点：N 个任务”，内容逐任务列出，“撤销”撤销整批。自动打点（定时 / 日志）不弹回显，只能 Ctrl+Z。
- **撤销**：`MonitorManager.add_marker` 为用户打点与基线登记待撤销条目（带新增时刻、同批 `undo_group`、新增基线时被降级的旧基线 ID，最多 20 条）；`undo_marker(marker_id)` / `undo_last_marker()` 在 `UNDO_WINDOW_SECONDS = 30` 秒内从库里删除该条（含同组）、发 `markers_changed`，返回 `UndoOutcome(status, markers)`（`UNDO_OK` / `UNDO_EXPIRED` / `UNDO_NOTHING` / `UNDO_FAILED`；超时的登记随即丢弃，手动删除的打点同时从登记里去掉）。**编号回退**：“第 N 轮”的 N 是用户打点个数 + 1，撤销一条用户打点后自然回到原值；撤销的是基线时，被它降级成普通打点的旧基线要恢复成基线（否则它多算一个用户打点，编号会错位），除非用户在这期间另设了基线。系统打点（暂停 / 恢复 / 崩溃等）不进撤销登记。结果由 `MarkerFeedback` 提示：成功“已撤销打点：第 3 轮（demo.exe）”，超时“已超过 30 秒，无法撤销”，没有可撤销的、写库失败各有说明。
- **迷你图刻度**：`SparklineWidget.set_markers` 接收打点对象（也兼容 `(时间, kind)`）；刻度可悬停（鼠标距刻度 ≤ 5 px），文字 `ui.formatting.marker_tick_text`：`第 3 轮 · 10:21:05 · 备注`（序号按用户打点先后数，名称就是默认名时不重复写，基线写“基线”，系统打点写自己的说明）；用户打点与基线刻度可右键（发 `marker_menu_requested`，经 `TaskCard` → `TaskBoard` → Presenter），异常退出 / 重启 / 续采只能悬停。

**分析查询共享模块 `core/history_query.py`**：`HistoryRequest`（不可变：任务、指标、范围键、起点/终点、表格与分桶上限、锚点、请求序号、是否自动刷新、`baseline_only`、`analysis`）→ `run_history_query(db, request)` → `HistorySnapshot`（明细点、统计、分桶点、速率序列、打点、基线、空洞、判定与增速、逐轮增量；`analysis=True` 时另有 min/max 带与打点区间；`error` / `storage_error` / `task_missing` 区分失败类型，`ok` 为成功且任务仍在）。同步执行、与线程无关，手动加载与自动刷新共用；`HistoryRefreshWorker` 只是它的线程外壳。

### 2.7 命令行控制、无窗口模式与自动化

**协议**（`core/ipc/protocol.py`，只用标准库，服务端与 pmctl 共用）：UTF-8 JSON 行，一行一条、`\n` 结尾，`ensure_ascii=True`，单行不超过 1 MiB（超出回 `bad_request` 并断开）。请求 `{"v":1,"id":7,"cmd":"marker","args":{…}}`；成功 `{"v":1,"id":7,"ok":true,"result":{…}}`；失败 `{"v":1,"id":7,"ok":false,"error":{"code":"invalid_args","message":"…"}}`；长命令在最终回复前每 5 秒发一行事件 `{"v":1,"id":7,"event":"heartbeat","data":{}}`（无 `ok` 字段）。未知字段忽略；`v` 不是 1 回 `bad_request` 并附 `supported:[1]`。错误码是稳定字符串：`bad_request` / `unknown_command` / `invalid_args` / `not_ready` / `disabled` / `not_found` / `invalid_state` / `busy` / `timeout` / `internal` / `forbidden`。

**服务端**（`core/ipc/server.py` 的 `IpcServer` + `commands.py` 的 `CommandDispatcher`）全部跑在界面线程：`QLocalServer` 事件驱动，**没有专用线程**，读库与写文件才交给后台线程。四条硬规则（违反任何一条都复现过进程直接终止或丢消息）：① 每连接独立缓冲、按 `\n` 切分（一次 `readAll` 可能多行也可能半行）；② `disconnected` 时先读空缓冲、处理完其中的完整请求，再打“已断开”标记，之后不再访问该连接的套接字（`deleteLater` 之后访问会让 PyQt 直接终止进程，0xC0000409）；③ 所有槽函数 try/except；④ 延迟回包前检查已断开标记。资源上限（防止同用户的失控脚本拖垮界面线程）：连接 ≤ 16（超出的新连接直接断开）、每连接读缓冲 = 单行上限的 2 倍、一次读到的数据最多处理 32 条请求（其余经 `singleShot(0)` 排到下一轮，同一连接内仍按序）、每连接同时 ≤ 4 条延迟回复、全局同时 ≤ 2 个 verdict 分析（超出回 `busy`）、秒数参数 ≤ 30 天、`label` ≤ 200 字、`note` ≤ 2000 字；路径参数（`dir`、`launch.exe` / `cwd`、方案里的日志与导出目录）必须是绝对路径（`\\.\`、`\\?\` 设备路径不算）。

**门禁与客户端身份**：门禁顺序：未知命令 → `unknown_command`；设置“允许命令行与脚本控制”关闭 → `disabled`（`ping` / `activate` 除外，无窗口模式的 `quit` 也除外——那是结束它的唯一途径）；组装未完成 → `not_ready`；危险命令（`start` / `stop` / `export` / `quit`）要求客户端完整性级别不低于服务端，否则 `forbidden`（GUI 以管理员运行时，同用户的普通进程不能借它绕过 UAC）；Windows 上读不到服务端自身的完整性级别时同样拒绝，客户端的取不到按最低处理。客户端身份在连接建立时就确定，不在执行命令时按 PID 事后查（客户端发完请求就退出、PID 被别的进程复用时，事后查到的是别人的令牌）：首选连接令牌（`ImpersonateNamedPipeClient` → `OpenThreadToken` → `RevertToSelf`，与 PID 无关；管道上还没有数据时系统不允许模拟，所以在连接时、首次读到数据时、断开处理残留请求前各试一次）；取不到时退回连接时 `GetNamedPipeClientProcessId` + `OpenProcess` 当场算出完整性级别，并持有进程句柄到连接结束（持有期间 PID 不会被复用）。反方向防冒名（管道名在全局命名空间可被抢注）：pmctl 连上后用 `GetNamedPipeServerProcessId` 取服务端 PID，与 `ping` 返回的 `pid` 比对，并核对该进程属于当前用户（读不到令牌时退而核对管道对象的所有者），不符即退出码 3。

| `wait` | `task_id`、`until`（`stopped` / `rounds>=N` / `elapsed>=S`）、`timeout_s?` | `reached`；到点未满足为 `ok:true, reached:false` |
| `export` | `task_id`、`dir`、`kinds`（`csv` / `report` / `summary`）、`evidence?`（true 时产出证据包 zip） | 写出的路径（证据包为一个 zip） |
| `verdict` | `task_id` | 整体判定与每指标判定；进程组任务另有 `members`（每个成员各指标的判定）；被测进程已退出时 `target_exit` 附 `exit_code` / `exit_text`；重启续接过的任务另有 `segment`（`number` / `count` / `note`，指标行的数值是最后一段的）、`segments`（逐段判定：`number` / `start` / `end` / `verdict` / `rising_metrics` / `rising_names` / `samples`）、`mid_run_crashes`（`timestamp` / `label`）与 `conclusion`（纯文本：“中途异常退出 N 次（最近一次 0xC0000017（…））；各段判定：第 1 段 持续上涨（私有字节）；第 2 段 本段数据不足”）；基线不在统计所在的启动段时指标行的 `baseline` 为空、`baseline_note` 为“基线在第 N 段，不可比” |
| `quit` | — | 回包后走真退出路径 |

`wait`、`export`、`verdict` 与 `start`（`wait=true` 等待进程启动时）是延迟回复：回复前每 5 秒一行心跳，客户端断开即取消，不阻塞界面线程；服务端处理中途抛出任何异常时，本次请求已创建的延迟回复一律取消（不留下继续发心跳的孤儿）。拒绝监控本程序自身（`invalid_args`）；按名称启动时有多个同名进程回 `invalid_args` 并在 `error.pids` 列出；`launch` 不能与 `wait` 同给。`target_kind=tree` 以 `pid`（或 `launch` 启动的程序）为根，`target_kind=name` 用 `name` 监控全部同名进程（不要求唯一、没有也能开始，`wait=true` 同样立即开始；`pid` / `launch` 不能与它同给）；二者都拒绝本程序自身（tree 的根不能是本程序，name 不能是本程序的进程名），进程组拒绝峰值类与基本优先级指标（显式给出回 `invalid_args`，缺省指标自动剔除），并自动补 `process_count`；`pmctl start` / `run` 对应 `--tree`（配合 `--pid` / `--launch`）与 `--group-name 进程名`。`export` 的 `evidence` 参数传 true 时产出一个证据包 zip（报告图片、明细与摘要 CSV、`task.json`、`README.txt`、日志摘录，此时 `kinds` 无效；zip 放在 `dir` 里、不覆盖已有文件，重名加编号），停止原因取内存里的、没有再取库里记录的；没有报告渲染函数时回 `invalid_state`，`evidence` 不是布尔值回 `invalid_args`。`pmctl export --evidence` 与 `pmctl run --evidence <目录>`（每个任务结束后、判定之前另导一个证据包）对应它。

**判定口径**（`core/verdict.py`，不依赖 Qt；`pmctl verdict` / `run` 与证据包共用）：单指标沿用分析页的趋势判定（`rising` / `stable` / `fluctuating` / `insufficient`；统计范围里有数据但没有判定的累计量与峰值为 `not_judged`，没有数据、或明细点存在而统计范围里没有数据（重启后最后一段还没有样本，原因 `no_stats_in_range`）为 `insufficient`）。整体判定按优先级：停止条件达成**之前**被测进程退出 → `target_exited`；中途异常退出过（有 `crash` 打点之后又出现 `restart` 打点，即崩溃后被续接）→ `target_exited`（`pmctl` 退出码 30，结论写次数、最近一次退出码与各段判定）；重启续接过（分析结果带 `segments`）→ 逐启动段判定（任一指标上涨 → `rising`，没有任何指标得出平稳 / 波动结论 → 本段数据不足 `insufficient`，否则 `stable`），整体取最差的一段（`rising` > `insufficient` > `stable`）；没有分段信息时任一指标持续上涨 → `rising`；没有任何指标得出平稳或波动的结论 → `insufficient`；否则 `stable`。“停止条件达成之前”由 `exited_before_condition` 判断（时长按墙钟、暂停也算，轮数为 `kind='user'` 的打点数）：按方案的时长或轮数已满足之后被测进程才退出（如停止条件到点后关闭被测程序），测试是完整的，照常判定；没有停止条件的任务，被测进程退出一律算“之前”。

**pmctl**（根目录 `pmctl.py`，打包为同目录的 `pmctl.exe`，console 程序）：用 `core.ipc.client` 的 ctypes 命名管道客户端（`CreateFileW` / `WaitNamedPipeW` / `ReadFile` / `WriteFile` / `PeekNamedPipe`；不用 `open()`：没有读超时、管道忙时无法 `WaitNamedPipe`、错误码被压成 errno 22），读先 `PeekNamedPipe` 再 `ReadFile`；长请求里 15 秒收不到任何一行（服务端每 5 秒一次心跳）按连接断开。子命令：`ping` / `status` / `start` / `marker` / `pause` / `resume` / `stop` / `wait` / `export` / `verdict` / `quit` / `run`；`--data-dir` 决定连接哪个实例，`--json` 原样输出，`--no-launch` 禁止自动拉起。退出码（映射表在客户端的 `ERROR_EXIT_CODES`，服务端只回错误码字符串）：

| 退出码 | 含义 |
|---|---|
| 0 / 10 / 20 / 30 | `verdict` 与 `run` 的判定：平稳 / 持续上涨 / 数据不足 / 被测进程在停止条件达成前退出（普通命令成功也是 0） |
| 2 | 参数错误，含服务端回 `bad_request` / `unknown_command` / `invalid_args` |
| 3 | 连接类：找不到管道、拉起超时、EOF 或管道关闭、心跳超时、身份校验失败、拒绝访问、`disabled`、`not_ready` |
| 1 | 其余错误：`not_found` / `invalid_state` / `busy` / `timeout` / `internal` / `forbidden` |

**拉起无窗口实例**：GUI 不在时（`--no-launch` 可禁止），pmctl 先 `OpenMutexW` 查 `Global\<实例名>` 与退回用的 `Local\<实例名>`：互斥量在而管道没就绪说明正在启动，只等不拉；都不在才拉起——打包时是同目录的主程序，开发时是 `python main.py`，参数 `--background --idle-exit-s 300 --data-dir …`（`--idle-exit` 可改，0 = 不因空闲退出；标准输入输出一律 `DEVNULL`，否则 CI 捕获的管道会被拖到无窗口实例退出；`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`）。随后按 25 → 200 ms 退避等管道出现并 `ping` 到 `ready`；新拉起的实例可能在同步升级数据库、事件循环暂时不转，首次 `ping` 最多等 20 秒、每 2 秒提示一次；拉起的进程提前退出就按退出码说明原因（0 = 设置里已关闭命令行控制，2 数据目录不可用，3 数据库升级失败，4 IPC 监听失败，其余 = 启动失败），不再干等到超时。

**`pmctl run`**：一条命令跑完 开始 → 自动打点 → 停止 → 导出 → 判定，适合 CI。必须有停止条件（`--stop-after`、`--rounds`，或方案文件里的 `stop_after_seconds` / `stop_after_rounds`），否则退出码 2；等待上限 = 时长 + 60 秒、或 轮数 × 定时打点间隔 + 60 秒，二者都有取小，只有轮数而没有定时打点（靠日志或手动打点凑轮数）时无法估计、不设上限；超时先发 `stop`、再最多等 60 秒，照常导出与判定，输出与 JUnit 标“超时停止”；中途出错或 Ctrl+C 时停掉本次已开始、尚未结束的任务；多个目标（多个 `--pid` / `--name`）取最严重的判定（30 > 10 > 20 > 0）。`--junit` 写 Surefire 结构的 JUnit XML（每个指标一个用例：持续上涨 = failure，数据不足或无趋势判定 = skipped，被测进程退出 = error）。

**无窗口模式**（`--background`，`core/headless.py` 的 `HeadlessRuntime` + `bootstrap._run_headless`）：第 1~4 步同窗口模式（另调 `set_headless(True)`，未捕获异常只记日志、不弹框——模态框会阻塞界面线程，让 pmctl 的请求全部超时），随后只加载配置（不设主题与排版、不导入 `ui.main_window` / qfluentwidgets，不显示迁移进度窗口，同步迁移，`FAILED_KEPT` 返回 3）；设置里关闭了“允许命令行与脚本控制”时记日志并以 0 退出。`HeadlessRuntime` 持有 `AutoMarkerService` 并每秒 `tick()`（有窗口时这件事由监控页 Presenter 的定时器做），持有 `StageSnapshotWriter`（报告图片用同一条离屏渲染函数，由组合根注入），命令上下文带 `handle_auto_export=True`（任务结束后按方案自动导出）；自身监控每 60 秒一次；存储守卫照常启动但不连界面（只记日志，退出钩子 `quit_hooks` 在收尾协调器之前先停它）；不建任何顶层窗口、托盘、全局快捷键与界面看门狗。退出（退出码 0，经 `ShutdownCoordinator` 收尾，只执行一次，见第 6 节）：`quit` 命令、Ctrl+C / Ctrl+Break（信号处理函数只投递到事件循环，另有 200 ms 的空定时器让解释器定期拿到控制权）、空闲到时（没有任务、等待与进行中的命令请求持续满 `--idle-exit-s` 秒）、会话结束（`commitDataRequest`，DirectConnection）。

**启动被测程序**（`core/process_launcher.py`）：监控页“启动被测程序”折叠区（`LaunchOptions`）与命令行 `start --launch` / `run --launch` 共用 `ProcessLauncher`（组合根创建在 `services.launcher`，命令处理器共用同一份）。`launch(spec)`：`subprocess.Popen` 启动（不捕获输出，继承本程序的桌面与权限，工作目录缺省为程序所在目录），观察 0.3 秒判断是否立即退出，再用 psutil 取创建时间；文件不存在、拒绝访问、需要管理员权限、不是有效 Windows 程序、启动后立即退出、读不到进程信息都返回中文 `error` 而不抛异常——失败就近提示（监控页在启动区下方、命令行回 `invalid_state`）、不建任务；成功则用拿到的 PID 与创建时间建任务，PID 复用检测照常。“停止时关闭被测程序”：只在任务因用户停止（含方案的停止条件）结束时触发，被测进程自己退出或 PID 复用时不动；`terminate(pid, create_time)` 先比对创建时间（不一致说明 PID 已被别的进程复用，一概不动），再给它的顶层窗口发 `WM_CLOSE`、等 5 秒，仍在运行才 `TerminateProcess`；它会阻塞数秒，所以放在 `TerminateWorker`（`close_in_background`，登记名“关闭被测程序”，退出路径等待上限 8 秒，结果只记日志）里执行。模块顶层只导入标准库，因为 pmctl 复用其 `split_args`。

**自动化方案**（`core/automation/`）：`AutomationPlan` 随任务存进 `tasks.plan_json`（带 `schema_version`；读入时不认识的字段忽略并记日志，版本更高抛 `PlanVersionError`，字段名发布后不改）。`AutoMarkerService` 按方案定时打点、监听日志文件匹配打点、判断停止条件（时长按墙钟含暂停，轮数为用户打点数）、到期请求阶段快照、任务结束后请求自动导出；每个采集周期的 `data_updated` 与外部约每秒一次的 `tick()`（有窗口：监控页 Presenter 的定时器；无窗口：`HeadlessRuntime`）双路径驱动，长周期与暂停时也准时，同一时刻被两条路径各调用一次也不会重复打点；暂停期间不打点不计时，恢复后重新计时；故障按任务隔离。`LogWatcher` 每次 `poll()` 只读上次位置之后新写入的完整行，不开线程、不长期持有文件句柄（Windows 上持有句柄会让被测程序的日志轮转失败）：开始监听时文件已存在则从末尾读起，文件变小或身份变了视为轮转、从头读，单次最多读 1 MiB；编码必须是文本编码（构造时拒绝 base64 之类，也不支持 UTF-16 / UTF-32）；日志在网络共享上时 `os.stat` 可能卡住界面线程，某次 `stat` 超过 2 秒即记 WARNING 并降级为每 30 秒才读一次。

**阶段快照与存储预估**：方案设了“每 N 小时写阶段快照”（`stage_snapshot_hours` + `stage_snapshot_dir`）时，`AutoMarkerService` 到期发 `stage_snapshot_due(task_id, 目录, 序号)`（暂停期间不累计，恢复后满 N 小时才发下一次），`StageSnapshotWriter`（监控页 Presenter 与 `HeadlessRuntime` 各自持有并连接该信号）写**报告图片 + 摘要 CSV**——范围为“全部”，不写明细 CSV（它随时长线性增长，十几个小时就是几十上百 MB）。一次写入分三段：工作线程（`StageAnalysisWorker`）建目录、读任务、按“全部”范围逐指标查分析快照 → 界面线程用注入的 renderer 离屏渲染报告图片（图表是控件只能在界面线程画，core 不反向依赖 ui，故由组装方注入）→ `ReportWorker` 写文件（先 `.tmp`、全部成功再原子替换）；整段期间经 `begin_export` / `end_export` 登记，与清理数据库互斥。文件名 `<进程名>_<task_id 前 8 位>_阶段<序号两位>_<yyyyMMdd-HHmm>`。写快照是附带功能：失败绝不影响采集，同一任务只提示一次（之后只记日志，无窗口模式只记日志），同一任务上一次还没写完时跳过本次。存储预估（`core/storage_estimate.py`，纯函数）：新建任务表单随指标数与采集间隔显示“每小时约 N 行 · 12 小时约 M MB”（悬停给 1 / 12 / 24 小时的估算依据），按每个样本约 18 字节、每指标每分钟一行汇总约 120 字节估算，是量级提示，不含打点与 WAL 的临时增长。

### 2.8 进程树 / 同名多实例（进程组任务）

监控目标有三种（`tasks.target_kind`，参数在 `tasks.target_spec` 的 JSON 里）：`pid` 单个进程（默认，行为与旧版逐字相同）、`tree` 根进程及其全部后代、`name` 全部同名进程（不区分大小写）。`tree` 与 `name` 统称进程组任务，**占 1 个任务配额**；`MonitorWorker` / `MonitorManager.create_task` 以 `group_spec`（`core.process_tree.GroupSpec`）/ `target_kind` 区分，`name` 任务的任务行 `pid` 记 0、`process_name` 为要监控的进程名。

**成员解析**（每周期，`ProcessTreeSource.observe`，接口可注入，生产实现 `SnapshotTreeSource`）：从 SnapshotHub 的全系统快照取 `ppid` + `create_time`（一次系统调用服务全部任务），快照不可用或取失败时整周期回退 psutil。后代 = 从根（以及仍存活的已确认成员）沿“父 PID 指向它”向下找，且**子进程创建时间不早于父进程**（Windows 不会在父进程退出后给孤儿换父，记录的父 PID 可能已被全新进程占用）；已确认过的成员（pid + 创建时间都对得上）即使中间的父进程退出了仍算成员。本程序自身永不进成员。

**序列命名与成员**：合计序列沿用原指标键（现有分析、报告、导出看到的就是合计）；成员序列是 `指标@成员键`（`utils.metrics.member_series_key` / `split_member_key`，`@` 的拼接与拆分全项目只走这两个函数；`series.metric` 本是自由文本，仓储、分析、汇总对 `@` 键原样适用）。成员 = 同名实例的合并（成员键为进程名小写），所以子进程每轮重建、PID 全换而名字不变时，成员曲线仍然连续。成员名最多 `MAX_GROUP_MEMBERS`（20）种，先到先得、终身占位；之后新出现的名字不建成员序列、其进程仍计入合计，只记一次日志并置 `members_truncated`。新增组指标 `process_count`（“进程总数”，合计 = 当前实例数，另有 `process_count@成员`；成员本周期没有实例为 0）。

**聚合规则**（`core/group_aggregator.py`，由 `MetricKind` 派生，不逐指标手写）：

| 指标种类 | 组内聚合 |
|---|---|
| `BYTES_KB` / `COUNT` / `PERCENT` | 各实例求和 |
| `SECONDS` / `CUMULATIVE_COUNT` / `CUMULATIVE_BYTES` | **虚拟累计**：每个实例（pid + 创建时间）自首次出现以来的正增量之和；首次出现只记起点、不计入；读数回绕只重设起点；实例消失已计入的不扣回——合计与成员序列都不会出现负值，分析页照常画每秒速率 |
| `cpu_percent` | 每个实例按自己的 CPU 时间与单调时钟差分，再求和；新出现的实例首个周期没有差分起点、不计入 |
| `PEAK` 与基本优先级 | 对组不适用：不可选，若仍被带入则记为不可用（`NOT_SUPPORTED`） |

**生命周期**：`tree` 根进程退出（含 PID 被复用）任务以 `PROCESS_EXITED` 结束，子进程退出不影响；启动时根不存在为 `PROCESS_NOT_FOUND`；`name` 永远“在运行”，成员归零的周期只写 `process_count=0`（与各成员的 0），其他指标留空洞（不写 0），任务不结束。含 `tree` 根的第一次观察锁定根的创建时间，之后每周期强制比对。

**`task_members` 留痕**：实例首次出现时写一行（`first_ms = last_ms`），实例消失或任务结束时把 `last_ms` 更新为最后一次见到的时刻；`(pid, create_time)` 唯一，PID 被复用是另一行。留痕缓冲在 `MonitorWorker` 里随样本一起在 `_flush_buffer` 批量写（先样本、后留痕，留痕单独一个事务）；留痕只是附带信息，写失败保留缓冲重试、日志节流，不影响采集；缓冲超限丢弃最旧的。进程崩溃时 `last_ms` 停在最后一次 flush 时见到的值。

**判定与导出**：合计与进程总数照常判定；每个成员的每个序列各自判定（`core.verdict.member_verdicts` / `member_overall`，无 Qt 依赖），整体判定把合计与全部成员一起看——合计或任一成员持续上涨即 `rising`（总量持平而某成员在涨同样是泄漏线索）。`TaskAnalysis.member_snapshots` 由 `core.history_query.load_member_snapshots` 加载（`TaskAnalysisWorker` 已接入，所以命令行 `verdict`、导出与证据包都带成员结论；`task.json` 的 `verdict.members`、README 的成员段与 `task` 里的 `target_kind` / `target_spec` 仅进程组任务才有）。明细 CSV 只导出合计，末尾追加“成员汇总”段（成员、实例数、首次出现、最后出现、各指标末值），报告图片不变。

**给界面的接口**：`TaskInfo.target_kind` / `members_truncated`；`MonitorManager.group_members(task_id)`（成员快照元组：成员键、显示名、当前实例数、最近一个周期的各指标合计值，含本周期没有实例的）；信号 `members_changed(task_id)`（已建成员列表或“有实例的成员集合”变化才发，首个周期发一次；实例数涨落体现在进程总数的采集值里，不发）；`data_updated` 只带合计序列；`utils.metrics.group_selectable_metrics` / `filter_group_metrics` 供选择指标时用；`Database.members` / `list_members(task_id)` 与 `PointRepo.fetch` 传 `member_series_key(...)` 取成员曲线。

**界面落点（2.0 阶段 3 C-1b）**：新建任务表单的“监控对象”分段控件与组指标选择；任务卡片的“成员 N 种 · 共 M 个进程”行与悬停列表（`members_changed` 驱动，`MonitorPresenter` 只在任务仍在运行时才把它算作“有运行中的进程组”）；分析页的“成员”下拉、成员视图（整页切到 `指标@成员键` 序列）、摘要表下方的“成员结论”折叠区与横幅里点名上涨成员（`member_overall`）。成员数据由 `core.workers.member_snapshots_worker.MemberSnapshotsWorker` 在一个后台线程里按序加载，`core.history_query.load_member_snapshots(..., is_cancelled=None, **request_options)` 为其取数（请求选项与合计查询一致，范围锚点是任务级的 `last_sample_at`）。合计的“上限占比”不适用于进程组（写“—”）；对比、报告、导出一律用合计。详见 2.5 节。

**短命线程的统一写法**（`core/workers/base.py`）：子类只实现 `execute(token)`，不覆盖 `run()`；返回值经 `result` 发出，异常一律捕获、记日志后经 `failed` 发出（`TaskError` 表示预期内失败，消息直接给用户、不记堆栈），`progress` 报进度；被取消（`CancelToken`）后既不发 `result` 也不发 `failed`。结果/失败信号是 `run()` 的最后一个动作。“最新请求获胜”用 `LatestRequestGate`：发起时 `next_seq()` 取号，结果回来 `is_current(seq)` 为真才应用。

**线程登记表**（`core/shutdown.py` 的 `ThreadRegistry`，经 `services.threads` 注入页面）：页面启动短命线程前 `register(thread, name=, cancel=, timeout_ms=)` 一次；线程 `finished` 时登记表自动注销并 `deleteLater`，页面不再自行连 `deleteLater`，也不在业务信号的槽里释放线程对象。退出时 `shutdown_all` 先对仍在运行的线程逐个调用取消回调，再按登记顺序逐个带超时等待，超时只记日志。现有登记：检查更新（1000ms，无取消）、更新下载（2000ms，可取消）、导出报告（2000ms，可取消）、清理数据库（5000ms，不可取消）、重建汇总（5000ms，不可取消）、历史数据查询（3000ms）、读取进程列表（3000ms，取消即结果作废）、命令行分析 / 命令行导出（2000ms，可取消）、阶段快照（3000ms，可取消）、自动导出（2000ms，可取消）、关闭被测程序（8000ms，不可取消）、导出诊断包（3000ms，不可取消）、WAL 兜底 checkpoint（3000ms，不可取消）、数据库完整性检查（3000ms，可取消，中途中断）；证据包导出与“导出报告”共用登记名（2000ms，可取消）。

### 3.2 采集线程的调度与收尾

- **调度**：按 `time.monotonic()` 截止时间推进，每周期 `deadline += interval`，不随采集耗时累积漂移；等待统一用 `threading.Event.wait(剩余时间)`，`stop` / `pause` / `resume` 置标志后 set 事件即可立即唤醒，无需轮询。落后超过一个周期（系统休眠唤醒、严重卡顿）则重置截止时间，不补采。暂停时无超时等待，恢复后立即采一次。
- **时钟注入**：`MonitorWorker(..., *, clock=None)` 收一个时钟对象（接口见 `core/monitor_task.py` 的 `SystemClock`：`monotonic()` / `now()` / `wait(event, timeout)`，缺省为无状态的共用实例 `SYSTEM_CLOCK`）。主循环的截止时间与剩余等待、等待本身、落库时间戳（任务开始、数据点、收尾结束时间）以及暂停/恢复系统打点的缺省时刻都经时钟取得，代码中不再直接调用 `time.monotonic` / `datetime.now` / `Event.wait`。测试与加速浸泡注入假时钟即可不真实睡眠地驱动成千上万个周期；状态机与 `_teardown` 恰好执行一次的不变式不因时钟而变。
- **进程组任务**：采集器换成 `GroupCollector`，每周期一次 `observe`（成员解析 + 逐实例读数，无额外线程）；本周期的实例出现 / 消失记进留痕缓冲，成员集合变化时发 `members_changed`（见 2.8 节）。收尾先把仍存活实例的 `last_ms` 补成最后一个周期，再 flush 样本与留痕。
- **落库**：采集结果进缓冲后立即 flush（`SAVE_BATCH_SIZE` 固化为 1）。flush 失败时缓冲保留待下一周期重试，缓冲上限 1000 条（超出丢弃最旧），连续失败达到阈值经 `error_occurred` 通知界面一次。
- **停止**：`stop()` 只改状态并 set 事件，近乎立即返回、不阻塞界面。收尾（最后一次 flush → 写 `stopped` 状态 → 置 `STOPPED` → 发出 `task_stopped`）全部在线程自己的 `run()` 的 `finally` 中完成，因此界面收到 `task_stopped` 时数据与状态一定已落库。
- **线程对象释放**：manager 把每个任务线程的 `QThread.finished` 连到自己的槽，线程真正结束后由 manager 自行从字典移除、`deleteLater` 并发出 `task_removed`；界面不必、也不应在 `task_stopped` 的槽里释放线程。`remove_task` 不再 `wait()`：线程仍在运行（含收尾中）时只请求停止，移除交给 `finished`；线程没在运行时立即移除。`stop_all_tasks` 同样只给全部任务置停止标志、不等待，等待由退出协调器带超时完成（见第 6 节）。短命线程的释放见 3.1 节的线程登记表。
- **PID 复用**：采集器依赖 `psutil.Process.is_running()` 对进程创建时间的比对，PID 被新进程占用视为进程已退出，任务以 `StopReason.PROCESS_EXITED` 结束。从进程列表选进程时，`get_all_processes()` 返回的 `create_time` 经 `create_task(..., create_time=...)` 传给任务，线程启动时先与该 PID 当前进程比对，不一致直接以 `StopReason.PID_REUSED` 结束并报错、不写数据点（界面文案与进程退出相同，均为“进程已终止”）；手动输入 PID（无创建时间）或读不到创建时间时跳过比对。

### 3.3 任务状态

| 层 | 状态 | 说明 |
|----|------|------|
| 库（`tasks.status`） | `running` / `stopped` | 启动时写 `running`，收尾写 `stopped`；崩溃遗留的 `running` 由启动校正处理 |
| 线程（`MonitorWorker`） | 显式状态 `WorkerState`：`WAITING` / `RUNNING` / `PAUSED` / `WAITING_RESTART` / `STOPPING` / `STOPPED` | 读写一律经状态锁；`is_running()` / `is_paused()` 只由状态派生，不与 `QThread.isRunning()` 混用 |
| 卡片（`TaskCard`） | 运行中 / 已暂停 / 正在停止 / 已结束 / 异常结束 | 状态词见 2.6 节；已结束的卡片不占配额；“同配置再测”新建任务 |

`WorkerState` 迁移表（其余组合一律拒绝且保持原状态）：

| 起始 | 触发 | 结果 |
|------|------|------|
| `WAITING` | `start()` | `RUNNING` |
| `WAITING` | `stop()` | `STOPPED`（从未启动，没有线程需要收尾） |
| `RUNNING` | `pause()` | `PAUSED` |
| `PAUSED` | `resume()` | `RUNNING` |
| `RUNNING` / `PAUSED` | 被测进程退出，续接策略开启且未达次数上限（仅 pid / tree 任务） | `WAITING_RESTART` |
| `WAITING_RESTART` | 每秒查找一次，找到“旧进程退出之后才启动”的同名同路径新进程 | `RUNNING`（同一 `task_id`、新 PID）；进入等待前处于暂停的回到 `PAUSED`，不悄悄恢复采集 |
| `WAITING_RESTART` | `stop()`（用户停止、程序退出） | `STOPPING`（按最后一次退出的原因收尾） |
| `WAITING_RESTART` | `pause()` | 拒绝（没有数据可暂停） |
| `RUNNING` / `PAUSED` / `WAITING_RESTART` | `stop()` 或主循环自行结束（进程退出且不续接、PID 复用等） | `STOPPING` |
| `STOPPING` | 收尾落库完成（发出 `task_stopped` 之前） | `STOPPED`（终态，对象不可复用） |

两个口径：`ACTIVE_STATES = {RUNNING, PAUSED, WAITING_RESTART}`（已请求运行且未请求停止，即 `is_running()`；等待重启的任务仍占配额、仍算运行中）；`LIVE_STATES = {RUNNING, PAUSED, WAITING_RESTART, STOPPING}`（线程仍可能写库）。`create_task` 按 manager 中保存的任务数限制上限，线程结束后 manager 自行移除，已结束的卡片因此不占配额。界面上的“n/5 运行中”、退出确认与数据库维护互斥都以 `running_task_count`（按 `LIVE_STATES` 计数）为口径。

**退出取证与重启续接**（`core/exit_forensics.py`、`core/restart_finder.py`、`MonitorWorker`）：确认被测进程存在后立刻经可注入的 `ExitCodeProbe` 持有一个 `SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION` 句柄（Win32 实现 `OpenProcess`，零等待 `WaitForSingleObject` 确认进程已结束才读 `GetExitCodeProcess`，退出码恰为 259 的已结束进程不会与“仍在运行”混淆）；拿不到句柄（目标提权等）降级为“未知退出码”，整个任务只记一次日志；按名监控不取证。句柄在任务结束与线程退出（`run()` 的 finally 兜底）时关闭。采集发现进程没了：读退出码（句柄还没显示“已结束”时每 0.1 秒重读，最多 5 次），**异常退出的分类口径**（`is_abnormal_exit`，退出码按无符号 32 位）：崩溃 = 0xC 开头的 NTSTATUS 错误码（除 0xC000013A）、预定义的警告类异常 0x80000001～0x80000004（保护页、未对齐、断点、单步）、0xE 开头的自定义异常（C++ 0xE06D7363、.NET 0xE0434352）；经纯函数映射为中文（0xC0000005 访问冲突、0xC0000409 栈缓冲区溢出、0xC00000FD 栈溢出、0xC0000374 堆损坏等，表外为“未知异常”）并判为 `StopReason.CRASHED`、写 `kind='crash'` 打点“异常退出 0xC0000005（访问冲突）”。不算崩溃：0、1（taskkill /f）、2 等程序自己返回的小整数；0xC000013A（`STATUS_CONTROL_C_EXIT`，用户按 Ctrl+C）——用户主动终止，仍是 `PROCESS_EXITED`，退出码照常记录并显示“0xC000013A（被 Ctrl+C 终止）”；其余 0x8 开头的值（0x80004005 E_FAIL、0x80070005 E_ACCESSDENIED 等 HRESULT，程序用 HRESULT 当返回值）显示为十六进制、不判崩溃；0x4（信息）、0xF（如 -1）同样视为程序自己的返回值。

**退出的及时发现与 PID 复用核对**：每次采样前先对握着的句柄做零等待 `WaitForSingleObject`，已显示结束就按退出处理（`ExitCodeProbe.has_exited`），不管采集器还读得到什么；采集器的快照路径把线程数为 0 的条目（已结束、仅被句柄握着的“僵尸”）也按已退出处理，进程树的根与成员同理——只针对被监控的目标，`process_catalog` 的进程列表不变。实测（Windows 11 26200，真 `SnapshotHub`）握着句柄的已结束进程**不会**留在全系统快照里（条目随进程结束消失），采集器经 `_recheck_missing` 本来就发现得了退出，上述三道防线是兜底，`tests/test_exit_visibility.py` 的真实进程用例钉住“结束后 2 个周期内进入取证 / 等待重启”。取到句柄后核对 `GetProcessTimes` 的创建时间与预期一致（不一致 = 确认存在到取句柄之间 PID 被复用，任务以 `PID_REUSED` 结束）；续接时候选进程同样核对。手动输入 PID 的任务事先没有创建时间：首次启动时把采集器读到的创建时间回填到任务行与内存，之后的复用检查、续采与重启查找都以它为准。退出码写 `tasks.exit_code`（无符号 32 位），停止原因写 `tasks.meta_json` 的 `stop` 键（`{"reason": …, "text": …}`，与被测目标元数据同住一个 JSON，`TaskRepo.save_meta` 保留它，**不新增列**）；明细 CSV 元数据行“退出: 异常退出 0xC0000005（访问冲突）”、证据包 `task.json` 与 README 同样写明。

**重启查找的条件**（`ProcessRestartFinder.is_new_instance`，宁可多等也不能认错进程，否则两个进程的数据串进同一个任务）：候选的创建时间必须读得到；不得早于旧进程的退出时刻减 2 秒（退出时刻取句柄的 `GetProcessTimes` ExitTime，取不到用最后一次成功采样的时刻），所以早已在运行的同名实例、Chromium 式多进程程序里主进程之后创建的同名子进程都不会被接上；父进程是旧进程（进程树任务还包括旧树的任何成员，在封口前记下）的候选不接——退出前几秒才派生的子进程落在容差内也不是“重启”；路径不同的同名进程不算（读不到路径时不排除）；同名多个取最新启动的。

续接策略（`AutomationPlan.resume_on_restart` / `restart_limit`，默认次数 3、范围 1～20，`save_plan` 同步进 `tasks.resume_on_restart` / `restart_limit`，采集线程在每次退出时强制重读、平时最多每 30 秒读一次，所以方案在任务启动后才落库也生效；构造参数 / `MonitorManager.set_restart_policy` 可直接覆盖）：
```
RUNNING ──被测进程退出──▶ 读退出码、判 CRASHED / PROCESS_EXITED（崩溃写 crash 打点）
   │                       │
   │          策略关闭 / 按名监控 / 已续接 restart_limit 次 ──▶ STOPPING ──▶ STOPPED（task_stopped 带该原因）
   │                       │
   │                 策略开启且未达上限
   │                       ▼
   │              WAITING_RESTART（保持线程；不写假数据点；不计入计划周期）
   │                每秒按“进程名 + 可执行文件路径”找创建时间更晚的新进程（同名多个取最新并记日志）
   │                       │ 找到：同一 task_id，换 PID / 创建时间 / 采集器 / 退出码句柄，
   │                       │       写 restart 打点“第 N 次启动 PID …”，restart_count += 1，清除上个进程的退出码
   ◀───────────────────────┘ stop()：不再查找，按最后一次退出的原因收尾（崩溃就是 CRASHED）
```
等待过程中任何一步出错（查找、封口旧进程树、接上新进程）都记日志并通知界面，按最后一次退出的原因结束任务；主循环顶部另有兜底，回到循环时若状态仍是 `WAITING_RESTART` 同样按退出原因结束，线程不会空转。
等待期间任务行仍是 `running`，卡片读 `TaskInfo.waiting_restart` / `restart_count` / `restart_limit` 显示“等待重启（第 n/m 次）”；管理器发 `task_waiting_restart(task_id, 是否在等待)` 与 `task_restarted(task_id, 已续接次数)`，退出码在 `TaskInfo.exit_code`（任务结束后卡片用 `task_stopped(CRASHED)` 显示“异常退出：访问冲突 0xC0000005”，退出码文本由 `format_exit_code` 给出）。快照的统计与区间表只用一个启动段的数据：`history_query.segment_of` 取最后一个 `restart` 打点时间为段起点（自定义范围取终点所在的段），统计起点、区间表起点与峰值上涨的起点都不早于它，结论 / 依据行附“仅统计第 N 次启动后的数据”（`segment_note`，命令行 `verdict`、证据包共用）；`crash` / `recover` 打点不切段。**整体判定逐段做**：`TaskAnalysis.segments`（`SegmentAnalysis`：段号、起止、判定、上涨的序列、样本数，`load_segments` 取，更早的各段按自定义范围各查一遍，最后一段复用整体查询）；规则见 2.7 节“判定口径”，`segments_summary` 给纯文本摘要。基线在更早的启动段时它属于另一个进程：`HistorySnapshot.baseline_comparable` 为假、`baseline_note` 为“基线在第 N 段，不可比”，命令行、证据包不输出“较基线”（`baseline` 为空，起点改用本段首值）。**强制断点**：`restart` / `recover` 打点处图表不连线、不算累计量速率，哪怕前后两点间隔没超过空洞阈值——`AnalyticsRepo.break_pairs` 现算打点前后各一个真实样本，`merge_gaps` 并入 `HistorySnapshot.gaps`；只在分析层并入，`rollup_1m` / `series_gaps` 仍恒等于“按样本重算”；min/max 带的分桶（`AnalyticsRepo.buckets` 的 `break_instants`）同样在这些时刻切断，不让一个桶跨过去，原始样本路径与分钟汇总路径的结果一致，有强制断点落在行内的汇总行改读原始样本。进入等待前处于暂停（含存储守卫因空间不足暂停）的任务，续接成功后仍是暂停（不发恢复信号，守卫的“因空间不足暂停”集合保持不变，之后用户或守卫恢复时照常生效）；`waiting_restart_changed(False)` 发出时 `TaskInfo.is_paused` 仍为真，监控页卡片据此（`set_waiting_restart(..., paused=)`）同时刷新暂停按钮与状态胶囊。进程树任务以新根续接（`target_spec` 仍记首次启动的根，运行与续采以任务行里的当前根为准）。

**磁盘写满**：写库遇到 `StorageFullError` 时采集线程保留缓冲（上限约一小时的数据，`min(50 万, max(1000, 每周期点数 × ⌈3600 / 周期⌉))` 行，超出丢最旧的并记日志）、经队列信号向管理器报告一次（`storage_full` → `storage_full_detected`），存储守卫据此 `report_storage_full()` 暂停全部运行中任务并记入“因空间不足暂停”，没有守卫接线时管理器自己暂停该任务；用户恢复后先补写保留的缓冲再采新数据，补写仍失败则再次报告。`Database.last_save_failure`（按线程隔离）告诉线程上次写库失败是不是磁盘已满。

- `data_updated` 的载荷是每次新建的 `dict`；采集失败的指标不在其中。
- `task_paused(task_id)` / `task_resumed(task_id)`：暂停/恢复成功后发出（随后才是 `markers_changed`），无论命令来自监控页、托盘还是命令行，界面都据此同步卡片状态。
- `target_info_ready(task_id, TargetInfo)`：被测目标元数据探测完成后发出，任务卡片据此在悬停提示里补上“被测程序”行；`MonitorManager.target_info(task_id)` 可同步取（任务移出管理器后为 `None`，请读库 `tasks.meta_json`）。探针线程内部经私有信号 `_target_probed` 把结果交回管理器所在线程。
- 命令行控制不另开信号链：`CommandDispatcher` 经 `CommandContext`（manager、db、`AutoMarkerService`、线程登记表、时钟、退出回调、报告渲染函数、launcher）调用 manager 的公开命令，因此与界面操作共用同一套信号（命令行打点后 `markers_changed` 照常刷新卡片）。`AutoMarkerService.stage_snapshot_due(task_id, 目录, 序号)` 由监控页 Presenter 或 `HeadlessRuntime` 连到 `StageSnapshotWriter.write`。
- 停止原因与指标不可用原因在信号中传 `core/contracts.py` 的枚举（`task_stopped` 为 `pyqtSignal(str, object)`），中文文案只在 `ui/formatting.py` 的 `stop_reason_text` / `unavailable_reason_text` 中定义；`error_occurred` 仍传中文消息字符串。
- 界面不持有、不调用任务线程（`MonitorWorker`）对象：任务信息与状态经 `MonitorManager` 的只读快照与查询获取（`get_task_info` / `list_task_infos` 返回 `TaskInfo`，另有 `is_task_active`、`is_task_paused`、`has_running_task_for_pid`、`running_task_count`）。`get_task` / `get_all_tasks` 仅供 core 内部与测试使用。
- `MonitorManager` 是普通 QObject（不是单例），由组合根以唯一的 `Database` 实例构造后注入 `MainWindow`，再由主窗口向下分发；测试中每个用例各自构造。
- 单实例的“激活”请求（从实例发 `{"cmd":"activate"}`，或旧版裸 `activate`）由 `IpcServer` 收到后经 `CommandDispatcher` 发出 `activation_requested`，转发为 `SingleInstanceGuard.activation_requested`，由入口连接到激活主窗口。

## 4. 核心数据流

### 4.1 采集 → 落库 → 展示

```
用户选进程/指标/周期/备注 → NewTaskForm 发出 TaskRequest → MonitorPresenter 校验（不默认选进程、同 PID 重复需确认、配额只计运行中任务）
  → MonitorManager.create_task → 注入同一 Database 的 MonitorWorker → start
  → run(): 登记任务行 → 进程存在性检查 → 创建时间比对（有 create_time 时）→ (含 CPU 指标则预热，首个样本推迟一个周期) → 定时循环
        collect_metrics(指标列表)      一个周期共用 oneshot 缓存与同一时间戳
          · 成功的指标 → DataPoint 入缓冲 → flush 到 samples（同事务更新 sample_count / last_sample_at、分钟汇总与空洞）
          · 失败的指标 → 不入返回字典，记入 collector.last_unavailable（留空，不记 0）
        emit data_updated → TaskCard 刷新数值、较开始变化量、趋势图
        新出现的不可用指标 → emit metrics_unavailable（每指标每任务一次）→ 卡片“不可用” + 提示原因
  → 进程消失或用户停止 → 收尾 → task_stopped → 卡片转入“已结束”分组（查看分析 / 同配置再测 / 关闭；可清除全部）
```

**被测目标元数据**（`core/target_info.py`）：`MonitorManager.start_task` 在任务线程启动后另起一个守护线程调 `probe(pid, clock=, dpi_scale=)`（显示缩放只有界面层读得到：主窗口把 `services.dpi_scale` 交给 manager，启动时在界面线程读一次再交给探针线程）。记录：被测 exe 的路径、版本资源（`version.dll` 的 `GetFileVersionInfoW` / `VerQueryValueW`）、命令行、进程创建时间、被测进程是否提权（`TokenElevation`），以及工具版本、本程序是否管理员、OS、CPU、逻辑核数、内存、显示缩放；任一字段失败只留 `None`、绝不抛出（被测进程可能已退出，可能以更高权限运行读不到路径，exe 可能没有版本资源，这些都不阻止任务开始）。结果是不可变的 `TargetInfo`，序列化为带 `schema_version` 的 JSON，经 `TaskRepo.save_meta` 存进 `tasks.meta_json`。探测完回到管理器所在线程：缓存（`target_info()`）、写库、发 `target_info_ready`。任务行由采集线程启动时才写入，探测可能先完成，此时 `save_meta` 返回 False，元数据挂在 `_pending_meta` 里，在这些时机补存：首个 `data_updated`（任务行此时必已落库）、`task_stopped`（一个周期都没采到就结束）、退出路径的 `join_all`（等探针线程并当场交付，随后即关库，不能等事件循环）、任务移出管理器；仍写不进去说明任务行从未落库，放弃并记 WARNING；写库失败不重试（重试只会每个周期刷同一条错误日志）。用处：明细 CSV 的元数据行（完整，含命令行）、报告图片元信息网格（只取“被测程序”“环境”两项：命令行可能很长、含敏感参数）、任务卡片悬停提示、证据包 `task.json` 的 `target`。

**进程组任务**（tree / name，见 2.8 节）走同一条链路，差别在采集这一步：`create_task(..., target_kind=)` 建 `GroupSpec`，`MonitorWorker` 用 `GroupCollector`；`collect_metrics` 一次返回 `{序列键: 值}`（合计序列 + `指标@成员` 序列 + 进程总数），全部作为同一周期的数据点落库；`data_updated` 只带合计；`_after_group_cycle` 取走成员快照、把实例出现 / 消失写进留痕缓冲、成员集合变化时发 `members_changed`；`flush` 先写样本再写 `task_members`。tree 的根退出返回 None → `PROCESS_EXITED`；name 的零成员周期只写进程总数。

采集失败语义是全链路契约：采集器、落库、卡片、分析图表、导出都把“缺失”当作空，绝不当作 0。权限不足时，非管理员运行对更高权限进程只有 `memory_uss` 采不到；其他会话进程（如 session 0 服务）的 GDI/USER 对象数抛“不支持”，与权限不足区分。

### 4.2 展示（分析页）

- 任务列表：`sample_count > 0` 的任务（单条 SQL）；下拉文本含时长、备注与“运行中”。默认范围“全部”；范围锚定该任务最后一个数据点的时间而非当前时刻；“自基线”从基线时刻起（无基线等同“全部”）；“自定义”由概览条刷选给出起止。
- 一次加载对任务的每个指标各跑一次 `run_history_query(analysis=True)`：锚点、打点、基线（`value_near` 取中位数；“基线之后已有几个样本”用 `analytics.point_count(since=)` 按范围计数）、明细最近 N 条 `points.fetch(PointQuery)`、图表线 `analytics.legacy_buckets`、统计起点之后的聚合 `analytics.aggregates` → 判定与增速（`core/analysis/trend`）、空洞 `analytics.gaps`、min/max 带 `analytics.buckets`（按时间等宽、不跨空洞，带 min/max/avg）、逐轮增量与打点区间（`core/analysis/intervals`）、累计量速率与峰值抬升（`core/analysis/series`）。起点均为 datetime；打点 / 基线时刻作查询边界前先经 `normalize_ms` 取整（见 7.2 节）。
- **两条查询路径**（`AnalyticsRepo`，结果相同：计数与时间戳完全一致，浮点只差求和顺序带来的舍入，`tests/test_analytics_rollup_path.py` 守护）：原始路径直接扫 `samples`；汇总路径读分钟汇总 `rollup_1m` 与写时空洞 `series_gaps`，范围两端不完整的汇总行回到 `samples` 取原始样本。范围内样本数按汇总行 `SUM(count)` 估算（一次主键范围查询），超过 `RAW_PATH_MAX_ROWS`（20 万）走汇总路径。依赖空洞口径的查询（`gaps` / `buckets`）只有在口径与写入时相同（`gap_factor` 为默认 2.5、`interval_seconds` 等于任务的采集周期）时才用表：此时 `gaps` 不论范围大小都直接读 `series_gaps`（`metric=None` 时取各序列覆盖区间合并后的间隙，即不同时间戳上的空洞）；`buckets` 在样本多、且算出的桶宽 ≥ 1 分钟时合并汇总行（跨桶边界的汇总行回到原始样本）。`aggregates` 把各桶相对桶起点的各阶和平移到同一原点再合并，两端不完整桶用原始样本补。构造参数 `AnalyticsRepo(path='raw' | 'rollup')` 可强制路径（测试比对用；强制汇总时口径不符仍走原始）。
- **图表点集**（`legacy_buckets`，2.0 行为变化）：范围内点数不超过 `2 × max_points`（`CHART_MAX_BUCKETS` = 2000）时原样返回全部点；否则把 [首点, 末点] 按**时间**等分为不超过 `max_points` 个桶（时长够长时桶宽取整分钟并对齐自然分钟，可直接用汇总行的 `min_ms` / `max_ms`），每桶取最小值点与最大值点（并列取较早的），都是真实样本，最多 `2 × max_points` 个点。1.x 是按行号等分、每桶取最小/最大行。
- **读事务**：`AnalyticsRepo` 的每次查询在一个显式 `BEGIN` 的读事务里完成。汇总路径要先后读 `rollup_1m`、`series_gaps` 与两端原始样本，WAL 下各语句默认各自取快照，采集线程同时追加样本会让前后几条语句看到不同的数据（桶数按旧样本算、端点又读到新样本）；同一读事务内所有语句看到同一快照。只读连接（`query_only`）同样允许 `BEGIN`。
- **整包取回**（`data/repos/_samples.fetch_packed`，用于明细最近 N 条与图表点集）：结果在 SQLite 里用 `group_concat` 拼成一个字符串一次取回、在 Python 里拆开。原因是 sqlite3 模块每取一行都要释放再获取一次 GIL，分析页 5 个指标的查询线程并行时逐行交接 GIL（护航效应）比依次执行还慢数倍。浮点经 `printf('%!.17g')` 转文本可逐位还原（本进程首次使用时自检一次）；出现类型不符的值、超出安全量级、拼出的字符串超过 SQLite 长度上限（`DataError`）或自检不通过时整体退回逐行读取，两条路径结果逐位相同，唯一的规范化是 `-0.0` 一律为 `0.0`。
- 坐标轴：`chart_axes` 中的纵轴按显示单位取整刻度，计数类指标用整数刻度；`sparkline.compute_y_range` 对平直曲线设纵轴最小跨度（水位量绝对下限、速率按参考值 5%）。
- 读库失败（`StorageError`）时用户操作的加载显示“读取数据失败”空状态并弹错误提示，与“暂无数据”区分；自动刷新失败保留当前显示，连续失败只提示一次。库升级失败、仍是旧结构（`schema_mismatch`）时旧结构里没有 `series` / `samples`：门面旧读方法降级为空结果，仓储读取抛 `StorageError`（分析页按读取失败处理），原因由主窗口的只读横幅说明（见 2.4 节）。
- **任何用户操作都不在主线程查数据**：切任务/范围、刷新、进入页面、导航跳转、删除后的重载、打点编辑后的静默重查与定时刷新，都经 `AnalysisViewModel` 交给 `HistoryRefreshWorker` 在后台执行，worker 只查询并返回快照，主线程槽再套用到控件，绝不在工作线程碰控件；加载期间页面显示加载态。结果带批次序号，过期或已切换则丢弃。唯一留在主线程的是任务列表（单条 SQL）。切换焦点指标、视图模式与时间模式不查库。
- 运行中任务：页面可见时定时刷新，保留用户的选择与缩放；刷新间隔随数据量分三档拉长，鼠标悬停或拖动趋势图、窗口最小化时跳过；任务结束时整体重载一次。
- 页面联动：分析页在 `showEvent` 中刷新任务列表（见 7.5 节）。

### 4.3 导出（报告三件套）

`AnalysisExportFlow` 弹保存对话框（默认文件名由命名模板生成，见下，记住上次目录；目标已存在需确认覆盖）→ 维护进行中直接拒绝（不弹对话框；确认覆盖期间维护开始也拒绝）→ 主线程离屏渲染报告图片 → `AnalysisViewModel.start_export` 经 `manager.begin_export()` 登记，线程 `finished` 时 `end_export` → `ReportWorker` 在线程中用 `points.iter_batches` 游标分批读取（打点经 `markers.list`；读库失败抛 `StorageError`，走导出失败路径），经 `core/report.py` 与 `core/export.py` 的纯函数生成：

- `<任务>.csv`：`#` 开头的元数据行（进程、备注、指标、范围、数据质量、被测目标元数据、导出时间等）+ 宽表（时间、已运行(秒)、进程名称、PID、各指标、打点），空洞处插空行；
- `<任务>_摘要.csv`：指标 × 打点区间，每行一个指标的一个区间；
- `<任务>_报告.png`：报告图片 2.0 版式（见下）。

每个文件先写同目录 `<目标>.tmp`，全部成功后逐个 `os.replace` 到目标；取消或失败只删除临时文件，不破坏已有文件。CSV 为 UTF-8 BOM。“仅 CSV / 仅图片”只写对应文件，“复制图片”只放剪贴板。完成后提示可“打开文件夹”，不自动打开。

**报告图片 2.0**（`ui/widgets/analysis/report_sheet.py`，版式计算在 `report_layout.py`）：报告 PNG、“复制图片”、命令行导出与阶段快照走同一条离屏管线（`render_report_for`）。自上而下：标题块（进程名 · PID · 备注，超长按宽度折行，避头标点、西文串不从中间劈开）→ 元信息网格（两列，`core.report.metadata_items`：开始 / 结束 / 时长 / 采集周期 / 指标数 / 点数 / 数据质量 / 被测程序 / 环境）→ 结论表（每指标一行：判定胶囊 / 基线 / 当前 / 较基线 / 每轮均增 / 增速 ± CI / R²）→ 打点区间增量表（至少 2 轮打点才有，`core.report.round_delta_rows`，只统计两端都是基线或用户打点的区间）→ 小倍数趋势图（只画“持续上涨”与“波动”的指标，与界面同一个 `ChartView`）→ 页脚（工具版本、生成时间、降采样说明）。配色默认固定浅色（报告常被贴进文档与邮件，与界面主题无关），设置页“报告配色”（`cfg.report_color_scheme`：`light` / `follow`）可改为跟随当前主题；报告控件按显式 palette 取色，不连 `themeChanged`、不改全局主题。尺寸：输出像素宽恒为 1600，逻辑布局宽 = 1600 / 设备像素比，设备像素比由参数显式给出（默认 1），控件经 `QWidget.render` 画进同一设备像素比的 `QImage`，因此不受屏幕缩放（`QT_SCALE_FACTOR`、系统缩放）影响。折行、网格、列宽与行高是 `report_layout.py` 的纯函数（文字宽度由调用方传入的 `measure` 给出，测试可用 `len`）。渲染必须在主线程，得到的 `QImage` 可交给导出线程保存。

**导出命名模板**（`core/naming_template.py`，纯函数，不依赖 Qt）：语法 `{process}_{build}_{note}_{date}`（默认，`app_config.export_name_template` / 设置页“导出”分组）。字段：`process`（进程名去 .exe）、`build`（任务 `build` 列优先，其次 D-3 元数据的文件版本）、`scenario`（暂无来源，恒空，留给参考库）、`note`（备注前 20 字）、`date`（**导出时刻** `YYYYMMDD_HHMMSS`，由调用方传入的 `now`，即 `services.clock.now()`；不是任务开始时间：同一任务按不同范围多次导出时不会每次撞名弹覆盖确认，也与 1.x 的命名习惯一致；设置页预览用固定的示例导出时刻）、`kind`（报告 / 明细 / 摘要 / 证据包）、`pid`（进程组任务为空）。渲染规则：空字段连同旁边多余的分隔符（`_ - . 空格`）一起去掉，不出现 `__`、开头或结尾的分隔符；Windows 非法字符与控制字符换成 `-`，字段值里的空白换成 `_`；保留名（CON、PRN、NUL、COM1…）加 `_file`；总长不超过 120，超长时先缩短最长的字段值，使日期保留；未知字段原样保留，设置页提示。模板没有 `{kind}` 时沿用旧后缀（报告 `_报告.png`、摘要 `_摘要.csv`、明细 `.csv`、证据包 `.zip`），有 `{kind}` 时类别已在名字里、只加扩展名，报告三件套在用户没改默认名时明细与摘要各取自己的类别渲染，改过名则同基名加 `.csv` / `_摘要.csv`。默认模板与旧的报告命名相比去掉了 PID、加了版本与备注；同一秒内为同名进程导出的文件会得到同一个默认名（确认覆盖对话框兜底），要区分可在模板里加 `{pid}`。命令行 `export` 与自动导出仍用 `core.report.task_basename` / `core.evidence.evidence_filename`，不受模板影响。

**复制结论**（`core/conclusion_text.py`，纯函数）：把分析页当前显示的结论整理成纯文本或 Markdown。首行元数据（进程名 · 文件版本 · PID 或目标类型 · 开始 ~ 结束 · 时长 · 采集间隔 · 备注）；“整体结论：判定。主句”两段原样取自结论条（调用方传入，不另写文案）；统计依据；各指标一行（判定、基线 → 当前、较基线、每轮均增、增速，`MetricLine.from_texts` 直接取摘要表 `SummaryRow.texts`，占位符省略）；有重启续接或中途异常退出时附 `core.verdict.segments_summary`；进程组合计视图附成员结论（`core.verdict` 的成员判定，持续上涨的在前）。Markdown 的指标与成员各是一张表（竖线转义、空单元格写 —，列数恒等）。

**证据包（.zip）**：分析页“导出报告 ▾ → 证据包（.zip）”（`AnalysisExportFlow` 的 `EXPORT_EVIDENCE` 分支）：保存对话框选 zip（默认名由命名模板生成，`kind` 为证据包）→ 主线程渲染报告图片 → `EvidenceWorker`（`ReportWorker` 子类，复用三件套写出，与“导出报告”同一登记与 `begin_export` 互斥）把三件套写到系统临时目录下的 `pm_evidence_*` 工作目录（无论成功、失败、取消都删除），再由 `core.evidence.build_evidence_package` 打成 zip：三件套 + `task.json` + `README.txt` + 可选 `log_excerpt.txt`。`task.json`（`schema_version` 1）含 `generated_at`、`tool`、`task`、`target`（被测目标元数据）、`quality`、`plan`、`markers`、`analysis`、`verdict`（整体 + 每指标，数值直接取自界面同一份 `HistorySnapshot`，不重新拟合）与 `files`；`README.txt` 首行整体判定、随后每指标一行、文件清单、生成时间与工具版本；日志摘录取 `app.log`（含轮转备份）在任务时间段内、含任务 ID 前 8 位或 ERROR / WARNING / CRITICAL 的行，最多 500 行，`services.log_path`（取自根 logger 上 `app.log` 处理器的实际路径）为 `None` 时省略。zip 先写同目录临时文件、全部写完再 `os.replace`，失败删临时文件、不破坏已有同名文件；任务对象缺元数据 / 方案 / 数据质量时从库补，任何一项取不到只留空。判定口径与 `pmctl verdict` 是同一份（`core/verdict.py`），界面导出不传停止原因时取库里记录的真实停止原因（`tasks.meta_json` 的 `stop` 键，见 3.3 节），所以被测进程退出 / 崩溃的任务，证据包整体判定同样可以是 `target_exited`；`task.json` 的 `task` 另有 `exit_code` / `exit_code_hex` / `exit_text` / `exit_exception` / `stop_reason`，顶层 `restarts`（`count` / `segment_number` / `segment_start` / `note`）；README 增“退出：”“重启：”行；明细 CSV 元数据在“退出: …”行写明退出码与中文说明。命令行 `export evidence=true` 产出同样的 zip（见 2.7 节）。

### 4.4 自动更新

`UpdateChecker` 拉取 GitHub 最新 Release → `parse_release_info` 提取版本、资产地址与 `asset_digest`。`UpdateDownloader` 只接受 https 且主机在白名单（`github.com`、`objects.githubusercontent.com`、`release-assets.githubusercontent.com` 及其子域）的地址，重定向同样校验；必须带有效的 `sha256:` digest，下载后逐字节校验，不一致删除文件。缺少 digest 时不下载，界面引导到发布页手动下载。静默检查（启动 3 秒后）发现新版本只发信号，由主窗口以非模态 InfoBar 提示。

**下载的取消与交付互斥**（`UpdateDownloader`）：基类对已取消的任务不发结果信号，若“读完最后一块之后、结果交给界面之前”到来的取消不处理，校验通过的安装包就会留在临时目录无人认领。因此 `execute` 末尾在 `_delivery_lock` 内确认未取消才把临时目录记为待交付，`cancel()` 在锁内删除待交付目录，`handle_result` 在锁内确认未取消才交付；交付之后的取消不再删除（安装程序可能已在用它）。

### 4.5 命令行控制（IPC）

```
pmctl <命令> → （GUI 不在则拉起 --background 实例）→ ping：服务端 PID 与 ping 的 pid 一致、属于当前用户
  → 一行 JSON 请求 → IpcServer（界面线程）按连接缓冲分帧
  → CommandDispatcher：白名单 → 自动化开关 → 是否 ready → 危险命令的完整性比对 → 参数校验
  → 调 MonitorManager / AutoMarkerService / WaitService / ProcessLauncher
      立即命令：一行 ok 回复
      延迟命令（wait / export / verdict / start wait=true）：每 5 秒 heartbeat 事件，完成时一行最终回复，客户端断开即取消
pmctl run：start（每个目标）→ wait stopped（带上限）→ export → verdict → 退出码 / JUnit
```

`verdict` 与报告类 `export` 的读库在后台线程（`TaskAnalysisWorker`：按“全部”范围逐指标 `run_history_query(analysis=True)`，与分析页同一查询路径），随后由 `core/verdict.py` 合成整体判定；`export` 的报告图片经注入的 `report_renderer` 在界面线程离屏渲染（无窗口模式也不出现可见窗口），再由 `ReportWorker` 写文件，`begin_export` 从开始持有到写文件结束，同一时刻只允许一个命令行导出（否则 `busy`）。命令与门禁细则见 2.7 节。

## 5. 数据库表结构与迁移

### 5.1 表结构（Schema v5，`PRAGMA user_version = 5`）

v5 是 2.x 的最终结构：2.x 期间不再迁移，后续阶段只往预留的表与列里写数据。建表 DDL 只在 `data/db/schema.py` 的 `create_current` 一处，它同时写入 meta 四键并置 `user_version`。

| 表 | 列 | 说明 |
|----|----|------|
| `tasks` | `task_id` PK, `pid`, `process_name`, `metric_type`, `interval`, `start_time`, `end_time`, `status`, `note`, `sample_count`, `last_sample_at`, `create_time`，及 2.x 预留的 19 列 `target_kind`（默认 `'pid'`）、`target_spec`、`group_id`、`member_key`、`exit_code`、`resume_on_restart`、`restart_limit`、`plan_json`、`meta_json`、`scenario`、`build`、`is_reference`、`source_task_id`、`origin`、`planned_cycles`、`done_cycles`、`missed_cycles`、`lag_p95_ms`、`collect_p95_ms` | 前 12 列与 v4 相同。`target_kind`（`pid` / `tree` / `name`）与 `target_spec`（tree：`{"root_pid", "root_create_time"}`；name：`{"name"}`）自进程组任务起使用，只在建任务时 INSERT、UPSERT 不改；进程组的成员序列在 `series` 里是 `指标@成员键`。`metric_type` 存 JSON 数组文本；`sample_count` 为采样周期数（同一周期多指标算一次，即不同毫秒时间戳个数），与样本同事务维护；分析页按 `sample_count > 0` 判断有数据；`create_time` 为被监控进程的创建时间（epoch 秒，可空，用于识别 PID 复用）。时间列仍是 ISO 文本。预留列一律可空或带默认值：1.4.1 回退时按 8 个旧列 `INSERT OR REPLACE` 仍能写入；`TaskRepo.save` 的 UPSERT 只更新模型携带的列，不会清掉它们 |
| `series` | `series_id` PK, `task_id`, `metric`，`UNIQUE(task_id, metric)` | 一个 (任务, 指标) 一条序列，`series_id` 是紧凑表里的短键。同一任务按指标列表顺序建立，同一毫秒多指标按 `series_id` 排列；指标名为空（旧数据指标为 NULL 且任务指标列表为空）时记为 `''` |
| `samples` | `series_id`, `ts_ms`, `value`，PK `(series_id, ts_ms)`，`WITHOUT ROWID` | 样本。`ts_ms` 为 UTC 毫秒整数，主键即聚簇顺序，约 18 字节/行（v4 的 `data_points` 约 193 字节/行；3 天 5 指标 1 秒周期的合成库 1,282,200 行约 23.4 MB）。同一序列同一毫秒只有一行，后写覆盖先写 |
| `rollup_1m` | `series_id`, `bucket_ms`, `count`, `first_ms`/`first_value`, `last_ms`/`last_value`, `min_value`/`min_ms`, `max_value`/`max_ms`, `sum_y`, `sum_yy`, `sum_x`, `sum_xx`, `sum_xy`，PK `(series_id, bucket_ms)`，`WITHOUT ROWID` | 分钟汇总（规则见下）。`min_ms` / `max_ms` 为最值最早出现的时间（图表取真实点用）；拟合用的各阶和以 x = 相对桶起点的秒数计算（避免绝对 epoch 平方的灾难性抵消），合并多个桶时由使用方平移到统一原点 |
| `series_gaps` | `series_id`, `start_ms`, `end_ms`，PK `(series_id, start_ms)`，`WITHOUT ROWID` | 写入时记录的空洞：空洞前后两个样本的时间 |
| `meta` | `key` PK, `value` | `schema_version`（与 `user_version` 相同）、`created_by_version`（建库或重建迁移的应用版本）、`last_writer_version`（最近一次以可写方式启动的版本，启动校正 `touch_writer` 更新）、`min_reader_version`（能安全读写本库的最低版本，v5 为 `2.0.0`）；判定见 `data/db/meta.py` 与 2.4 节第 7 步 |
| `task_members` | `task_id`, `pid`, `create_time`, `name`, `first_ms`, `last_ms`，PK `(task_id, pid, create_time)` | 进程组任务（tree / name）的成员留痕：实例首次出现写一行，消失或任务结束时更新 `last_ms`（只增不减）；PID 复用（创建时间不同）是另一行；由 `MemberRepo` 写（见 2.8 节） |
| `handle_snapshots` | `task_id`, `ts_ms`, `type_name`, `count`，PK `(task_id, ts_ms, type_name)` | 句柄按类型的计数快照；v5 只建表，后续阶段写入 |
| `task_markers` | `id` PK, `task_id`, `timestamp`, `label`, `created_at`, `kind` | 打点；`kind` 取 `user`/`baseline`/`pause`/`resume`（默认 `user`），另有 `crash`（被测进程异常退出，标签“异常退出 0xC0000005（访问冲突）”）、`restart`（被测进程重启后续接，“第 N 次启动 PID …”）、`recover`（工具被强杀后续采，“工具重启后继续监控”）由采集线程写入，`interrupt` 仍是预留；每个任务至多一个 `baseline`；索引 `(task_id, timestamp)` |
| `data_points` | `id` PK, `task_id`, `timestamp`, `value`, `metric_type` | **v4 原样定义、v5 中恒为空表**（连同 v4 的索引 `(task_id, metric_type, timestamp)`）：用户回退到 1.4.1 时它只认识这张表，降级期间的样本写在这里，再用 2.x 启动时由启动校正导回 `samples` 并清空 |

**分钟汇总与空洞的规则**（`data/repos/rollup.py`，写入、重算、查询三处共用）：

- 空洞：同一序列相邻两样本间隔（毫秒差 / 1000.0 秒）严格大于 `tasks.interval × 2.5`，与 `AnalyticsRepo.gaps` 的口径逐位相同；任务不存在或周期不是正数时不记空洞。
- 段起点：序列的首个样本与每个空洞的 `end_ms`。桶键 `bucket_ms = max(所在自然分钟起点, 所在段的段起点)`：一个自然分钟里出现空洞时拆成两行，**任何汇总行都不跨空洞**；同一序列的汇总行互不重叠。
- 不变式：`rollup_1m` 与 `series_gaps` 恒等于“从 `samples` 按上述规则整体重算”的结果（各阶和只差求和顺序带来的舍入），由 `tests/test_rollup.py` 与加速浸泡守住。维护方式：按时间顺序追加（采集常态）时在写样本的同一事务里逐行判空洞、算桶键，按 (序列, 桶) 合并后每桶一条 UPSERT；同一毫秒覆盖已有样本时按样本重算该分钟；乱序写入（早于该序列最后一个样本、且该毫秒原本没有样本）按受影响区间重算空洞与汇总，并记 WARNING 与计数（正常采集不会出现）；改采集周期（`TaskRepo.save` 发现 `interval` 变化）时在同一事务内重算该任务的全部序列；导回回退数据、重建式迁移与设置页“重建汇总”（`Maintenance.rebuild_rollups`，后台线程、两段式维护锁，见 7.6 节）用 `rebuild_rollups` 整体重算（逐序列各两条 SQL，不在 Python 里逐行处理）。

**写入与序列缓存**：`PointRepo.append` 先在事务外把时间编码为毫秒（类型不对直接 `TypeError`、不开事务），再在一个写事务内经 `series_cache` 解析或新建序列、`INSERT OR REPLACE` 样本、维护汇总与空洞，并累加 `sample_count` / `last_sample_at`。序列缓存按全局代号失效：所有删除 `series` 的路径（删任务、过期清理、孤儿清理）在删除事务内 `invalidate()`，写入方在**拿到写锁之后**才读缓存，因此不会用到删除前取得的旧映射（被删的 `series_id` 可能被新序列复用）。`iter_batches` 每个序列一个有序游标，按 (时间, 序列号) 多路归并。

**与 v4 的语义差异**：时间精度为毫秒（写入按 `to_ms` 四舍五入）；同一序列同一毫秒后写覆盖先写；同一毫秒多指标按 `series_id` 排序；空指标名的序列记为 `''`。v5 仓储与 v4 仓储（`tests/fixtures/frozen_v4_repos/` 冻结副本）在同一数据上的查询结果由 `tests/test_storage_v5.py` 逐项比对。

- 外键约束未启用，删除任务时在同一事务里手工删 `series` 及其 `samples` / `rollup_1m` / `series_gaps`、`task_markers`、`task_members`、`handle_snapshots`、`data_points`（尚未导回的降级数据）与 `tasks`（`delete_task_rows`，`TaskRepo.delete` 与过期清理共用）。
- 每个连接统一设置 `busy_timeout=5000`、`synchronous=NORMAL`、`journal_size_limit`（8 MB，按连接生效）；`journal_mode=WAL` 是写在库文件头里的持久属性，每个工厂只在首次打开可写连接时设一次（每次都设约多花 0.3 ms）。只读工厂（`read_only=True`）不切日志模式（切换本身就是一次写），连接设 `query_only`，`transaction()` 直接抛 `StorageError`（`ConnectionFactory` 负责）。
- **常驻占位连接**：SQLite 在最后一个连接关闭时 checkpoint 并删除 `-wal/-shm`；每次操作新建连接、无常驻连接时，每次写入都等于“最后一个连接关闭”，`-wal` 被反复删除重建，实测单次写入约 13.65 ms。工厂默认持有一个只读（`query_only`）空闲连接让 `-wal` 常驻，单次写入降到约 1.55 ms；`-wal` 由自动 checkpoint 循环复用。迁移/备份/改名库文件时用 `keep_alive=False`（Windows 上打开的文件不能改名），`Database.close()` 释放占位连接。常驻连接下 `-wal` 不会随连接关闭被删，故 `Maintenance.vacuum` 在 VACUUM 前后各做一次 `wal_checkpoint(TRUNCATE)`，`cleanup_older_than` 删除后也截断一次，避免“压缩后占用反而变大”。
- 启动时（任务启动前）由组合根经 `MaintenanceService.startup_reconcile` 按序各调用一次：① `touch_writer` 记录本次写入的应用版本（`meta.last_writer_version`）；② `import_legacy_points`：把回退 1.4.1 期间写进 `data_points` 的行导回 `samples`（口径同重建式迁移对 v1 源库：旧内存键 `memory_vms` / `memory_pagefile` 并入 `memory_private` 且同一时刻只留一行，任务指标列表里的旧键同样改名；NULL 指标回填任务首指标；孤儿丢弃；时间戳无效的行跳过；同毫秒后写者胜），清空 `data_points`，重算受影响任务的计数与这些任务全部序列的汇总、空洞（导回的样本可能早于已有样本，增量维护不适用）；`data_points` 为空时只做一次只读检查，不开写事务。必须在孤儿任务校正之前：1.4.1 不维护 `last_sample_at`，导回后它才有值；③ `purge_orphan_series`：删除任务已不存在的序列及其样本、汇总、空洞，以及孤儿的 `task_members` / `handle_snapshots` / `task_markers` 行（1.4.1 删任务只删它认识的表）；④ `reconcile_orphan_tasks`（把崩溃遗留的 `running` 任务校正为 `stopped`，结束时间取 `last_sample_at`）；⑤ `reconcile_sample_counts`（对 `sample_count=0` 但有样本的任务按样本重算，存在性逐序列走主键前缀、不扫全表；兜底 1.4.1 对已有任务 `INSERT OR REPLACE` 清零计数的情形）；⑥ `cleanup_old_tasks`（保留天数默认 0 = 禁用，且必须在孤儿校正之后）。各步失败只记日志（门面降级为 0），不阻止启动；只读库（更高版本创建或升级失败）整个跳过。这些方法刻意不放在构造函数里。

### 5.2 迁移机制：重建式迁移（v0–v4 → v5）

任何 v0–v4 的旧库**一次**迁到 v5，且从不在旧文件上改结构：新建 `<库>.migrating`，用 `create_current` 建好 v5 结构，再把旧库以只读方式挂载、用 SELECT 把数据搬进来，最后换库。旧文件全程不被写入（WAL 库只做一次 checkpoint），逐字节保留为 `.bak_v<起始版本>`，磁盘峰值约为旧库 + 新库。代码在 `data/db/migrations/`：`runner.py` 的 `MigrationRunner` 负责探测、预检、换库、恢复与结果报告，`rebuild.py` 负责建库与搬数据。

**流程**（`MigrationRunner.migrate()`）：

1. **探测**：用不设任何 PRAGMA 的裸连接读 `tasks` 表是否存在与 `user_version`（连接工厂的可写连接会把回滚日志模式的旧库切成 WAL，在备份之前就改掉文件头）；文件不存在时不连接（不让 sqlite3 建出空文件）。没有 `tasks` 表 → 直接建当前结构（`UP_TO_DATE`，`created=True`；原路径没有库但留有换库中断痕迹时先按第 6 步恢复）；`user_version` ≥ 5 → `UP_TO_DATE`（更新的库原样使用，只记警告，是否只读由 meta 决定，见 2.4 节第 7 步）。`probe()` 是同一探测的只读版，另给出库文件大小（含 `-wal`）与待搬迁行数估计（`data_points` 的最大 rowid，走 B 树最右端），供组合根决定是否先显示进度窗口；探测本身出错（库被锁、损坏）原样抛出、不记入 guard。
2. **磁盘预检**：库所在磁盘的可用空间须 ≥ 旧库大小（含 `-wal`）× 0.3 + 200 MB（新库实测约为旧库的 0.1～0.15 倍，比例留出余量），不足 → `BACKUP_ABORTED`，报告带 `required_bytes` / `free_bytes`（`disk_shortage` 为真，界面写明“需要约 N MB 可用空间（当前 M MB），数据库未改动”）；查询可用空间本身失败只记警告、照常迁移。
3. **让旧库自包含**：WAL 模式的旧库做一次 `wal_checkpoint(TRUNCATE)`（裸连接）；回滚日志模式的旧库不做任何写入。checkpoint 被其他连接挡住 → `BACKUP_ABORTED`（原因“旧数据库正被其他程序占用”），旧库原样。
4. **重建**（`rebuild.rebuild_into`）：新文件以 `journal_mode=OFF`、`synchronous=OFF` 写（失败即整个删除，不需要日志），旧库以 `mode=ro&immutable=1` ATTACH（不加锁、不建 `-wal/-shm`）；搬 `tasks`、搬样本（每 5 万行一批，回调进度“搬样本 N / M 行”）、按样本重算任务计数、整体生成汇总与空洞（按序列回调进度“生成汇总 N / M”）、搬 `task_markers`。**完成标记**：建表时 `create_current` 置的 `user_version` 先改回 0，全部数据提交并 fsync 之后才写成 5，再切 WAL 并 fsync——中途崩溃留下的 `.migrating` 不会被当成完整的新库。失败时删掉新文件；只对 `sqlite3.OperationalError` 与 `OSError`（锁、IO、磁盘满这类瞬时故障）重试一次，数据转换等程序性异常重试必然再失败，直接 `FAILED_RESTORED`。
5. **换库**：先确认旧库没有残留日志（`-wal` 非空或存在 `-journal` 说明有其他进程在写，不能换，`FAILED_RESTORED`），再用 `os.link(db, bak)` 给旧文件建硬链接备份（与旧库是同一份文件），然后 `os.replace(.migrating, db)` → `MIGRATED`。两步之间任何时刻原路径都是完整的库；换入失败只需删掉多出来的硬链接（`FAILED_RESTORED`）。文件系统不支持硬链接时退回**改名式**：先写 `<库>.swap_pending` 标记（旧库名、新库名、备份名、起始版本、时间，fsync 落盘后才改名），旧文件改名为备份、新文件改名为库，换完删除标记。改名式下任何失败之后旧库都回到原路径（`FAILED_RESTORED`）；只有连改回也失败才是 `FAILED_KEPT`（原路径暂无数据库，报告的 `backup_path` / `broken_path` 指向旧文件，标记与完整的新文件留给下次启动恢复）。
6. **换库中断的恢复**（探测阶段，原路径没有库——文件不存在或 0 字节）：只认两种中断痕迹——`.swap_pending` 标记或完整的 `.migrating`（能打开、`user_version` 为 5、有 `tasks` 表、`quick_check` 通过）。完整的 `.migrating` → 换到原路径，按 `MIGRATED` 报告；有标记 → 把标记里记的备份（找不到再取最新的 `.bak_v[0-4]*`）改回原路径、重新迁移；放不回 → `FAILED_KEPT`。硬链接式换库从不让原路径为空，改名式先写标记再改名，所以"原路径没有库、只剩裸 `.bak_v*`、没有标记"只会来自用户主动删库：这时按全新库启动、不动备份，并记 WARNING 列出发现的备份文件名与手动找回方法；不完整的 `.migrating` 一并删除。换库成功后，与本次备份是同一份文件的多余硬链接备份（上次中断留下的 `.bak_v0` 之类，`os.path.samefile` 判定）会被删除。`.bak_v5` 与无关文件不算中断痕迹。

**数据转换口径**（与冻结的就地迁移链 v1–v4 逐项一致，`tests/test_rebuild_migration.py` 对 golden 样本比对“直接重建”与“就地链到 v4 再重建”）：

- `tasks`：v0 的裸指标名转 JSON 数组；v0/v1 指标列表里的 `memory_vms` / `memory_pagefile` 改名为 `memory_private` 并去重（列表不变时保留原文本）；缺失的 `note` 取 `''`、`create_time` 取 NULL；`sample_count` / `last_sample_at` 搬完样本后按样本重算。
- 样本：(task_id, 指标) 建 `series`；v0 没有 `metric_type` 列，取所属任务的原指标名；v0/v1 同一 (task_id, timestamp) 下的三项重复内存指标按冻结 v2 口径只保留 id 最小的一行再改名；仍为 NULL 的指标回填为所属任务指标列表的首项（列表为空时记为 `''`）；任务不存在的孤儿数据点丢弃；同一序列同一毫秒有多行时保留 id 最大（后写）的一行。
- 时间换算（ISO 文本 → UTC 毫秒，与 `mappers.to_ms` 一致）：本机时区没有夏令时（`time.daylight == 0`）且抽样核对偏移一致（首行、末行、当前时间与首末之间每个自然年的第一行，逐年按 id 二分查找、不扫表）时走纯 SQL 快路径（`julianday` 换整秒 + 微秒四舍五入 − 固定时区偏移）；否则逐行调用注册的 Python 函数。快路径里不是标准形态的文本同样逐行交给 Python。时间戳为 NULL 或无法解析的行**跳过并计数**（`MigrationReport.skipped_rows`，记 WARNING 与样例），不让这类确定性的数据错误使迁移整体失败（否则每次启动都会失败）。
- `task_markers` 原样搬（v3 之前没有该表；没有 `kind` 列时取 `user`）。
- 别名与版本号用字面量写死，不引用会演进的常量（运行时解析函数的冻结副本在 `_frozen.py`）。

**结果与报告**：`MigrationReport` 带 `outcome`、起止版本、`backup_path`（本次新建的备份）、`broken_path`、`created`、`required_bytes` / `free_bytes`、`skipped_rows` 与失败原因 `reason`（中文，如“旧数据库正被其他程序占用”“新数据库无法换到原位置（…）”“读写数据库文件出错（…）”“旧数据转换出错（…）”“上次升级中断，未能自动恢复”，供只读横幅显示）。重建式迁移从不改动旧库，所以 `FAILED_RESTORED` 的含义是“迁移没有完成，原路径仍是未被改动的旧库”，不会出现 `RESET`。`Database` 把报告映射为三个互斥标志（`backup_aborted` / `migration_failed` / `data_reset`）与成功时的 `migrated_from` / `backup_path`；组合根对失败结果的处理见 2.4 节第 6、7 步（`FAILED_KEPT` 退出码 3，其余失败只读打开、跳过启动校正）。备份命名 `<库>.bak_v{起始版本}`，该文件已存在时不覆盖（可能是更早一次迁移留下的唯一原始数据），改用 `<库>.bak_v{版本}_{YYYYmmdd_HHMMSS}[_序号]`。同一库路径每进程只尝试一次迁移（按（库路径, 目标版本）记录的 guard），失败时不会因反复实例化 `Database` 而重复迁移。

- **冻结的就地迁移链**：`v1.py`～`v4.py`（每版一个 `apply(cursor)`）与 `_frozen.create_schema_v4` 保留不动，`MigrationRunner(target_version=1..4)` 仍走就地链（checkpoint + 文件级备份 → 单事务执行链 → 失败从备份原子还原并重试一次，还原失败按旧库可读与否 `FAILED_KEPT` / `RESET`）。生产路径不再调用，只供 golden 样本生成器派生 v2/v3 样本、测试里的“就地链到 v4”对照。链上各版的口径：v0 → v1 `data_points` 补 `metric_type`、`tasks.metric_type` 转 JSON 数组；v1 → v2 合并旧内存指标并去重；v2 → v3 增加 `note` / `sample_count` / `last_sample_at`、新建 `task_markers`、删孤儿、回填 NULL 指标、收敛索引；v3 → v4 增加 `create_time` 与 `kind`。
- 旧库迁移未成功（只读打开的旧结构）时，`TaskRepo.list_with_data` / `AnalyticsRepo.sample_count` 在缺少 `sample_count` 列时回退为按样本（有 `samples` 表）或旧 `data_points` 判断，`mappers.row_to_task` 对缺失的新列取默认值，旧指标键在界面上仍显示为“私有字节”。
- **真实升级起点只有 v0 与 v1**：已发布版本写出的库只有 `user_version` 0（v1.0.5 / v1.0.6）与 1（v1.1.0 起至 v1.4.1；v1.2.0 起为 WAL 模式）两种；v2、v3 只存在于开发过程，由真实 v1 库经冻结就地链截断派生的样本覆盖（真实旧库矩阵见第 8 节）。
- **备份逐字节等于旧库**：探测与 checkpoint 都用裸连接、旧库以 immutable 方式挂载、备份就是旧文件本身（硬链接或改名），回滚日志模式的旧库（v1.0.x、v1.1.0 写出的）文件头也不再被切成 WAL（v4 时代由 golden 测试 strict xfail 锁定的问题已解决，现为普通断言）。
- **回退 1.4.1 的兼容**（`tests/test_reverse_compat_v141.py` 用 1.4.1 冻结副本锁定）：1.4.1 的 `Database` 只判断 `user_version >= 1`，打开 v5 库时直接使用，不迁移、不备份、不改结构；能列任务（`tasks` 新增列都有默认值），但看不到 2.0 写入的历史（它只读 `data_points`）；降级期间新写的点落在 `data_points`，再升回 2.x 时由启动校正导回 `samples`（见 5.1 节）；它删任务只删 `tasks` 与 `data_points`，留下的孤儿序列、样本与打点由启动校正清掉；它写的任务 `sample_count` 为 0，由启动校正重算补回；它对已有任务行调用 `save_task`（`INSERT OR REPLACE`，只写 8 个旧列）会清空 `note` / `sample_count` / `last_sample_at` / `create_time`，其中 `sample_count` 可由启动校正恢复，其余不可恢复（正常的回退使用路径碰不到）。数据量大的导回经进度窗口执行（见 2.4 节）。

### 5.3 门面与仓储分工、错误语义

- **仓储**（`db.tasks` / `db.points` / `db.markers` / `db.analytics` / `db.maintenance`）共用 `Database` 的同一个连接工厂，每次操作自建连接，可在任意线程调用。失败一律抛 `StorageError`（原始 `sqlite3.Error` 挂在 `__cause__`）；参数类型错误（`TypeError`/`ValueError`）是调用方的编程错误，原样抛出，不伪装成存储故障。**新代码直接用仓储**，需要区分“读取失败”与“没有数据”的地方（分析页、导出、设置页清理）必须用仓储并捕获 `StorageError`。
- **门面旧方法**（`save_task`、`get_task_data_points`、`get_metric_stats`、`add_marker` 等）是对仓储的薄委托，签名与返回语义不变：原来吞异常返回 `None` / `[]` / `0` / `False` 的，捕获 `StorageError` 后记 ERROR 日志（带堆栈）并返回原值；成功时的布尔方法仍返回 `True`（与是否命中行无关）。`save_data_points` 的连续失败计数与日志节流（首次带堆栈，之后每 100 次一条）留在门面。旧方法的 `since_iso` 字符串在门面内部转成 `datetime` 再交给仓储。采集线程（`save_task` / `save_data_points` / `update_task_status`）与启动校正（`reconcile_*` / `cleanup_old_tasks`）继续走门面。
- **磁盘已满**：`_guard.storage_errors` 把 `SQLITE_FULL`（主码 13）与 IOERR 家族里“磁盘满”的那部分转成 `StorageError` 的子类 `StorageFullError`，所以所有 `except StorageError` 照旧能接住，要区分的调用方再单独捕获子类。IOERR 只在有明确证据时才归为磁盘满：扩展码属写入 / fsync / 截断 / 共享内存扩展类（或不带扩展码），且文本含 “disk full” / “database or disk is full”，或 `__cause__` 链上的 `OSError` 是 `ENOSPC` / Windows 的 112、39；其余 IOERR 仍是普通 `StorageError`，免得把磁盘坏了说成磁盘满了。这里只做分类：门面旧方法照旧吞掉并返回原值，采集线程怎么保留缓冲、怎么续采由 worker 负责。测试里造真实的 `SQLITE_FULL`：`tests/storage_faults.simulate_disk_full(db)`（给连接设 `PRAGMA max_page_count`，写入大量数据时由 SQLite 自己报满，不用打桩）。
- **例外**：`vacuum()` 失败抛 `StorageError`（设置页据此提示“清理失败”，不再显示“完成”）；`iter_data_points()` 失败抛 `StorageError`（导出必须知道读取是否完整）。
- 打点 ID：`markers.add` 返回自增 ID；`MonitorManager.add_marker` 直接用它，门面 `add_marker` 仍只返回布尔。
- **只读模式**：`Database(read_only=True)` 用于库由更高版本写入、当前版本不能安全修改（`newer_version` 记写入者版本），或升级没成功、库仍是旧结构（`schema_mismatch=True`，此时一律只读）。只读时不跑迁移，连接工厂设 `query_only`、`transaction()` 直接抛 `StorageError`，因此所有仓储写入抛 `StorageError`，门面旧写方法按原语义返回 `False`；启动校正整个跳过；主窗口挂常驻横幅并让监控页拒绝开始监控、等待启动与打点（见 2.4 节）。`AnalyticsRepo` 的显式读事务在只读连接上同样可用。
- 依赖方向：`data` 运行时不依赖 `core`（`data/models.py` 对 `core.contracts` 的引用只在 `TYPE_CHECKING` 下）。版本比较放在 `utils/version.py`，`data.db.meta` 与 `core.update_checker` 共用（后者原样再导出 `compare_version`，旧引用不变）。聚合结果转趋势拟合输入用 `core.analysis.trend.fit_input_from_aggregates(agg)`。`gaps` / `buckets` 的空洞判定默认倍数为 2.5（相邻采样间隔 > 2.5 × 采集周期，常量 `DEFAULT_GAP_FACTOR` 定义在 `data/repos/rollup.py`、经 `analytics_repo` 沿用）。

## 6. 退出路径不变式

**进程退出码**（`app.bootstrap.run()` 的返回值）：0 正常退出（含已有实例、本进程只发激活消息后退出）；2 数据目录不可用（`EXIT_DATA_DIR_UNAVAILABLE`）；3 数据库升级失败且旧库没能回到原路径（`EXIT_MIGRATION_FAILED`）；4 仅无窗口模式：没能开始 IPC 监听（`EXIT_IPC_UNAVAILABLE`：没有管道就收不到包括 `quit` 在内的任何命令，留着只会成为关不掉的后台进程）。无窗口模式启动时发现设置里关闭了“允许命令行与脚本控制”，记日志后同样以 0 退出（pmctl 据此提示去设置里打开）。2、3、4 都发生在主窗口与任何后台线程创建之前，直接返回、不经下面的收尾：数据目录不可用时只记日志（打包版另弹原生错误框）；迁移阶段（进度窗口与 `MigrationWorker` 在主窗口之前、界面线程轮询等它结束，窗口在迁移结束前忽略关闭事件）结果为 `FAILED_KEPT` 时弹原生错误框写明原文件位置后返回。迁移的其余失败不退出，以只读方式继续启动（见 2.4 节）。

组合根创建 `QApplication` 时设置 `setQuitOnLastWindowClosed(False)`，因此唯一真退出路径是 `MainWindow.closeEvent` 收尾完成后显式调用 `QApplication.quit()`；`app.bootstrap.run()` 在 `exec_()` 返回后以 `os._exit` 终止进程，规避仍在阻塞的后台线程（如卡在 `urlopen` 的下载线程）被销毁时 Qt 的致命中止（0xC0000409）。

**收尾只经 `ShutdownCoordinator`**（`core/shutdown.py`）。真退出时主窗口先隐藏窗口给出即时反馈，再按固定四步收尾，进度文案（“正在停止监控任务…”“正在结束后台操作…”“正在保存…”）写日志并显示在托盘图标的悬停文字上：

1. `manager.stop_all_tasks()`：给全部监控任务置停止标志（不等待）；紧接着 `registry.cancel_all()` 对登记表里仍在运行的短命线程（检查更新、下载、导出、清理、历史刷新）统一发出取消，让它们与任务收尾并行；
2. `manager.join_all(3000, deadline=)`：带超时等待任务线程收尾落库；
3. `registry.shutdown_all(deadline=)`：按登记顺序等待登记表线程（已取消的不重复取消），登记后从未启动的条目顺手清掉；
4. `db.close()`：关闭数据库（释放常驻占位连接）。

整个流程有 **30 秒总期限**：开始时换算成截止时间传给第 2、3 步，落实到每一次等待——每次取单项超时与剩余时间的较小者，剩余 ≤0 的直接跳过并记日志，因此卡住的线程再多，总耗时也不超过期限；期限耗尽后各步仍照常执行（只是不再等待），进度文案顺序不变，仍关闭数据库。任何一步出错只记日志、绝不抛异常。期限内没收完的线程随后被 `os._exit` 直接终止——“不丢数据”由“总期限 + 日志”兜底，而不是无限等待。以下不变式不得破坏（`tests/test_close_behavior.py` 守护）：

1. 默认配置（不最小化到托盘）且无运行中任务时，关窗直接走真退出。
2. 托盘菜单“退出”、设置页“关于与更新”的“立即安装”（`install_requested` → `quit_for_install`）都置 `_really_quit = True`，绕过隐藏分支与关窗三选，走同一条真退出路径；有因磁盘已满未写入的数据（`held_point_count`）时，托盘“退出”先经 `services.dialogs.confirm` 弹“有 N 条因磁盘已满未写入的数据，退出后将丢失。仍要退出吗？”，取消则不退出；“安装并退出”在启动安装包**之前**（`about_group.exit_guard`）问同一句，取消则不启动安装程序、状态栏写“已取消安装”。命令行 `quit` 与会话结束（注销 / 关机）不能交互，只记一条 WARNING。系统注销/关机（`commitDataRequest`，DirectConnection）同样置位，并在处理函数里直接 `close()` 进协调器：Qt 的会话结束流程只关闭可见窗口，隐藏在托盘时若等它发关闭事件，协调器会被绕过；收尾只做一次，之后的关闭事件直接接受。会话结束被取消、窗口重新显示（`showEvent` / 托盘“显示主界面”）时，只复位由会话结束置的标志，之后关窗仍走托盘与确认。
3. 隐藏到托盘不停止任务、不做任何清理，仅忽略本次关闭事件。
4. 有运行中任务且并非 `_really_quit` 时经 `services.dialogs.ask_close_action` 弹出三选（生产实现为 `CloseActionDialog`：最小化到托盘 / 停止监控并退出 / 取消；磁盘已满、数据只留在内存时多一行警示“有 N 条因磁盘已满未写入的数据，退出后将丢失”，条数来自 `MonitorManager.held_point_count`，仅关窗路径；托盘 / 安装更新 / 命令行 / 会话结束的退出不经过它，托盘与安装更新用上面的二次确认）；主按钮与默认焦点是“最小化到托盘”，无托盘时隐藏主按钮、焦点给“取消”，“停止监控并退出”是普通按钮、回车不触发。开启“关闭时最小化到托盘”且托盘可用时直接隐藏。
5. 无托盘环境（offscreen/CI 或精简系统）下 `TrayController.is_available()` 为 False，所有托盘分支天然短路，行为退化为无托盘现状。
6. 真退出的收尾整体包进 `try/finally`，`QApplication.quit()` 放在 `finally`：收尾中途抛异常也必须退出，否则窗口已隐藏而事件循环不退出，用户无法恢复。`finally` 里先隐藏托盘图标（`os._exit` 不经 Qt 析构，不隐藏会残留幽灵图标），再注销全局打点快捷键。
7. 真退出只经 `ShutdownCoordinator` 按上述四步收尾，总期限 30 秒按截止时间落实到每次等待、超时记日志；主窗口不逐页收尾线程，页面新增短命线程时只需在 `services.threads` 登记。
8. 单实例守卫在 `QApplication` 创建之后、窗口与线程创建之前运行：互斥量判定已有实例时尝试发送激活消息（送没送达都）直接返回退出码 0；互斥量不可用降级为允许启动、主实例监听失败照常启动（见 2.4 节），不能因单实例机制本身阻止用户使用。
9. 真退出前（`closeEvent` 里、进入协调器之前）先停界面看门狗（`UiWatchdog`）与 `SystemThemeWatcher`：收尾会阻塞界面线程最长 30 秒，看门狗不能把它当成卡死，收尾期间也不再切主题（窗口已隐藏，重刷样式表只会拖慢退出）。
10. 无窗口模式没有主窗口，真退出由 `HeadlessRuntime.quit()` 经同一个 `ShutdownCoordinator` 完成（只执行一次，退出码 0）：触发源是 `quit` 命令（任何时候都放行，包括关闭了命令行控制）、Ctrl+C / Ctrl+Break、`--idle-exit-s` 空闲到时、会话结束（`commitDataRequest`，DirectConnection：必须在系统结束进程之前同步收尾，任务的结束时间与数据质量才能落库）。有窗口模式下命令行 `quit` 等价于托盘“退出”（`MainWindow.request_quit`）。被测目标元数据探针线程（守护线程）由 `manager.join_all` 在总期限内等待并当场交付结果，不在登记表里。
11. 存储守卫（`StorageGuard`）的定时器与在途后台作业（-wal 兜底 checkpoint、quick_check）在收尾协调器之前先停：有窗口模式在 `closeEvent` 里紧接着停看门狗之后 `_stop_storage_guard()`，无窗口模式由 `HeadlessRuntime.quit()` 的 `quit_hooks` 调用 `guard.stop()`。`stop()` 幂等、不等待，只取消在途作业（quick_check 会 sqlite3 级中断）；作业线程都在登记表里，由第 3 步在总期限内等待，所以 quick_check 跑到一半退出也不会拖住退出。
12. 等待被测进程重启的任务（`WAITING_RESTART`）随程序退出及时结束：它每秒查找一次新进程，等待走时钟的 `wait(事件, 1.0)`，`stop()` 置位事件即醒来，所以 `stop_all_tasks` → `join_all` 在 30 秒期限内（不必等满一个轮询周期）收尾，按最后一次退出的原因落库（`tests/test_soak_exit_paths.py` 守护）。
14. 真退出的 `closeEvent` 在收尾之前先停窗口状态的防抖定时器并保存一次窗口状态（收尾会隐藏窗口并阻塞界面线程）；保存失败只记日志、不阻止退出（`tests/test_window_state.py` 守护）。
13. 会话锁 `session.lock` 在所有正常退出路径的收尾完成之后删除（关窗、托盘退出、命令行 `quit`、会话结束、无窗口 `quit`；收尾抛异常也在 `finally` 里删），隐藏到托盘与取消关闭不删；锁属于另一个仍在运行的实例时既不覆盖也不删（见 2.4 节）。强杀 / 崩溃 / 断电不经这些路径，锁因此残留，下次启动据此判为异常退出。

## 7. 关键契约

### 7.1 采集失败语义

采不到的指标**不记 0**：`collect_metrics` 的返回字典中不包含它，原因记入 `collector.last_unavailable`；任务通过 `metrics_unavailable` 通知界面；库里该时间戳不存在对应行，分析图表与 CSV 按空处理。原因是 `UnavailableReason` 枚举。不适用的指标（如其他会话进程的 GDI/USER）以携带原因枚举的 `MetricNotSupported` 表达，与权限不足（`AccessDenied` → `ACCESS_DENIED`）区分，文案不同。进程不存在或 PID 被复用时 `collect_metrics` 返回 `None`，任务据此以 `StopReason.PROCESS_EXITED` 结束。

### 7.2 时间参数纪律：仓储只收 datetime，样本存为 UTC 毫秒

仓储的时间参数（`DataPoint.timestamp`、`PointQuery.since/until`、`markers.list`、`analytics.*` 的 `since/until/ts`）**只接受 `datetime`**（本地 naive），传入 float/int/str 直接 `TypeError`——从入口杜绝绘图用的 epoch float（`dp.timestamp.timestamp()`）流入查询：对 ISO 文本列，SQLite 会做跨类型比较、过滤静默失效；对整数毫秒列，收到秒级 epoch 不会报错，只是差了 1000 倍。编码只在 `data/mappers.py`：

- 样本（`samples.ts_ms`、`rollup_1m` / `series_gaps` 的各毫秒列）存 **UTC 毫秒整数**：`to_ms` / `from_ms` 往返无损。整秒部分由 `datetime.timestamp()` 得到（本地时间按本机时区解释，含夏令时规则），微秒部分按“四舍五入到毫秒、0.5 毫秒进位”整数运算；不用 `round(dt.timestamp() * 1000)`（浮点乘法在恰好 0.5 毫秒处的进位方向不确定，会与迁移时 SQL 侧的换算差 1 毫秒）。返回给调用方的时间一律经 `from_ms` 转回本地 naive datetime；空洞判定与分桶边界都是整数毫秒相减，结果确定。
- 任务与打点的时间列（`tasks.start_time` 等、`task_markers.timestamp`）仍是 `datetime.isoformat()` 文本，经 `to_iso` / `from_iso`。
- **边界取整规则**：范围类边界（查询的 `since` / `until`，闭区间）比较的是已存的毫秒值本身，`since` 向上取整、`until` 向下取整（`ceil_ms` / `floor_ms`，“m ≥ since 当且仅当 m ≥ ceil_ms(since)”），不限的一侧用远超真实时间戳的哨兵，SQL 一律写成 `ts_ms BETWEEN ? AND ?`（`data/repos/_samples.ms_range`）。时刻类边界（打点、基线这类“事件发生的时刻”）与样本同一取整规则：`core/history_query` 先经 `normalize_ms`（即按 `to_ms` 四舍五入后的时刻）再作查询边界，因此与打点同一时刻采集的样本一定算打点之后，早于打点 1 毫秒以上的一定算之前。
- `ts_ms` 只在 data 层出现（`tests/test_storage_v5.py` 守护）；`ui` 与 `core` 不出现 `since_iso` 字符串参数，门面旧方法的 `since_iso` 仅为兼容保留，内部转换。

### 7.3 主题 themeMode 禁止重定义

`app_config.AppConfig` 直接复用 `QConfig` 基类内置的 `themeMode`，**不得**重新声明同名 `ConfigItem`。`qfluentwidgets.setTheme()` 操作模块级单例 `qconfig.themeMode`，`QConfig.set()` 又用 `is` 身份比较判断是否主题项；重定义会产生两个互不联动的对象，表现为“设置页选了深色没生效”“重启后主题还原”。启动时应用主题要传原始配置值 `cfg.get(cfg.themeMode)`（可能是 AUTO），不能传解析后的 `qconfig.theme`，否则会把“跟随系统”静默覆写成具体主题。

### 7.4 qfluentwidgets 特殊行为统一见 `qfw_compat`

qfluentwidgets 控件有几处与 Qt 原生控件不同的行为（`addItem` 加入第一项时自动选中并发信号、`clear()` 不恢复占位文字、`setCurrentIndex` 的越界与 -1 处理、`MessageBoxBase` 默认焦点、`SwitchSettingCard` 英文文案、`setMinimumHeight` 覆盖布局最小尺寸等）。清单与处理方式只在 `ui/widgets/qfw_compat.py` 的模块说明里维护一份：能封装的已封装在 `TaskSelector`、`SearchableCombo`、`InputDialogBase`、`CnSwitchSettingCard` 中，页面与新控件直接用这些封装，不再各自打补丁；新发现的特殊行为补进该清单并加测试（`tests/test_qfw_compat.py`）。下拉项一律用 userData 携带 `task_id` / `metric_type` / 进程目标，文本只用于显示。

### 7.5 showEvent 联动

页面之间没有直接的数据推送，新建任务后分析页的任务列表靠 `showEvent` 在每次切入时重新加载（同时启动 `HistoryAutoRefresh`，`hideEvent` 停止并作废在途查询）；唯一的跨页推送是打点：manager 的 `markers_changed` 让监控卡片刷新刻度、分析页静默重查。页面开着期间，运行中任务的下拉时长由 `TaskOptionsModel.refresh_running` 算出变化项、`TaskSelector.update_option` 原地改写，不重建列表，以免打断用户当前的选择与图表视图。新增依赖其他页面数据的页面时沿用此机制，并注意长耗时操作（如导出）期间用户切走再切回会重复触发 `showEvent`，需保证控件状态幂等。

### 7.6 数据库维护互斥

清理/压缩数据库与运行中任务、导出互斥，维护锁只经 `MaintenanceService` 占用与释放（底层是 `manager.begin_maintenance` / `end_maintenance`，页面不直接调用）。设置页用**两段式**：点击后先做只读预检（有运行中任务或导出时直接提示，不弹确认）→ 确认 → 在**界面线程**调用 `maintenance.begin()`（已有维护、有运行中任务或导出时抛 `MaintenanceBusy(reason)`，按 reason 提示，不启动线程）→ 以 `CleanupWorker(..., already_locked=True)` 启动后台线程（线程内 `cleanup_and_vacuum(days, already_locked=True)` 不占也不放锁）→ 线程 `finished`（无论成功、失败）后在界面线程 `maintenance.end()`。开始监控、开始导出的判断同样在界面线程，与占锁串行，因此不存在“确认之后、后台线程真正占锁之前”任务或导出趁机开始的窗口。维护期间 `create_task` / `start_task` / `begin_export` 被拒绝。不在界面上使用时，`cleanup_and_vacuum(days)` 自行占锁并在结束时释放。设置页“重建汇总”（`RebuildRollupsWorker` → `MaintenanceService.rebuild_rollups(already_locked=True)`）与清理同样两段式占锁，二者互斥；重算在一个事务里，失败整体回滚、原汇总不变。分析页的导出启动线程前 `begin_export()`，线程 `finished` 时 `end_export()`（每个 worker 各注销一次，与视图模型引用是否已被替换无关）。删除任务数据（`delete_task_data`）对运行中任务同样拒绝。

**存储健康作业的互斥**：存储守卫的 -wal 兜底 checkpoint 与 quick_check 不占维护锁（占了会让用户在“压缩数据库”灰着时找不到原因，且挡住新任务），而是经 `MaintenanceService.begin_storage_job()` / `end_storage_job()` 登记一个计数：登记时维护正在进行就返回 `False`、守卫跳过本轮；登记期间 `begin()` 抛 `MaintenanceBusy(BUSY_STORAGE_JOB_RUNNING)`（设置页提示“数据库正在做例行整理，请几秒后再试”）。因此清理 / 压缩 / 重建汇总与这两项后台作业永不同时碰库；与监控任务、导出不互斥（checkpoint 的忙等待上限只有 1 秒，宁可退到 PASSIVE，也不让采集线程跟着等）。

### 7.7 日志与异常兜底

`app.bootstrap.run()` 最早处（解析路径之后）调用 `setup_logging`（根 logger 挂 `RotatingFileHandler`，5MB x 5）与 `install_excepthook`（未捕获异常记日志，并在主线程弹窗提示日志位置；`faulthandler` 把致命信号写入 `crash.log`；安装前若 `crash.log` 超过 1 MB 先轮转为 `crash.log.1`（覆盖旧的 .1），轮转失败只记日志）。Windows 上 faulthandler 会把辅助功能 / UI 自动化工具触发的首次机会 COM 异常（0x8001010d、0x80040155）也记成 “Windows fatal exception”，进程其实并未崩溃，faulthandler 又无法按异常码过滤：判断是否真的崩溃看进程是否退出、`app.log` 是否有“未捕获异常”，`crash.log` 里这两类条目可忽略。工作线程中的异常只记日志、不打断采集。各模块一律用 `logging.getLogger(__name__)`。数据库失败的处理见 5.3 节：门面旧方法返回 `False` / 空结果并记日志；仓储抛 `StorageError`，由调用方转成界面上的失败提示。

### 7.8 其他约定

- 组合根构造并注入的 `Database` 是全应用唯一实例；`MonitorWorker` 的 `db` 必须注入（缺省抛 `TypeError`），`ui` / `core` 不得自建 `Database()`（`tests/test_layering.py` 守护）。
- 监控任务停止后线程对象不可复用，`start_task` 拒绝已结束的任务；“重新监控”通过新建任务实现。
- 耗时操作不放 UI 线程；UI 写库一律经 manager，读查询可走注入的 `Database`。
- 不可撤销操作（删除任务数据、清理数据库）的确认框统一经 `services.dialogs.confirm`，生产实现为 `ui/components/confirm.py` 的 `DestructiveConfirmBox`：按钮文案中文（如“删除”/“清理”与“取消”），显示后焦点在“取消”。

### 7.9 可观测性

- **采集周期统计**（`core/cycle_stats.py`，不依赖 Qt）：`MonitorWorker` 每个周期喂一次数——调度延迟、采集耗时、写库耗时，三个定长 10 桶直方图（上界 1 / 2 / 5 / 10 / 20 / 50 / 100 / 200 / 500 ms + 溢出桶），内存固定、运行多久都不增长，另有计划 / 完成 / 跳过周期数。量耗时用 `clock.perf_counter()`（`SystemClock` 提供；Windows 上 `time.monotonic` 分辨率约 15.6 ms，量不出 1 ms 级耗时；假时钟没有该方法时退回 `monotonic()`，测试照样能用拨动时钟制造耗时）。口径：调度延迟 = 实际醒来时刻 − 计划截止时刻（单调时钟）；落后超过一个周期时调度器重置截止时间、不补采，跳过的周期数计入 missed，延迟只记相对最近一个网格点的余量；计划周期数按“活动段”累计（每段从首采或恢复时刻到暂停或停止，段内网格点数 = floor(时长 / 周期) + 1，暂停段不算）；完成周期数 = 采集调用正常返回的周期（含进程已退出、全部指标不可用），采集抛异常的周期既不算完成也不算跳过；p95 取直方图累计首次达到 95% 的桶的上界（只会偏大），落在溢出桶时取观测到的最大值。收尾（`_teardown`，在发出 `task_stopped` 之前）经 `TaskRepo.save_quality` 写入 `tasks` 的 `planned_cycles` / `done_cycles` / `missed_cycles` / `lag_p95_ms` / `collect_p95_ms` 五列；写库 p95 只在 `QualityStats` 与日志里，没有对应的列。运行中经 `quality_snapshot()` → `TaskInfo.quality` 给界面与 `pmctl status`；`core.report.quality_text` 把它写成一句话（如“采集完成率 99.8%（12,345 / 12,370 周期，调度延迟 p95 12 ms）”，有缺采时最多显示 99.9%），进报告元信息网格与 CSV 元数据行。
- **慢操作告警**（`data/repos/_guard.storage_errors`）：每个仓储操作都包在它里面，顺带量一次耗时，超过 500 ms 记一条 WARNING（操作名 + 耗时）；同一种操作（`action_kind`：第一个空白或左括号之前的部分，如“保存任务 <id>”归为“保存任务”）60 秒内只记一次，被抑制的次数在下一条里一并报出；流式读取（耗时里含调用方消费数据的时间）不计时；告警失败不改变操作本身的结果。
- **自身监控**（`core/self_monitor.py`）：界面线程的 `QTimer` 每 60 秒调一次 `tick()`（启动时马上采一次），采本进程的私有字节 / 句柄 / 线程 / GDI / USER，存入 1440 项（24 小时）的定长环形缓冲；`verdict()` 对最近 N 小时（默认 6）的私有字节做与分析页同一套的趋势判定，回答“监控工具自己有没有在泄漏”。有窗口与无窗口模式都启动，组合根把它与定时器挂在 `AppContext` 上。
- **界面卡死看门狗**（`utils/crash_handler.install_ui_watchdog`，只在有窗口模式、窗口显示后安装）：界面线程的 `QTimer` 每 `min(1 秒, 阈值/3)`（不低于 50 ms）续期一次 `faulthandler.dump_traceback_later(阈值, repeat=False, exit=False)`（先 `cancel` 再重设）；界面线程被阻塞超过阈值（默认 10 秒）时续期停止，`faulthandler` 的后台线程把全部线程的栈写进 `crash.log`（以 `Timeout (0:00:10)!` 开头），进程不退出，同一次卡死只写一次，恢复后下一次续期重新布防。`faulthandler` 的定时转储全进程只有一份，所以看门狗也只有一个（再次安装先停旧的）；续期与停止都在界面线程；没有可写的 `crash.log` 或不在界面线程时不安装、只记日志。真退出收尾前必须先停（见第 6 节）。
- **存储健康**（`core/storage_guard.py`，设计与阈值见 2 节目录表）：磁盘空间、-wal 大小与 quick_check 的结果都写日志（低空间 WARNING、暂停 WARNING、checkpoint 前后大小与耗时、quick_check 耗时与结论；未通过为 ERROR）；quick_check 未通过时主窗口与设置页“数据”分组各提示一次（再次检查结果不重复提示），提示里引导用户“复制诊断信息”并联系作者。实测 quick_check 耗时：1.28M 行 v5 库（25 MB）约 0.13 秒、2.99M 行（58 MB）约 0.32 秒、旧版 100 万行库（158 MB）约 0.38 秒（热缓存、笔记本 SSD）；后台线程里跑，随时可中断。
- **诊断信息与诊断包**（`core/diagnostics.py`，设置页“数据”分组的“复制诊断信息 / 导出诊断包”）：`collect_diagnostics` 给出一段中文纯文本：版本与运行环境、数据目录、数据库（大小、结构版本、meta）、任务数与各任务数据质量（最多 20 个）、快照中心统计、自身监控最近值与判定、界面看门狗、崩溃日志大小、最近 50 行日志；`write_diagnostic_bundle` 打成 zip = 上述文本 + `app.log` 最近 2 MB + `crash.log`（及 `crash.log.1`）+ `config.json`，在 `DiagnosticBundleWorker` 后台线程执行。部件（paths / db / manager / hub / self_monitor / watchdog）鸭子类型、全部可选，任何一节取值失败只在该节写“读取失败: 原因”。
- **真实 24 小时浸泡的工具链**（`tools/soak_probe.py` + `tools/soak_verdict.py` + `tools/soak_run.ps1`，被测负载 `tests/fixtures/soak_target.py`；步骤与产物见 `doc小时浸泡手册.md`）：探针是独立进程，只用标准库与 psutil，IPC 只用 `core.ipc.client`，不依赖采集、数据库代码，所以本工具自身的问题不会污染记录。每 10 秒向输出目录追加三份 CSV（每行即时 flush，已有文件时追加）：`soak_probe.csv`（本工具的私有字节 / 工作集 / 句柄 / GDI / USER / 线程 / CPU，`alive=0` 表示那一刻工具不在）、`soak_tasks.csv`（经 `status` 读到的各任务 `planned_cycles` / `done_cycles` / `missed_cycles`，即上文采集周期统计的累计值）、`soak_events.csv`（`target_exited` / `target_found` / `ipc_lost` 等）；列名与顺序是探针与判定之间的契约，由 `tests/test_soak_probe.py` 守护。`soak_verdict` 取记录的最后 N 小时（缺省 20）做五项检查：覆盖、私有字节（`judge` 非“持续上涨”且增长 ≤ 30 MB，增长取拟合增量与首尾 5% 均值差的较大者）、句柄 / GDI / USER / 线程（非“持续上涨”，小容差内只提示）、各任务采样完成率 ≥ 99.5%、工具未退出；趋势判定用 `core.self_monitor.fit_input` 组装输入，与 `SelfMonitor.verdict()` 同口径。负载 `soak_target.py` 的 `restart` 模式由 `--supervise` 的监督进程拉起新进程，因为 `ProcessRestartFinder` 不接旧进程自己派生的子进程。
- **`--startup-trace`**：见 2.4 节。

### 7.10 配色令牌与主题跟随

- **颜色只在 `ui/theme_tokens.py` 定义**：每个令牌是（浅色, 深色）二元组，值为 `#rrggbb` 或样式表可用的 `rgba(r, g, b, a)`。图表、迷你图、判定胶囊、任务卡片状态胶囊、打点徽标、空洞阴影、选中色条各按当前主题取用，同一种语义（“在涨”“注意”“数据”）不在不同控件里各写一份；图表专用的组合（轴线、十字线、min/max 带等）在 `ui/chart_theme.py`，由令牌派生。
- **图表背景一律透明**，由所在卡片（或概览条下的窗口底）提供底色：写死一个“接近卡片”的底色在 Mica 与悬停下都会露出一块色差明显的矩形（原来的 `#2b2b2b` 已删除）。`chart_palette` 里的 `background` 只用于导出图片这类需要不透明底的场合。
- **对比度由测试守护**：底色令牌 `WINDOW`（窗口底）/ `SURFACE`（卡片常态，窗口底叠半透明白后的合成色）/ `SURFACE_HOVER`（卡片悬停）只作对比度参照；`ui/color_contrast.py` 是 WCAG 2.x 纯函数（带透明度的前景先按 alpha 合成到底色再算），`tests/test_color_contrast.py` 对 `SURFACE` 与 `SURFACE_HOVER` 两者逐项断言：文字 ≥ 4.5:1，图形元素（曲线、轴线、竖线、色条）≥ 3:1。新增或调整颜色一律改令牌并让该测试通过。
- **跟随系统**（`ui/theme_follow.py`）：qfluentwidgets 只在 `setTheme(AUTO)` 那一刻读一次系统主题；它自带的 `SystemThemeListener` 在 Windows 上阻塞在 `darkdetect.listener` 里、没有可靠的退出方式，会卡住退出路径，所以改用主线程 `QTimer` 每 5 秒轮询一次（`darkdetect.isDark()`，读一次注册表，开销可忽略）：只在配置为 AUTO 且解析结果变化时改写内存中的主题（不写配置，配置仍是“跟随系统”）并发 `qconfig.themeChanged(Theme.AUTO)`，已打开的图表、胶囊、卡片据此重新取色。主窗口构造时创建并 `start()` `theme_watcher`，真退出收尾前 `stop()`。

## 8. 测试与 CI

- 运行（两种用法）：**本地快速集** `python -m pytest tests/`（`addopts` 默认排除 perf / soak / slow，开发时日常用，单进程约 3.5~4 分钟，用例数与清单用 `pytest --collect-only -q` 查看，本文不列清单；机器核数多时用 `python tests/run_parallel.py` 并行，见下）；**CI 完整集** `python -m pytest tests/ -m "not perf and not soak and not gui_real" --durations=25`（含 slow，发版前与 CI 用）。只看慢用例 `-m slow`，想连 slow 一起在本地跑用 `-m "slow or not slow"`。命令行再给 `-m` 会覆盖 `addopts` 里的默认值，所以完整集的表达式里不要漏写 perf / soak。
- `pytest.ini` 配置 `testpaths = tests`，注册 `perf` / `soak` / `slow` / `gui_real` / `real_exit_probe` 五个 marker，并以 `addopts = -m "not perf and not soak and not slow"` 默认排除性能基准、加速浸泡与慢用例（显式 `-m perf` / `-m soak` / `-m slow` 选择；命令行再给 `-m` 会覆盖默认值）。`tests/conftest.py` 默认把 `QT_QPA_PLATFORM` 设为 `offscreen`，并通过自动 fixture 只设置环境变量 `PROCESS_MONITOR_DATA_DIR` 指向临时目录（不覆写任何路径常量，路径都由 `AppPaths.resolve()` 在使用时解析），**测试不得触碰开发机的 `data\`**；需要显式注入路径的用例用 `app_paths` fixture 拿到本用例的 `AppPaths`。另有会话级 `QApplication`、迁移记录与应用配置复位（`_reset_app_config` 遍历 `AppConfig` 类上声明的全部 `ConfigItem` 回落默认值，新增配置项自动被覆盖，不会漏复位），以及自动 fixture `_dispose_leaked_widgets`：每个用例结束后释放它留下的、仍存活的无父顶层控件（页面、主窗口、卡片、图表）。原因：无父顶层控件不会随 Python 引用消失而析构，残留的设置页把 `qconfig.themeChanged` 连到 `setTheme`，之后每次切主题都多发一次信号（还会把主题模式改写成具体主题），qfluentwidgets 的样式表管理器给每个残留控件重刷样式表使切换越来越慢，残留控件的定时器也越积越多。只释放类所在模块以 `ui.` / `tests.` 开头的控件：pyqtgraph 等第三方库自己持有的无父菜单与面板由其 Python 对象管理生命周期，从 C++ 侧提前删掉会在宿主析构时直接崩溃；仍有子 `QThread` 在运行的控件先请求结束并等 3 秒，等不到就不释放（否则线程对象随父对象析构会致命中止）、只发警告；用例开始前已存在的顶层控件不动，有父对象的弹出窗口随父对象一起释放。新增涉及路径的模块时，从注入的 `AppPaths` 取路径，不新增模块级路径常量。
- **测试时长控制**（默认集改造前 4,217 个用例单进程 399.5 秒，现 4,375 个用例约 213~220 秒（3.5~3.7 分钟）；完整集（含 slow）约 312 秒；并行 `tests/run_parallel.py` 6 份约 63 秒。目标是默认集 ≤ 150 秒，单进程尚未达到）。耗时不集中在少数用例，而是平摊在“每个用例都建一个窗口 / 页面 / 库”上（主窗口构造约 0.3 秒、分析页约 0.15 秒、每次新连接的 PRAGMA 与提交约 1 毫秒），做过的提速都不改断言语义：
  - **会话级共享的准备**：`db` fixture 由会话级模板库（`_template_db_file`，建一次空库后关闭）复制而来，约 3 毫秒，比逐用例建库（约 20 毫秒）快得多；需要“全新建库”过程本身的用例（迁移报告 `created` 等）自己 `Database(新路径)`。`tmp_path` 与数据目录改用 `tempfile.mkdtemp` 的随机名（根在会话基础目录下，随 pytest 的保留策略清理）：pytest 自带的带序号目录每建一个都要扫描同级全部已有目录，目录数随用例数增长而平方级变慢，4000 多个用例光建目录就 30 多秒。
  - **图表菜单残留**：pyqtgraph 的 `PlotItem` 构造时无条件建约 30 个无父 `QMenu`（`ctrlMenu`），只在 `PlotItem.close()` 释放；控件被删后它们仍是应用的顶层控件，全量里积到上千个，让每个用例的 `topLevelWidgets()` / `processEvents()` 越来越慢（pytest-qt 每个用例前后调 5 次 `processEvents`）。`tests/helpers.dispose_widget` 在删除控件前先调 `release_plot_menus` 释放它们；`conftest` 里 `PlotItem` 默认不再建 `ViewBoxMenu`（测试不依赖 pyqtgraph 自带的右键菜单）；`_dispose_leaked_widgets` 先按类所在模块筛本项目的控件再取指针。
  - **轮询间隔**：`helpers.poll_until` / `process_events_until` 的睡眠从 10 毫秒降到 2 毫秒，条件满足后的平均多等从约 5 毫秒降到约 1 毫秒（全量里这类等待有几千次）。
  - **缩短真实等待**：`test_ui_watchdog`（转储阈值 1 秒改 0.3 秒、续期窗口 3 秒改 1.5 秒）、`test_shutdown_coordinator`（总预算 2 秒改 0.6 秒，仍远小于单项超时累加）、`test_snapshot_hub`（周期 0.25 秒改 0.2 秒、跑 1.5 秒）、`test_monitor_page_flow` 收尾等待 100 毫秒改 60 毫秒（补全菜单的 50 毫秒定时器）。
  - **慢用例标 `slow`**（默认本地排除、CI 完整集运行）：判断标准是单独跑也超过 2 秒（真实进程树整机枚举、多进程并发等少数 1.6 秒左右的也一并标），且必须有快速替身覆盖同一逻辑，没有就补一个快速版本。清单与替身：

    | slow 用例 | 约耗时 | 快速替身 |

  - **用例超时看门狗**（`tests/watchdog.py`，不依赖 pytest-timeout）：根 `conftest` 引入它的 `pytest_configure` 钩子与自动 fixture，每个用例开始时 `faulthandler.dump_traceback_later(60, exit=True)`、结束时取消；用例卡住超过限定秒数，faulthandler 的 C 线程（不需要 GIL）把全部线程的栈写到会话开始时复制的标准错误副本里（避开 pytest 的输出捕获），随后以退出码 1 结束进程——CI 不会被一个卡死的用例拖到作业超时，也看得到卡在哪。环境变量 `PM_TEST_TIMEOUT_S` 调限时（缺省 60，`0` 关闭）、`PM_TEST_TIMEOUT_EXIT=0` 改为只转储不退出；带 perf / soak / gui_real 的用例放宽 10 倍、slow 放宽 3 倍。`faulthandler` 全进程只有一个定时器，`test_ui_watchdog` 里真实安装的界面看门狗会顶掉它（用例内不再受 60 秒保护），属已知取舍。自测在 `test_test_watchdog.py`：临时项目里放一个会睡 30 秒的用例，断言超时后打出主线程与辅助线程的栈并很快退出。
  - **本地并行**（`tests/run_parallel.py`，只用标准库）：把测试文件按上次耗时均衡分成 N 份（缺省按核数一半、最多 6），每份起独立的 pytest 子进程同时跑并汇总；每个进程各有 QApplication、临时目录与数据目录，互不干扰。多余的参数原样传给 pytest（如 `-m "not perf and not soak and not gui_real"` 跑完整集）。机器同时很忙时带真实时序的少数用例会偶发超时，判定“有没有偶发失败”仍以单进程为准。
- 数据目录也可由命令行 `--data-dir`、环境变量 `PROCESS_MONITOR_DATA_DIR` 或便携标志指定（见第 2 节），便于便携运行与手工验证。
- 测试分层：数据层与迁移（含旧库构造）、采集与调度鲁棒性、导出纯函数与线程、更新校验、页面流程与界面契约（布局、排版、格式化）、单实例、日志与隔离；`tests/e2e/` 是 offscreen 下的全链路冒烟（标 `slow`：本地快速集不跑，CI 完整集与发版前运行；选进程开始 → 托盘打“基线”、快捷键入口打两轮 → 停止 → 分析页判定摘要与打点区间 → 导出报告三件套 → 设置页 → 带运行中任务关窗，退出协调器全部收尾）。涉及 GUI 的用例用 offscreen，不弹窗口。
- **真实退出路径的事件循环隔离**：e2e 冒烟用例会走真实退出路径（收尾后调用 `QApplication.quit()`），而测试进程从不运行主事件循环，Qt 会一直记着“已退出”，之后同进程里所有新建的局部 `QEventLoop.exec_()` 都立即返回，`qtbot.waitSignal` 等不到后台线程信号。`tests/e2e/conftest.py` 的 autouse fixture 在每个用例后调 `tests/helpers.reset_qt_quit_state()` 清除（`qt_quit_pending()` 可检测是否有残留）；`tests/e2e/test_quit_isolation.py` 先制造污染、再检查后一个用例看到的是干净状态，去掉该 fixture 必失败。 根 `conftest` 另有 autouse fixture `_no_stale_quit_state` 作全局兜底：任何用例收尾时若留下该状态，就清除它并让留下它的那个用例报错（而不是让几个文件之后的 `waitSignal` 莫名超时）；窗口收尾用 `tests/helpers.dispose_widget`，不要对真主窗口调 `close()`（`test_marker_undo_ui.py` 的窗口夹具曾因此污染 `test_update_fake_release.py`）。
- 界面层的测试策略：
  - **业务规则在无控件单元测试里覆盖**：`test_history_vm.py` / `test_analysis_vm.py`（选择语义、锚点、过期丢弃、多指标批次、空状态与错误）、`test_monitor_presenter.py`（用假表单/假面板覆盖重复 PID、停止确认、打点序列、同配置再测、错误去重；等待进程启动另见 `test_wait_for_process.py`）、`test_task_options_model.py`、`test_history_query.py`、`test_analysis_trend.py` / `test_analysis_intervals.py` / `test_analysis_series.py`、`test_report.py`；全局快捷键 `test_hotkey.py` 只用假后端与假消息；控件各有自己的测试（`test_summary_table.py`、`test_interval_table.py`、`test_chart_view.py`、`test_chart_view_extensions.py`、`test_sample_table.py`、`test_task_selector.py`、`test_searchable_combo.py`、`test_process_picker.py`、`test_new_task_form.py`、`test_task_board.py`、`test_page_scaffold.py`、`test_qfw_compat.py`）；响应式布局：`test_layout_breakpoints.py`（档位边界、回滞、广播器、高 DPI 取整扫描）、`test_responsive_layout.py`（各档位摘要表可见列与用户勾选的往返、小倍数列数、工具条下拉、结论条分行、主窗口 1280 无横向滚动 / 800 摘要表不截字 / compact 收侧栏、`QT_SCALE_FACTOR=1.25 / 1.5` 子进程冒烟）。
  - **页面测试只测连线与关键可见状态**（`test_*_page_flow.py`、`test_*_ui_contract.py`）：经公开控件模拟用户操作（如对 `task_selector.combo` 设下标），断言命令确实发出、可见状态正确，尽量不碰私有成员；分析页页面测试注入同步查询执行器（`tests/helpers.py` 的 `SyncHistoryRunner` / `ManualHistoryRunner`）与立即执行的 defer。

## 9. 打包与发布链

```
改版本号（config.APP_VERSION）→ 全量测试 → build\build.bat → GitHub Release（上传安装包）
```

- **版本号**：唯一来源是 `config.APP_VERSION`（现为 `2.0.0-beta.1`）。预发布期间带后缀 `-beta.N` / `-rc.N`，正式发布时改为 `X.Y.Z`；读取方是窗口标题、设置页“关于与更新”、更新检查（按 SemVer 比较，带后缀的低于同号正式版）、库 meta 的写入版本（`created_by_version` / `last_writer_version`；只读判定只取发布号部分，见 2.4 节第 7 步）、`build/gen_version_info.py` 与 `build.bat`。`setup.iss` 不写默认版本号：`MyAppVersion` 必须由 `build.bat` 以 `/DMyAppVersion=<版本>` 传入，未传入时预处理阶段 `#error` 中止编译，安装包版本因此不会与程序脱节。
- **打包自检与安装包冒烟**：`app/self_test.py`（`--self-test --data-dir <空目录>`，`app.bootstrap.run` 最开头分流，不走常规启动顺序）按固定步骤走一遍迁移 golden 旧库（`ProcessMonitor.spec` 的 datas 带入 `_internal\selftest\v1.4.1_v1.db.gz`）→ 主窗口 → 进程列表 → 监控自身 3 点 → 导出 → pmctl ping → 真退出路径，失败退出码 5、参数不合规 2；`build/run_self_test.py` 带超时地运行它（`build.bat` 与冒烟脚本共用）。`build/installer_smoke.ps1` 用 1.4.1 旧安装包验证覆盖升级（文件清单与 dist 一致、`[InstallDelete]` 清 `_internal`、迁移、`.bak_v1`、`update_prefs.json` 被导入并删除、正常退出、卸载保留数据）；`.github/workflows/release.yml` 只构建与冒烟，不发布。安装包文件名由 `setup.iss` 直接定为 `Windows_v{版本}_Setup.exe`，打包前清空 `dist\`。详见 `build/README_打包说明.md`。
- `build\build.bat` 是无人值守一键脚本：读取版本号 → 生成 `version_info.txt` → PyInstaller 以 onedir 模式打包（`ProcessMonitor.spec`）→ 校验产物体积/文件数并运行打包自检 → Inno Setup（`setup.iss`）编译安装包 → 产出 `dist\installer\Windows_v{版本}_Setup.exe`（Release 资产名）。
- **文件版本号**：`build/gen_version_info.py` 的 `_to_version_tuple` 把 `config.APP_VERSION` 映射为 Windows 版本资源的 4 段数字，第 4 段表示发布阶段，使同一 `X.Y.Z` 下 beta < rc < 正式版，与 `utils/version.compare_version` 的 SemVer 优先级同序：`X.Y.Z` → `(X, Y, Z, 100)`，`X.Y.Z-beta.N` → `(X, Y, Z, N)`，`X.Y.Z-rc.N` → `(X, Y, Z, 50 + N)`，其他预发布标签取 0，`+构建元数据` 忽略；N ≥ 50 会撞号、任一段超出 0~65535 时抛 `ValueError` 中止打包。`FileVersion` / `ProductVersion` 字符串保留原文。
- **版本比较**：自动更新按 SemVer 2.0 比较版本优先级（`utils/version.compare_version`，`core.update_checker` 原样再导出）：去掉 v/V 前缀与 `+构建元数据`；主版本段相同时带预发布的低于不带的；预发布标识符逐段比较（数字按数值、字母数字按 ASCII、数字低于字母数字、前缀相同时段少者小）；任何输入都不抛异常。因此 beta 用户能收到同号正式版的更新提示。
- **安装器探测运行中的程序**：`setup.iss` 写 `AppMutex=ProcessMonitor.Running,Global\ProcessMonitor.Running`，安装与卸载启动时若任一互斥量存在即提示先关闭程序。名称须与 `app/single_instance.py` 的 `INSTALLER_MUTEX_NAME` 一致（`tests/test_single_instance.py` 锁定）；Inno Setup 只按所列名称逐个检查、不自动补查 `Global\`，故两个都列出：不带前缀的名称落在当前会话（即程序创建的 `Local\` 名），`Global\` 名覆盖其他会话里运行的实例。
- **`pmctl.exe`**：`ProcessMonitor.spec` 里第二组 `Analysis` / `PYZ` / `EXE` 生成它（入口根目录 `pmctl.py`，`console=True` 以便在 cmd / CI 里输出文字与退出码），与主程序共用同一个 `COLLECT`，产物在 `dist\进程监控助手\` 下与主程序并列；`setup.iss` 的 `dist\进程监控助手\*` 递归规则自动带上它，安装包无需改动。它的分析单独进行，`excludes` 去掉 PyQt5 / psutil / qfluentwidgets / pyqtgraph / numpy / ui / data / sqlite3 等，只带标准库与 `core.ipc.client` / `core.ipc.protocol`、`utils.instance_name`、`app.paths`、`config`——所以 `pmctl.py` 与这些模块不得导入 PyQt5 / psutil / ui（`core/process_launcher.py` 顶层也只导入标准库，因 pmctl 复用其 `split_args`）。pmctl 拉起无窗口实例时找的是它同目录的主程序 `config.APP_NAME + '.exe'`。打包后冒烟（手动，见打包文档）：`pmctl.exe --data-dir %TEMP%\pm_smoke ping`（应自动拉起并打印版本）与 `… quit`，都应退出码 0、任务管理器里不残留进程。
- **发布校验 `build/verify_release.py`**（只用标准库）：发版前检查草稿、发版后复核 GitHub Release，逐项输出中文结果，全部通过退出码 0，有失败 1，参数错误 2；`--tag` 必填，`--token` 缺省读 `GITHUB_TOKEN`，`--allow-draft` 允许草稿，`--local-setup` 核对本地安装包的摘要与大小，`--release-json` / `--latest-json` 用保存的 API 返回体离线检查。规则：(a) 版本四处一致（`config.APP_VERSION`、tag 去 `v`、`CHANGELOG.md` 顶部版本段、Release 名称；预发布期间 CHANGELOG 顶部可以仍是“未发布”）；(b) 恰好一个文件名含 `setup`（不区分大小写）的 `.exe` 资产，名为 ASCII 的 `Windows_v{版本}_Setup.exe`；(c) 该资产带 `sha256:` 摘要，给了 `--local-setup` 时摘要与大小都与本地一致；(d) `-beta.N` / `-rc.N` 必须是 prerelease，正式版必须非 prerelease 且非 draft；(e) 正文不超过 60 行，正式版含“升级须知”；(f) tag 形如 `vX.Y.Z` / `vX.Y.Z-beta.N` / `vX.Y.Z-rc.N`；(g) `releases/latest`：正式版发布后应指向本 tag，预发布不得是 latest。规则来自更新通道契约：已安装的 1.4.1 只取第一个文件名含 setup 的 `.exe`、不校验 digest，`releases/latest` 不返回 prerelease 与 draft，2.x 更新器缺 digest 就拒绝自动安装；契约由 `tests/test_update_contract_v141.py` 与冻结副本 `tests/fixtures/frozen_v1_4_1/update_checker.py` 钉住（见第 8 节）。GA 发布后 1 小时内用真实 1.4.1 走一遍自动更新的步骤见打包文档“发布校验”。
- 打包用 `requirements-lock.txt` 复现验证过的精确依赖；`requirements.txt` 只声明宽松下限供开发。
- 自动更新依赖 Release 资产的 `digest`（`sha256:`）：发布时上传的资产由 GitHub 生成摘要，应用据此校验；没有摘要时用户只能手动下载。
- 安装目录与数据目录分离（默认数据在 `%LOCALAPPDATA%`；便携模式例外，数据在安装目录下的 `data\`），覆盖安装与卸载重装不影响历史数据。
- 不提交 `build/` 下的临时产物、`dist/`、DLL/EXE、数据库；详细步骤、常见问题见 `build/README_打包说明.md`。
