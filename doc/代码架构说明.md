## 1. 项目定位与技术栈

**进程监控助手（ProcessMonitor）** 是面向软件测试人员的 Windows 桌面应用：周期性采集指定进程的 27 项性能指标（内存 11 / CPU 4 / 系统资源 6 / IO 6），实时展示、SQLite 持久化、历史图表回放、CSV 导出，核心场景是用“基线—打点—变化量/增长速度”排查内存、句柄、GDI/USER 对象和线程泄漏。

| 技术 | 用途 |
|------|------|
| Python 3.8+（CI 与发布统一 3.11） | 语言 |
| PyQt5 + PyQt-Fluent-Widgets | 界面与 Fluent 控件、QConfig 用户配置体系 |
| psutil（+ ctypes 调 `user32.GetGuiResources`） | 进程指标采集 |
| pyqtgraph | 历史图表（日期轴、十字线、打点竖线、导出） |
| SQLite（标准库 `sqlite3`，WAL） | 持久化 |
| urllib（标准库） | 自动更新检查与下载 |
| PyInstaller（onedir）+ Inno Setup | 打包与安装包 |
| pytest | 自动化测试 |

仅面向 Windows（句柄/GDI/USER、托盘、命名管道单实例均依赖 Windows）。最多同时运行 5 个任务（`config.MAX_MONITOR_TASKS`）。

## 2. 目录与分层

四层单向依赖：**UI → Core → Data → Utils**，另有入口与配置。跨层通信一律走 Qt 信号槽；UI 不绕过 core 直接写库（读查询允许直接走注入的 `Database`）。

```
main.py                入口：日志/异常钩子 → QApplication → 单实例 → 配置/主题 → MainWindow
config.py              路径、版本、常量（缺省值来源）；支持环境变量 PROCESS_MONITOR_DATA_DIR 覆盖数据目录
app_config.py          用户偏好（QConfig 体系，JSON 落盘）：主题、默认周期、保留天数、托盘、上次所选指标

ui/                    界面层
  main_window.py         FluentWindow：五页导航、托盘、关窗确认、更新提示、页面间跳转中转
  pages/                 monitor / history / export / setting / about 五个页面
  components/            task_card（监控任务卡片）、sparkline（趋势图与等跨度抽稀）、chart_axes（图表坐标轴）、
                         dialogs（打点输入、关窗三选）、metric_selector（指标多选）、spinbox_setting_card
  formatting.py          界面文案纯函数（时长、任务下拉文本、统计条文本、默认导出文件名），不依赖 Qt 控件
  typography.py          应用级排版系统（字体栈、字号 token、语义标签）
  chart_theme.py         图表配色，随深浅主题切换

core/                  核心业务层
  monitor_manager.py     单例；任务创建/启停/暂停/移除、打点、数据库维护互斥、转发任务信号
  monitor_task.py        单个任务的 QThread：调度、采集、缓冲落库、收尾
  process_collector.py   psutil 封装：批量采集（oneshot）、不可用指标记录、GDI/USER 采集、PID 复用检测
  export.py              导出纯函数：表头、宽表透视、打点列
  export_worker.py       CSV 导出线程：流式读取、写临时文件、成功后替换
  history_refresh_worker.py  历史页自动刷新线程：后台执行只读查询，结果打包为 dataclass 发回主线程
  update_checker.py      GitHub Release 检查线程与下载线程（域名白名单 + SHA-256 校验）

data/                  数据层
  database.py            Database：建表、迁移、读写、聚合、校正、清理、维护
  models.py              MonitorTask / DataPoint / Marker 三个 dataclass

utils/                 工具层
  metrics.py             27 个指标的键、中文名、单位、说明、分类、预设、格式化与旧键别名
  logger.py              日志（RotatingFileHandler，5MB x 5）
  crash_handler.py       未捕获异常兜底与 faulthandler 崩溃日志
  thread_utils.py        shutdown_thread：先取消再限时等待

tests/                 pytest 用例与 e2e 冒烟；conftest.py 提供数据目录隔离等公共 fixture
build/                 打包脚本、spec、Inno Setup 脚本（说明见 build/README_打包说明.md）
doc/                   PRD 与本文档
```

数据库与日志位置：打包后为 `%LOCALAPPDATA%\进程监控助手\data\monitor.db` 与 `...\logs\`；开发环境为项目下的 `data\` 与 `logs\`。设置了 `PROCESS_MONITOR_DATA_DIR` 时数据目录以它为准。

### 2.1 指标体系

指标键、分类、单位、中文名、说明集中在 `utils/metrics.py`，其余模块只引用不重复定义。要点：

- Windows 上 psutil 的 vms / pagefile / private 数值相同，已合并为 `memory_private`（“私有字节”），“提交大小峰值”改名“私有字节峰值”；旧键经 `canonical_metric_type` 归一，库里的旧键由 v1→v2 迁移改写。
- 内存类原始值单位为 KB，展示时按量级自适应 KB/MB/GB/TB；计数类指标为整数。
- “泄漏排查预设”（私有字节、句柄、GDI、USER、线程）是监控页默认选择，用户的上次选择保存在 `app_config.last_metrics`，读取时经 `normalize_metrics` 校验，非法或为空回落到预设。
- 新增指标需同步：键常量、分类列表、中文名、单位、说明、（内存类）KB 集合/整数集合，以及采集器中的取值分支。

### 2.2 页面职责

| 页面 | 职责 |
|------|------|
| 实时监控（`monitor_page`） | 进程搜索与 PID 输入、指标选择、周期与备注、创建任务；维护任务卡片（含已结束卡片）；打点、暂停/恢复、停止确认；配额提示 |
| 历史数据（`history_page`） | 任务/指标/时间范围筛选；统计条、趋势图（十字线、打点竖线、PNG/剪贴板导出）、明细表；运行中任务自动刷新；删除已停止任务的数据 |
| 导出数据（`export_page`） | 选择任务、任务摘要、保存路径与覆盖确认，驱动 `ExportWorker` |
| 设置（`setting_page`） | 主题、默认周期、保留策略、托盘开关；数据库占用、清理压缩（后台线程，与运行中任务互斥） |
| 关于（`about_page`） | 版本信息、检查/下载/安装更新、缺少校验信息时的发布页引导 |

页面构造时由 `MainWindow` 注入 `db` 与 `manager`（均为可选，缺省回退到自建/单例，仅为兼容独立构造的测试）。

### 2.3 配置分工

`config.py` 保存随代码发布的常量与缺省值；`app_config.py` 把其中需要用户可调的项包装为可持久化的 `ConfigItem`，运行时业务代码统一读 `cfg.get(...)`。`app_config.py` 的主题项见 7.3 节契约。

## 3. 线程模型与跨线程信号

### 3.1 线程清单

| 线程 | 类型 | 生命周期 |
|------|------|---------|
| UI 主线程 | Qt 事件循环 | 全程；所有控件与定时器只在此线程操作 |
| `MonitorTask` | 每个监控任务一个 QThread | 任务启动到收尾结束；停止后对象不可复用，重新监控要新建任务 |
| `ExportWorker` | CSV 导出，QThread | 一次导出；支持取消 |
| `HistoryRefreshWorker` | 历史页运行中任务的自动刷新查询，QThread | 一次刷新；同一时刻最多一个，只读不改库 |
| `_CleanupWorker`（设置页） | 数据库清理与压缩，QThread | 一次清理；与运行中任务互斥 |
| `UpdateChecker` / `UpdateDownloader` | 更新检查与下载，QThread | 一次检查/下载；下载可取消 |

### 3.2 采集线程的调度与收尾

- **调度**：按 `time.monotonic()` 截止时间推进，每周期 `deadline += interval`，不随采集耗时累积漂移；等待统一用 `threading.Event.wait(剩余时间)`，`stop` / `pause` / `resume` 置标志后 set 事件即可立即唤醒，无需轮询。落后超过一个周期（系统休眠唤醒、严重卡顿）则重置截止时间，不补采。暂停时无超时等待，恢复后立即采一次。
- **落库**：采集结果进缓冲后立即 flush（`SAVE_BATCH_SIZE` 固化为 1）。flush 失败时缓冲保留待下一周期重试，缓冲上限 1000 条（超出丢弃最旧），连续失败达到阈值经 `error_occurred` 通知界面一次。
- **停止**：`stop()` 只置标志并 set 事件，近乎立即返回、不阻塞界面。收尾（最后一次 flush → 写 `stopped` 状态 → 发出 `task_stopped`）全部在线程自己的 `run()` 的 `finally` 中完成，因此界面收到 `task_stopped` 时数据与状态一定已落库。
- **线程对象释放**：`task_stopped` 是工作线程发出的信号，槽仍在发射方调用栈内，不能在其中同步销毁该 QThread。监控页用 `QTimer.singleShot(0, ...)` 延后一轮事件循环再调用 `manager.remove_task`。短命工作线程（导出、清理、历史页刷新）则把 `QThread.finished` 连到 `deleteLater`，而不是在业务完成信号的槽里释放。
- **PID 复用**：采集器依赖 `psutil.Process.is_running()` 对进程创建时间的比对，PID 被新进程占用视为“进程已终止”，任务以该原因结束。

### 3.3 任务状态

| 层 | 状态 | 说明 |
|----|------|------|
| 库（`tasks.status`） | `running` / `stopped` | 启动时写 `running`，收尾写 `stopped`；崩溃遗留的 `running` 由启动校正处理 |
| 线程（`MonitorTask`） | `_running` / `_paused` 标志 + `isRunning()` | `is_running()` 只读 `_running`，不与 `isRunning()` 做或运算（否则 `stop()` 置的 False 会被冲回 True，`wait()` 挂起） |
| 卡片（`TaskCard`） | 运行中 / 已暂停 / 正在停止 / 已结束 | 已结束的卡片不占配额；“重新监控”新建任务 |

`create_task` 按 manager 中保存的任务数限制上限；任务结束后监控页延后调用 `remove_task`，已结束的卡片因此不占配额。界面上的“n/5 运行中”、退出确认与数据库维护互斥都以 `running_task_count`（线程仍在运行，含暂停与收尾中）为口径。

### 3.4 信号链

```
MonitorTask ──data_updated(task_id, {指标: 值})──────┐
            ──metrics_unavailable(task_id, {指标: 原因})┤
            ──task_stopped(task_id, reason)───────────┤→ MonitorManager 同名信号（转发）→ MonitorPage / SettingPage 等
            ──error_occurred(task_id, msg)────────────┘
MonitorManager 另有 task_added / task_started / task_removed / task_limit_reached
MonitorPage ──history_requested(task_id)────────→ MainWindow：切到历史页并选中该任务
            ──task_ended_abnormally(title, msg)──→ MainWindow：窗口在后台时发托盘气泡
AboutPage   ──update_available_silent(info)─────→ MainWindow：非模态 InfoBar（托盘隐藏时补气泡）
ExportWorker ──export_progress / export_finished / error_occurred──→ ExportPage
UpdateChecker / UpdateDownloader ──check_finished / download_progress / download_finished / error_occurred──→ AboutPage
```

- `data_updated` 的载荷是每次新建的 `dict`；采集失败的指标不在其中。
- `MonitorManager` 是 QObject 单例，`MainWindow` 构造时注入统一的 `Database` 实例并向下分发；测试中每个用例前后重置单例。
- 单实例的“激活”消息由 `QLocalServer` 的新连接触发，发出 `SingleInstanceGuard.activation_requested`，由入口连接到激活主窗口。

## 4. 核心数据流

### 4.1 采集 → 落库 → 展示

```
用户选进程/指标/周期/备注 → MonitorPage 校验（不默认选进程、同 PID 重复需确认、配额只计运行中任务）
  → MonitorManager.create_task → 注入同一 Database 的 MonitorTask → start
  → run(): 登记任务行 → 进程存在性检查 → (含 CPU 指标则预热) → 定时循环
        collect_metrics(指标列表)      一个周期共用 oneshot 缓存与同一时间戳
          · 成功的指标 → DataPoint 入缓冲 → flush 到 data_points（同事务更新 sample_count / last_sample_at）
          · 失败的指标 → 不入返回字典，记入 collector.last_unavailable（留空，不记 0）
        emit data_updated → TaskCard 刷新数值、较开始变化量、趋势图
        新出现的不可用指标 → emit metrics_unavailable（每指标每任务一次）→ 卡片“不可用” + 提示原因
  → 进程消失或用户停止 → 收尾 → task_stopped → 卡片保留为“已结束”（查看历史 / 重新监控 / 关闭）
```

采集失败语义是全链路契约：采集器、落库、卡片、历史图表、导出都把“缺失”当作空，绝不当作 0。权限不足时，非管理员运行对更高权限进程只有 `memory_uss` 采不到；其他会话进程（如 session 0 服务）的 GDI/USER 对象数抛“不支持”，与权限不足区分。

### 4.2 展示（历史页）

- 任务列表：`sample_count > 0` 的任务（单条 SQL）；下拉文本含时长、备注与“运行中”。默认范围“全部”；范围锚定该任务最后一个数据点的时间而非当前时刻。
- 图表数据由数据库端分桶降采样（最多 2000 桶，每桶取最小/最大两点）；统计条由 `get_metric_stats` 在整个所选范围上聚合（起点/当前/变化量/增速/最小/最大，增速为最小二乘斜率，单位“每小时”）；明细表只取最近 2000 条并标注总数；打点另查 `task_markers` 画竖线。
- 坐标轴：`chart_axes` 中的纵轴按显示单位取整刻度，计数类指标用整数刻度；`sparkline` 与图表对平直曲线设纵轴最小跨度。
- 运行中任务：页面可见时定时刷新，保留用户的选择与缩放；查询（锚点、明细、分桶、统计、打点）在 `HistoryRefreshWorker` 中执行，worker 只查询并返回 dataclass，主线程槽再套用到控件，绝不在工作线程碰控件；结果带请求序号与（任务、指标、范围）标识，过期或已切换则丢弃；刷新间隔随数据量分三档拉长，明细视图、鼠标悬停图表、窗口最小化时跳过；任务结束时整体重载一次。
- 页面联动：历史页与导出页在 `showEvent` 中刷新任务列表（见 7.5 节）。

### 4.3 导出

`ExportPage` 选择任务与路径（切任务重置默认文件名，目标已存在需确认覆盖）→ `ExportWorker` 在线程中用 `iter_data_points` 游标分批读取，经 `core/export.py` 的纯函数透视为宽表（每行一次采集、每指标一列、末列“打点”）→ 写入同目录 `<目标>.tmp`，成功后 `os.replace` 到目标；取消或失败只删除临时文件，不破坏已有文件。CSV 为 UTF-8 BOM。

### 4.4 自动更新

`UpdateChecker` 拉取 GitHub 最新 Release → `parse_release_info` 提取版本、资产地址与 `asset_digest`。`UpdateDownloader` 只接受 https 且主机在白名单（`github.com`、`objects.githubusercontent.com`、`release-assets.githubusercontent.com` 及其子域）的地址，重定向同样校验；必须带有效的 `sha256:` digest，下载后逐字节校验，不一致删除文件。缺少 digest 时不下载，界面引导到发布页手动下载。静默检查（启动 3 秒后）发现新版本只发信号，由主窗口以非模态 InfoBar 提示。

## 5. 数据库表结构与迁移

### 5.1 表结构（Schema v3，`PRAGMA user_version = 3`）

| 表 | 列 | 说明 |
|----|----|------|
| `tasks` | `task_id` PK, `pid`, `process_name`, `metric_type`, `interval`, `start_time`, `end_time`, `status`, `note`, `sample_count`, `last_sample_at` | `metric_type` 存 JSON 数组文本；`sample_count` 为采样周期数（同一周期多指标算一次），与数据点同事务维护；历史页/导出页按 `sample_count > 0` 判断有数据 |
| `data_points` | `id` PK, `task_id`, `timestamp`, `value`, `metric_type` | `metric_type` 可空（兼容旧数据）；仅有的一个（非 UNIQUE）索引 `(task_id, metric_type, timestamp)` |
| `task_markers` | `id` PK, `task_id`, `timestamp`, `label`, `created_at` | 打点；索引 `(task_id, timestamp)` |

- 外键约束未启用，删除任务时手工级联（`data_points`、`task_markers`、`tasks` 同一事务）。
- 每个连接统一设置 `journal_mode=WAL`、`busy_timeout=5000`、`synchronous=NORMAL`。
- 启动时（任务启动前）各调用一次：`reconcile_orphan_tasks`（把崩溃遗留的 `running` 任务校正为 `stopped`，结束时间取 `last_sample_at`）、`reconcile_sample_counts`（对 `sample_count=0` 但有数据点的任务重算，兜底“回退旧版再升级”的情形）、`cleanup_old_tasks`（保留天数默认 0 = 禁用，且必须在孤儿校正之后）。这些方法刻意不放在构造函数里。

### 5.2 迁移机制（v0 → v3）

- 新库直接建当前结构并置 `user_version`；旧库按 `user_version` 链式迁移：
  - **v0 → v1**：`data_points` 补 `metric_type` 并按任务原指标回填；`tasks.metric_type` 由裸字符串转 JSON 数组。
  - **v1 → v2**：`memory_vms` / `memory_pagefile` 并入 `memory_private`，同一 `(task_id, timestamp)` 的重复数据点去重。
  - **v2 → v3**：`tasks` 增加 `note` / `sample_count` / `last_sample_at`（幂等，先查列）；新建 `task_markers`；删除孤儿数据点；回填 NULL 的 `metric_type`；索引收敛为 `(task_id, metric_type, timestamp)` 并删除旧索引；回填 `sample_count` 与 `last_sample_at`。
- **事务与备份**：迁移前先 `wal_checkpoint(TRUNCATE)` 再文件级备份为 `monitor.db.bak_v{原版本}`；整条迁移链在一个显式事务里执行（DDL 与 `user_version` 同事务），任一步失败整体回滚，随后从备份还原并重试一次。
- **三态结果**（互斥，主窗口据此提示）：`migration_failed`（两次均失败，已还原旧数据，本次运行新数据无法保存）、`data_reset`（还原也失败，损坏库改名为 `.broken_<时间戳>`，以空库运行）、`backup_aborted`（备份失败，已中止迁移，旧库原样保留）。
- 整个流程每进程只尝试一次（类级 guard），避免反复实例化 `Database` 重复备份。
- 迁移代码用字面量写死别名与版本号，不引用会演进的常量；新增迁移时只追加 `_migrate_vN_to_vN+1` 并在链上加一环。
- 旧库迁移未成功时，`get_tasks_with_data` 在缺少 `sample_count` 列时回退为按数据点判断，旧指标键在界面上仍显示为“私有字节”。

## 6. 退出路径不变式

`main.py` 设置 `setQuitOnLastWindowClosed(False)`，因此唯一真退出路径是 `MainWindow.closeEvent` 清理完成后显式调用 `QApplication.quit()`；`main()` 在 `exec_()` 返回后以 `os._exit` 终止进程，规避仍在阻塞的后台线程（如卡在 `urlopen` 的下载线程）被销毁时 Qt 的致命中止（0xC0000409）。以下不变式不得破坏：

1. 默认配置（不最小化到托盘）且无运行中任务时，关窗直接走清理并退出。
2. 托盘菜单“退出”与关于页“立即安装”都置 `_really_quit = True`，绕过隐藏分支与确认对话框，走同一条真退出路径。系统注销/关机（`commitDataRequest`，DirectConnection）同样置位，避免确认框阻塞关机。
3. 隐藏到托盘不停止任务、不做任何清理，仅忽略本次关闭事件。
4. 有运行中任务且并非 `_really_quit` 时弹出三选（停止并退出 / 最小化到托盘 / 取消）；开启“关闭时最小化到托盘”且托盘可用时直接隐藏。
5. 无托盘环境（offscreen/CI 或精简系统）下 `tray_icon is None`，所有托盘分支天然短路，行为退化为无托盘现状。
6. 真退出的清理整体包进 `try/finally`，`QApplication.quit()` 放在 `finally`：清理中途抛异常也必须退出，否则窗口已隐藏而事件循环不退出，用户无法恢复。
7. 清理顺序：`stop_all_tasks`（先给全部任务置停止标志，再逐个**无超时** `wait`，保证收尾落库完成——这是 `os._exit` 的数据安全前提，不得给它加超时）→ 对仍在收尾的任务补限时 join → 取消并等待下载线程 → 等待更新检查线程 → 取消并等待导出线程 → 等待清理线程 → 等待历史页刷新线程。其余线程用 `shutdown_thread` 限时等待，超时只记日志。
8. 单实例守卫在 `QApplication` 创建之后、窗口与线程创建之前运行：连上已有实例则发送激活消息并 `os._exit(0)`；监听失败降级为允许多开，不能因单实例机制本身阻止用户使用。

## 7. 关键契约

### 7.1 采集失败语义

采不到的指标**不记 0**：`collect_metrics` 的返回字典中不包含它，原因记入 `collector.last_unavailable`；任务通过 `metrics_unavailable` 通知界面；库里该时间戳不存在对应行，历史图表与 CSV 按空处理。不适用的指标（如其他会话进程的 GDI/USER）以 `MetricNotSupported` 表达，与权限不足（`AccessDenied`）区分，文案不同。进程不存在或 PID 被复用时 `collect_metrics` 返回 `None`，任务据此以“进程已终止”结束。

### 7.2 时间戳 ISO 文本纪律

库内时间戳是 TEXT，一律为 `datetime.isoformat()` 形态，比较靠字典序。所有 `since_iso` 参数只接受 ISO 字符串；绘图用的 epoch float（`dp.timestamp.timestamp()`）严禁传入查询：SQLite 的类型亲和性会把它转成文本参与比较，恒小于任何 ISO 串，过滤会静默失效。

### 7.3 主题 themeMode 禁止重定义

`app_config.AppConfig` 直接复用 `QConfig` 基类内置的 `themeMode`，**不得**重新声明同名 `ConfigItem`。`qfluentwidgets.setTheme()` 操作模块级单例 `qconfig.themeMode`，`QConfig.set()` 又用 `is` 身份比较判断是否主题项；重定义会产生两个互不联动的对象，表现为“设置页选了深色没生效”“重启后主题还原”。启动时应用主题要传原始配置值 `cfg.get(cfg.themeMode)`（可能是 AUTO），不能传解析后的 `qconfig.theme`，否则会把“跟随系统”静默覆写成具体主题。

### 7.4 ComboBox 先 addItem 后 setItemData

qfluentwidgets 的 `ComboBox.addItem` 不返回索引，且不能在添加前设置 userData：必须先 `addItem(text)`，再用 `index = count() - 1` 调 `setItemData(index, value)`。任务下拉与指标下拉都靠 userData 携带 `task_id` / `metric_type`，文本只用于显示。

### 7.5 showEvent 联动

页面之间没有直接的数据推送，新建任务后历史页与导出页的任务列表靠各自的 `showEvent` 在每次切入时重新加载（历史页还借此启动自动刷新计时、`hideEvent` 停止）。新增依赖其他页面数据的页面时沿用此机制，并注意长耗时操作（如导出）期间用户切走再切回会重复触发 `showEvent`，需保证控件状态幂等。

### 7.6 数据库维护互斥

清理/压缩数据库与运行中任务互斥：设置页先 `manager.begin_maintenance()`（有运行中任务时拒绝），维护期间 `create_task` / `start_task` 被拒绝，线程 `finished` 时 `end_maintenance`。删除任务数据（`delete_task_data`）对运行中任务同样拒绝。

### 7.7 日志与异常兜底

`main()` 最早处调用 `setup_logging`（根 logger 挂 `RotatingFileHandler`，5MB x 5）与 `install_excepthook`（未捕获异常记日志，并在主线程弹窗提示日志位置；`faulthandler` 把致命信号写入 `crash.log`）；工作线程中的异常只记日志、不打断采集。各模块一律用 `logging.getLogger(__name__)`，数据库操作失败返回 `False` / 空结果并记日志，不向 UI 抛出。

### 7.8 其他约定

- `MonitorManager` 单例的 `db` 仅首次构造时生效；`MainWindow` 注入的 `Database` 是全应用唯一实例。
- 监控任务停止后线程对象不可复用，`start_task` 拒绝已结束的任务；“重新监控”通过新建任务实现。
- 耗时操作不放 UI 线程；UI 写库一律经 manager，读查询可走注入的 `Database`。

## 8. 测试与 CI

- 运行：`python -m pytest tests/`；用例清单用 `pytest --collect-only -q` 查看，本文不列清单。
- `pytest.ini` 只配置 `testpaths = tests`。`tests/conftest.py` 默认把 `QT_QPA_PLATFORM` 设为 `offscreen`，并通过自动 fixture 把 `config.DATA_DIR` / `DB_PATH` / `UPDATE_PREFS_PATH` 与 `app_config.CONFIG_PATH` 指向临时目录，**测试不得触碰开发机的 `data\`**；另有会话级 `QApplication` 与每用例前后的 `MonitorManager` 单例重置。新增涉及路径的模块时，要在隔离 fixture 里一并覆写。
- 数据目录也可由环境变量 `PROCESS_MONITOR_DATA_DIR` 指定，便于便携运行与手工验证。
- 测试分层：数据层与迁移（含旧库构造）、采集与调度鲁棒性、导出纯函数与线程、更新校验、页面流程与界面契约（布局、排版、格式化）、单实例、日志与隔离；`tests/e2e/` 是 offscreen 下的全链路冒烟（建任务 → 采集 → 历史页 → 导出 → 设置页 → 关窗）。涉及 GUI 的用例用 offscreen，不弹窗口。
- CI（`.github/workflows/ci.yml`）：push 到 main 与 PR 触发，`windows-latest` + Python 3.11，用 `requirements-lock.txt` 安装依赖，设置 `QT_QPA_PLATFORM=offscreen` 后运行 `pytest tests/ -v`。
- 发布前建议另用真窗口跑一次 `tests/e2e/test_gui_smoke.py`（说明见打包文档）。

## 9. 打包与发布链

```
改版本号（config.APP_VERSION）→ 全量测试 → build\build.bat → GitHub Release（上传安装包）
```

- `build\build.bat` 是无人值守一键脚本：读取版本号 → 生成 `version_info.txt` → PyInstaller 以 onedir 模式打包（`ProcessMonitor.spec`）→ 校验产物体积/文件数并冒烟启动 → Inno Setup（`setup.iss`）编译安装包 → 产出 `dist\installer\进程监控助手_v{版本}_Setup.exe` 及同内容的 `Windows_v{版本}_Setup.exe`（后者用于 Release 资产命名）。
- 打包用 `requirements-lock.txt` 复现验证过的精确依赖；`requirements.txt` 只声明宽松下限供开发。
- 自动更新依赖 Release 资产的 `digest`（`sha256:`）：发布时上传的资产由 GitHub 生成摘要，应用据此校验；没有摘要时用户只能手动下载。
- 安装目录与数据目录分离（数据在 `%LOCALAPPDATA%`），覆盖安装与卸载重装不影响历史数据。
- 不提交 `build/` 下的临时产物、`dist/`、DLL/EXE、数据库；详细步骤、常见问题见 `build/README_打包说明.md`。
